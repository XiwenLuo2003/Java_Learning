## 1. ArrayList 扩容机制

> 代码：[ArrayListDemo](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L16)

### Q1：ArrayList 是怎么扩容的？（高频）

* **满分话术**：
  1. **底层**是一个 `Object[] elementData` 数组，`size` 记录元素个数。
  2. **懒初始化**：`new ArrayList<>()` 时并不分配数组，而是指向一个共享的空数组 `DEFAULTCAPACITY_EMPTY_ELEMENTDATA`；**第一次 `add` 时才分配长度为 10 的数组**。
  3. **扩容时机**：`add` 时发现 `size == elementData.length`，调用 `grow()`。
  4. **扩容大小**：新容量 = 旧容量 + 旧容量 >> 1，也就是 **1.5 倍**（[grow 源码与精简版](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L36)），然后 `Arrays.copyOf` 把旧数组拷贝到新数组。如果一次 `addAll` 很多元素，1.5 倍还不够，就直接扩到需要的大小。
  5. **实测序列**：0 → 10 → 15 → 22 → 33 → 49（[实验 1](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L44)）。
  6. **一个细节**：`new ArrayList<>(0)` 用的是另一个空数组 `EMPTY_ELEMENTDATA`，你明确说了要 0，第一次 `add` 就不会给 10，扩容序列是 0 → 1 → 2 → 3 → 4 → 6 → 9（[实验 2](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L59)）。两个空数组就是为了区分这两种情况。
* **优化**：能预估数量时，构造时直接指定容量，或者先调用 `ensureCapacity(n)`，避免多次扩容和数组拷贝。
* **为什么是 1.5 倍**：太小（比如每次 +1）会频繁扩容拷贝；太大（比如 2 倍）浪费空间。1.5 倍是折中，而且用位运算 `>> 1` 计算很快。

### Q2：ArrayList 和 LinkedList 的区别？

* **满分话术**：
  | | ArrayList | LinkedList |
  |---|---|---|
  | 底层 | 动态数组 | 双向链表 |
  | 随机访问 `get(i)` | O(1)，实现了 `RandomAccess` 接口 | O(n)，要从头或尾遍历 |
  | 头部插入删除 | O(n)，要移动后面所有元素 | O(1) |
  | 尾部追加 | 均摊 O(1) | O(1) |
  | 内存 | 紧凑，CPU 缓存友好；但有预留空间 | 每个节点多两个指针，内存碎片化 |

  **实际开发几乎都用 ArrayList**：就算是中间插入，ArrayList 的 `System.arraycopy` 是连续内存拷贝，速度非常快，而 LinkedList 先要 O(n) 遍历找到位置，缓存命中率还低。需要队列 / 栈时用 `ArrayDeque`，也比 LinkedList 快。

### Q3：遍历时删除元素为什么会抛 `ConcurrentModificationException`？怎么正确删除？

* **满分话术**：
  1. **fail-fast 机制**：集合有一个 `modCount` 字段，每次结构修改（增、删）都 +1。迭代器创建时记下 `expectedModCount = modCount`，每次 `next()` 都检查两者是否相等，不等就抛 `ConcurrentModificationException`。foreach 底层就是迭代器，循环里调用 `list.remove()` 改了 `modCount`，迭代器的 `expectedModCount` 没变，下一次 `next()` 就报错（[实验 3](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L78)）。
  2. **一个反直觉的特例**：删的是倒数第二个元素时不报错。因为删完 `size` 减 1，`hasNext()` 判断 `cursor != size` 为 false，循环直接结束，最后一个元素也没被遍历到。
  3. **正确做法**：用迭代器自己的 `iterator.remove()`（[第 99 行](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L99)），它会同步更新 `expectedModCount`；或者用 JDK 8 的 `removeIf`（[第 103 行](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L103)）。
  4. **注意**：fail-fast 只是“尽力检测”，**不是线程安全的保证**。多线程下要用 `CopyOnWriteArrayList`（写时复制，迭代的是快照，不会抛异常）或 `Collections.synchronizedList`。

### Q4：`Arrays.asList` 有什么坑？

* **满分话术**（[实验 4](code/src/main/java/com/example/collection/arraylist/ArrayListDemo.java#L108)）：
  1. 返回的是 `Arrays` 的**内部类** `ArrayList`，不是 `java.util.ArrayList`，它没有重写 `add`/`remove`，调用会抛 `UnsupportedOperationException`；
  2. 它是原数组的**视图**，修改数组，list 也跟着变；
  3. 传基本类型数组 `Arrays.asList(new int[]{1, 2})` 得到的是只有一个元素（`int[]`）的 List。
  
  需要可变的 List 时写 `new ArrayList<>(Arrays.asList(...))`。JDK 9 的 `List.of` 则是**完全不可变**的，连 `set` 都不行，而且不允许 null。

## 2. HashMap 底层结构（JDK 1.7 vs 1.8）

> 代码：[MiniHashMap](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L15)、[HashMapDemo](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L15)、[Jdk7ResizeLoopDemo](code/src/main/java/com/example/collection/hashmap/Jdk7ResizeLoopDemo.java#L28)

### Q1：HashMap 的底层结构是什么？JDK 1.7 和 1.8 有什么区别？（高频）

* **满分话术**：JDK 1.7 是**数组 + 链表**，JDK 1.8 是**数组 + 链表 + 红黑树**。数组的每个位置叫一个“桶”，hash 冲突的元素在同一个桶里串成链表；1.8 里链表太长会转成红黑树，把最坏情况的查找从 O(n) 降到 O(log n)。

  | | JDK 1.7 | JDK 1.8 |
  |---|---|---|
  | 结构 | 数组 + 链表 | 数组 + 链表 + 红黑树 |
  | 节点 | `Entry` | `Node`（树节点是 `TreeNode`） |
  | 链表插入 | **头插法** | **尾插法**（[putVal 第 105 行](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L105)） |
  | hash 扰动 | 4 次位移 + 5 次异或 | 1 次：`h ^ (h >>> 16)`（[hash()](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L62)） |
  | 扩容时机 | 先判断扩容，再插入 | 先插入，再判断扩容（[第 127 行](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L127)） |
  | 扩容迁移 | 每个节点重新算下标，头插导致链表反转 | 按 `hash & oldCap` 拆成 lo、hi 两条链，保持原顺序（[resize](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L196)） |
  | 并发扩容 | 可能**链表成环**，get 时死循环 | 不会成环，但仍会丢数据 |

### Q2：为什么链表长度超过 8 才转红黑树？为什么退化阈值是 6？为什么不直接用红黑树？

* **满分话术**：
  1. **为什么不一开始就用红黑树**：`TreeNode` 的大小约是普通 `Node` 的两倍，而且插入要旋转、变色维护平衡。链表短的时候，遍历几个节点比维护一棵树还快、还省内存。
  2. **为什么是 8**：源码注释里给了依据。在 hash 分布良好、负载因子 0.75 的情况下，一个桶里的节点数服从**泊松分布**，长度达到 8 的概率约为**千万分之六**。也就是说，正常情况下几乎不会转树，转树是为了防御**极端情况**（hashCode 写得很差，或者被人故意构造 hash 冲突攻击）。
  3. **准确的触发条件**：插入后链表长度**超过 8**（源码里 `binCount >= TREEIFY_THRESHOLD - 1` 时新节点是第 9 个，[见注释](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L107)），**并且** table 容量 **≥ 64**。容量不到 64 时只扩容不转树（[treeifyBin](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L134)），因为容量小时冲突多半是因为数组太小，扩容能把链表拆短，代价更低。
  4. **实测**（[实验 5](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L100)，反射读真实 HashMap）：用 hashCode 恒为 1 的 key 往同一个桶里放，第 9 个 key 进来时容量 16 → 32，第 10 个 32 → 64，**第 11 个才真正变成 `TreeNode`**。
  5. **退化阈值 6**：扩容拆分或删除后，树节点数 ≤ 6 时退化回链表。8 和 6 之间留了缓冲，防止节点数在 8 附近来回增删时频繁地转树、退化。
  6. **为什么用红黑树不用 AVL**：AVL 是严格平衡，查询略快但插入删除要更多旋转；红黑树是近似平衡，插入最多 2 次旋转、删除最多 3 次，写多读多的场景综合性能更好。

## 3. HashMap.put 流程、扰动函数、下标计算

> 代码：[MiniHashMap#putVal](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L81)（建议和 IDEA 里的 JDK 源码分屏对照）

### Q1：讲一下 HashMap 的 put 流程？（快手一面原题）

* **流程图**（路线要求自己画一遍）：
  ```
  put(key, value)
    │
    ├─ hash = key == null ? 0 : h ^ (h >>> 16)              扰动
    │
    ├─ table 为空？──是──▶ resize() 初始化（默认 16，阈值 12）
    │
    ├─ i = (n - 1) & hash
    │
    ├─ tab[i] 为空？──是──▶ 直接放新 Node ─────────────────────┐
    │       │否                                                │
    │       ├─ 头节点 key 相同？──是──▶ 记下这个节点 e          │
    │       ├─ 头节点是 TreeNode？──是──▶ putTreeVal 树插入     │
    │       └─ 遍历链表：找到相同 key 就记下 e；                │
    │                    走到尾部就尾插，长度 > 8 则 treeifyBin │
    │                    （容量 < 64 先扩容，≥ 64 才转树）       │
    │                                                           │
    ├─ e != null（key 已存在）？──是──▶ 覆盖 value，返回旧值（size 不变）
    │                                                           │
    └─ ++size > threshold？──是──▶ resize() 扩容 ◀─────────────┘
  ```
* **满分话术**（对照 [putVal](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L81)）：
  1. **计算 hash**：`key.hashCode()` 的**高 16 位异或低 16 位**（[hash()](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L62)），null 的 hash 是 0，所以 HashMap 允许一个 null key，放在 0 号桶。
  2. **懒初始化**：table 为空时调用 `resize()` 创建数组，默认长度 16。
  3. **算下标**：`(n - 1) & hash`（[第 90 行](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L90)），桶为空就直接放进去。
  4. **处理冲突**：先比头节点（**hash 相等且 key `==` 或 `equals`**）；头节点是红黑树就走树的插入；否则遍历链表，找到相同 key 就停下，走到尾部就**尾插**，插入后链表长度超过 8 调用 `treeifyBin`。
  5. **key 已存在**：覆盖 value 并**返回旧值**（[第 120 行](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L120)），这种情况 `size` 不变，也不会触发扩容。
  6. **扩容检查**：`++size > threshold`（容量 × 0.75）就 `resize()`（[第 127 行](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L127)）。

### Q2：为什么要做扰动？为什么是高 16 位异或低 16 位？

* **满分话术**：下标是 `(n - 1) & hash`，n 比较小时只有 hash 的**低几位**参与运算（n = 16 时只看低 4 位），高位的差异被完全丢掉。如果一批 key 的 hashCode 恰好只在高位不同，就会全部挤进同一个桶。把高 16 位异或到低 16 位上，让高位特征也参与下标计算，冲突就少了。用异或是因为它不会像 `&` 偏向 0、`|` 偏向 1，能保留两边的信息。
* **实测**（[实验 1](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L28)）：hashCode 为 `0x00000000`、`0x00010000` …… `0x00070000` 的 8 个 key，不扰动全在 0 号桶，扰动后分散到 0~7 号桶。
* **为什么只扰动一次**：JDK 1.7 做了 4 次位移 5 次异或，1.8 认为链表过长已经有红黑树兜底，扰动一次在效果和速度之间取得平衡。

### Q3：为什么重写 `equals` 必须重写 `hashCode`？用什么做 key 比较好？

* **满分话术**：
  1. HashMap 先用 hash 定位桶，**hash 不同根本不会去比较 equals**。只重写 `equals` 的话，两个“相等”的对象 hashCode 不同，落在不同的桶，HashMap 会认为是两个 key（[实验 6](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L135)：`size = 2`，`get` 拿不到）。规范要求：equals 相等，hashCode 必须相等；反之不要求。
  2. **key 最好用不可变对象**（String、Integer、record）。可变对象放进去之后被修改，hashCode 变了，就再也找不到了，而且一直占着内存（[实验 7](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L144)）。String 还缓存了 hashCode，用作 key 性能更好。

## 4. 容量为什么是 2 的幂、扩容为什么乘 2

> 代码：[MiniHashMap#tableSizeFor](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L71)、[MiniHashMap#resize](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L151)、[HashMapDemo 实验 2~4](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L40)

### Q1：为什么容量必须是 2 的幂？为什么每次扩容乘 2？（快手一面原题）

* **满分话术**：
  1. **算下标快**：当 n 是 2 的幂时，`n - 1` 的二进制是全 1（16 - 1 = `1111`），`(n - 1) & hash` 就是取 hash 的低几位，**完全等价于 `hash % n`**，但位运算比取模快得多。还有一个好处是负数 hash 也能得到合法下标（`-17 % 16 = -1`，而 `15 & -17 = 15`）。如果 n 不是 2 的幂，比如 10（`1001`），中间两位永远是 0，有些桶永远用不到，冲突会大大增加（[实验 2](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L40)）。
  2. **扩容迁移高效**：容量翻倍后，新下标比旧下标只多看 hash 的**一位**，也就是 `oldCap` 对应的那一位。这一位是 0 就留在**原位置 j**，是 1 就去 **j + oldCap**，不需要重新算 hash（[resize 里的 `hash & oldCap`](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L196)）。
  3. **实测**（[实验 4](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L73)）：5、21、37、53 在容量 16 时都在 5 号桶；扩容到 32 后，`hash & 16` 为 0 的 5、37 留在 5 号桶，为 16 的 21、53 去了 21 号桶，而且两条链都保持原来的顺序。
  4. 所以“2 的幂”和“2 倍扩容”是配套的：只有每次乘 2，容量才能一直保持 2 的幂。

### Q2：`new HashMap(10)` 的容量是多少？想放 100 个元素，初始容量应该传多少？

* **满分话术**：
  1. 构造器会用 `tableSizeFor` 把传入的值调整成 **≥ 它的最小 2 的幂**（[tableSizeFor](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L71)），所以 `new HashMap(10)` 是 16，`new HashMap(17)` 是 32。而且构造时并不创建数组，这个值先暂存在 `threshold` 里，第一次 put 时 `resize()` 才拿出来当容量（[resize 的 oldThr 分支](code/src/main/java/com/example/collection/hashmap/MiniHashMap.java#L164)）。
  2. 放 100 个元素：直接传 100 → 容量 128、阈值 96，放到第 97 个还是会扩容（[实验 3](code/src/main/java/com/example/collection/hashmap/HashMapDemo.java#L51)）。应该传 `预期数量 / 0.75 + 1`，即 134 → 容量 256。Guava 的 `Maps.newHashMapWithExpectedSize(100)`、JDK 19 的 `HashMap.newHashMap(100)` 帮你算好了。

### Q3：负载因子为什么是 0.75？

* **满分话术**：是**时间和空间的折中**。负载因子越大，数组利用率越高，但冲突越多、链表越长，查询变慢；越小冲突越少，但浪费空间、扩容更频繁。0.75 下按泊松分布，桶里元素数达到 8 的概率极低，查询基本保持 O(1)。另外 0.75 × 2 的幂总是整数，阈值好算。

## 5. HashMap 线程不安全与 JDK 7 死循环

> 代码：[Jdk7ResizeLoopDemo](code/src/main/java/com/example/collection/hashmap/Jdk7ResizeLoopDemo.java#L28)、[ConcurrentHashMapDemo 实验 1](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L19)

### Q1：HashMap 为什么线程不安全？JDK 7 的死循环是怎么产生的？

* **满分话术**：
  1. **JDK 7 并发扩容成环**：扩容的 `transfer` 用**头插法**把节点搬到新数组，会把链表顺序反转。两个线程同时扩容、共享同一批节点时：
     * 线程 1 读到 `e = 3, next = 7` 后被挂起（[第 74 行](code/src/main/java/com/example/collection/hashmap/Jdk7ResizeLoopDemo.java#L74)）；
     * 线程 2 完成扩容，链表被反转成 `7 → 3`，此时 `7.next = 3`（[第 79 行](code/src/main/java/com/example/collection/hashmap/Jdk7ResizeLoopDemo.java#L79)）；
     * 线程 1 恢复，先把 3 头插进去，再处理 7，读到的 `7.next` 已经变成 3，于是又去处理 3，执行 `3.next = 7`，**形成 3 → 7 → 3 的环**（[第 91 行](code/src/main/java/com/example/collection/hashmap/Jdk7ResizeLoopDemo.java#L91)），原来排在后面的 5 也丢了。
     * 之后 `get` 一个落在这个桶、但不存在的 key，就会在环上无限循环，**CPU 100%**。
  2. **JDK 8 的改进**：改成尾插，扩容时按 lo、hi 两条链保持原来的相对顺序，不会再成环。
  3. **但 JDK 8 依然线程不安全**：两个线程同时发现同一个桶为空，各自 `tab[i] = newNode`，后写的覆盖先写的；`++size` 不是原子操作，也会少加。实测 4 个线程各放 1 万个不同的 key，size 经常不到 4 万（[实验 1](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L19)）。
  4. 所以多线程场景要用 `ConcurrentHashMap`。

## 6. ConcurrentHashMap 并发安全原理

> 代码：[MiniConcurrentHashMap](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L13)、[ConcurrentHashMapDemo](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L13)

### Q1：ConcurrentHashMap 是怎么保证线程安全的？JDK 1.7 和 1.8 有什么区别？（高频）

* **满分话术**：
  1. **JDK 1.7：分段锁**。整个 Map 分成 16 个 `Segment`（继承 `ReentrantLock`），每个 Segment 是一个小 HashMap。put 时先定位 Segment 再加锁，不同 Segment 可以并发写，最大并发度就是 Segment 的个数，而且 Segment 数量创建后不能改。
  2. **JDK 1.8：CAS + synchronized，锁粒度细化到每个桶**。去掉了 Segment，结构和 HashMap 一样是数组 + 链表 + 红黑树。put 流程（[MiniConcurrentHashMap#put](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L52)）：
     * key、value 都不能为 null；
     * 自旋：table 没初始化就先初始化（也是 CAS 控制只有一个线程初始化）；
     * **桶为空：CAS 放入新节点**，不加锁（[第 66 行](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L66)），失败说明别的线程抢先了，重新循环；
     * **头节点 hash 是 MOVED（-1）**：说明正在扩容，当前线程去**帮忙迁移**（`helpTransfer`）；
     * **否则 `synchronized` 锁住头节点**（[第 79 行](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L79)），加锁后先确认头节点没变（[第 81 行](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L81)），再按链表或红黑树插入；
     * 最后 `addCount` 计数，并检查是否需要扩容（[第 108 行](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L108)）。
  3. **为什么 1.8 用 synchronized 而不是 ReentrantLock**：锁的是单个桶，粒度很细，竞争很少；JDK 6 之后 synchronized 有锁升级优化，低竞争下开销很小；而且不用像 Segment 那样每个桶都创建一个锁对象，省内存。
  4. **实测**（[实验 2](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L34)）：4 线程并发写 4 万个 key，ConcurrentHashMap 和 MiniConcurrentHashMap 的 size 都是 40000，还能看到 CAS 成功、CAS 失败、加锁插入各发生了多少次。

### Q2：ConcurrentHashMap 的 get 为什么不用加锁？

* **满分话术**：读操作全程无锁，靠 **volatile** 保证可见性：table 数组元素用 `Unsafe.getReferenceAcquire`（volatile 语义）读取，`Node` 的 `val` 和 `next` 都是 volatile 字段（[Node 定义](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L18)），其他线程写入后读线程立刻可见。如果正好碰上扩容，头节点是 `ForwardingNode`，它的 `find` 方法会去新数组里查。所以 get 是**弱一致**的：可能读不到“正在进行中”的写入，但不会读到错乱的数据。

### Q3：ConcurrentHashMap 的 size 是怎么算的？扩容是怎么做的？

* **满分话术**：
  1. **size**：用 `baseCount + CounterCell[]` 计数，和 `LongAdder` 是同一个思路（[MiniConcurrentHashMap 用的就是 LongAdder](code/src/main/java/com/example/collection/concurrent/MiniConcurrentHashMap.java#L34)）。没有竞争时 CAS 修改 `baseCount`；CAS 失败说明竞争激烈，就分散到不同的 `CounterCell` 上累加。`size()` 时把 `baseCount` 和所有 Cell 加起来，所以是个**估计值**，并发修改时不是精确快照。
  2. **扩容**：**多线程协同迁移**。第一个发现需要扩容的线程创建 2 倍大小的新数组，然后从后往前**按区间**（每个线程一次领至少 16 个桶）迁移；迁移完一个桶就在旧数组放一个 `ForwardingNode`（hash = MOVED）。其他线程 put 时遇到 `ForwardingNode` 就去帮忙迁移剩下的区间，读线程遇到它就去新数组查。`sizeCtl` 字段控制初始化和扩容状态：负数表示正在初始化或扩容。

### Q4：为什么 ConcurrentHashMap 不允许 null？用了 ConcurrentHashMap 就一定线程安全吗？

* **满分话术**：
  1. **不允许 null 的原因是二义性**：`get(key)` 返回 null 时，分不清是“没有这个 key”还是“value 就是 null”。HashMap 单线程下可以再调 `containsKey` 确认，但并发下两次调用之间数据可能已经被别的线程改了，无法确认。所以干脆禁止（[实验 4](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L78)）。
  2. **不一定**：它只保证**单个方法**是原子的。“先 get 再 put”这种复合操作，两个线程可能读到同一个旧值，各自 +1 写回，结果少加（[实验 3 的错误写法](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L63)）。要用它提供的原子复合方法：`merge`、`compute`、`computeIfAbsent`、`putIfAbsent`，它们在桶锁内完成“读-改-写”（[第 69 行](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L69)）。

### Q5：ConcurrentHashMap、Hashtable、Collections.synchronizedMap 有什么区别？

* **满分话术**：`Hashtable` 和 `Collections.synchronizedMap` 都是**整张表一把锁**（方法上加 synchronized，或者对一个 mutex 对象加锁），任何时刻只有一个线程能读写，并发性能很差；而且它们的迭代器是 fail-fast 的，遍历时要手动对整个 Map 加锁。`ConcurrentHashMap` 锁粒度是**单个桶**，读不加锁，迭代器是**弱一致**的，遍历时修改不会抛 `ConcurrentModificationException`（[实验 5](code/src/main/java/com/example/collection/concurrent/ConcurrentHashMapDemo.java#L86)）。`Hashtable` 已经是遗留类，不要再用。

## 高频追问速查

| 问题 | 一句话答案 |
|---|---|
| HashMap 默认容量、负载因子、阈值？ | 16、0.75、12；第一次 put 才创建数组 |
| HashMap 允许 null 吗？ | 允许一个 null key（hash 为 0，放 0 号桶）和多个 null value；ConcurrentHashMap、Hashtable 都不允许 |
| HashMap 的 key 能重复吗？怎么判断重复？ | 不能。hash 相等 且（`==` 或 `equals`）就是同一个 key，覆盖 value |
| 链表转红黑树的条件？ | 链表长度超过 8 且容量 ≥ 64；容量不到 64 先扩容 |
| 红黑树什么时候退化回链表？ | 树节点数 ≤ 6（扩容拆分或删除时） |
| 扩容后元素的新位置？ | `hash & oldCap == 0` 留在原位置，否则去“原位置 + oldCap” |
| JDK 8 HashMap 还会死循环吗？ | 扩容不会成环了；但并发下仍会丢数据，极端情况下红黑树操作也可能出问题，并发场景一律用 ConcurrentHashMap |
| LinkedHashMap 怎么实现 LRU？ | 构造时 `accessOrder = true`，按访问顺序维护双向链表；重写 `removeEldestEntry` 在超出容量时返回 true |
| TreeMap 的底层？ | 红黑树，按 key 排序，key 要实现 `Comparable` 或传 `Comparator` |
| HashSet 的底层？ | 一个 HashMap，元素作为 key，value 是一个固定的 `PRESENT` 对象 |
| fail-fast 和 fail-safe？ | fail-fast：检测到并发修改就抛异常（ArrayList、HashMap）；fail-safe：遍历快照或弱一致视图，不抛异常（CopyOnWriteArrayList、ConcurrentHashMap） |
| CopyOnWriteArrayList 适合什么场景？ | 读多写极少（如配置、监听器列表）；每次写都复制整个数组，写多了很慢，且读到的可能是旧数据 |
