## 1. 数据结构与底层

> 代码：[`MiniSds`](code/src/main/java/com/example/redis/principle/MiniSds.java#L18)、[`MiniSkipList`](code/src/main/java/com/example/redis/principle/MiniSkipList.java#L14)、[`DatatypeDemoController`](code/src/main/java/com/example/redis/datatype/DatatypeDemoController.java#L23)

### Q1：Redis 有哪 5 种基础类型？各自底层是什么？常用场景？

* **满分话术**：

  | 类型 | Redis 7 常见编码 | 典型场景 |
  |---|---|---|
  | String | SDS（`int`/`embstr`/`raw`） | 缓存对象、计数器、分布式锁、BitMap / HyperLogLog 也挂在 String 上 |
  | Hash | `listpack`（小）/ `hashtable`（大） | 对象多字段、购物车、会话 |
  | List | `listpack` / `quicklist` | 最新列表、简陋消息队列 |
  | Set | `intset` / `hashtable` | 去重、共同关注（`SINTER`）、一人一单（`SISMEMBER`） |
  | ZSet | `listpack`（小）/ `skiplist` + `hashtable`（大） | 排行榜、滑动窗口、延迟队列、字段过期索引 |

  命令演示见 [第 1 组请求](code/requests.http)。**面试常追问的两个底层**：String 的 SDS、ZSet 的跳表。

### Q2：SDS 比 C 字符串好在哪里？扩容策略是什么？

* **满分话术**（跑 [`MiniSds#main`](code/src/main/java/com/example/redis/principle/MiniSds.java#L104)）：
  1. **O(1) 取长度**：头里存了 `len`，不用 `strlen`。
  2. **二进制安全**：靠 `len` 判断结尾，中间可以有 `\0`，所以能存图片、protobuf（[实验 1](code/src/main/java/com/example/redis/principle/MiniSds.java#L105)）。
  3. **空间预分配**：`sdsMakeRoomFor`——小于 1MB 时新容量 = `2 × (len+addlen)`，大于等于 1MB 时每次多给 1MB（[源码逻辑](code/src/main/java/com/example/redis/principle/MiniSds.java#L51)、[实验 2](code/src/main/java/com/example/redis/principle/MiniSds.java#L115)），避免每次追加都 `realloc`。
  4. **惰性空间释放**：`sdsclear` / `sdsrange` 只改 `len`，`alloc` 不动，下次追加直接复用（[实验 3](code/src/main/java/com/example/redis/principle/MiniSds.java#L131)）。
  5. **多种头部**：按长度选 `sdshdr5/8/16/32/64`，短 key 只多 1 字节开销（[实验 4](code/src/main/java/com/example/redis/principle/MiniSds.java#L139)）。

### Q3：ZSet 为什么用跳表？和红黑树比呢？

* **满分话术**（跑 [`MiniSkipList#main`](code/src/main/java/com/example/redis/principle/MiniSkipList.java#L161)）：
  * ZSet 元素多了以后的编码是 **skiplist**：实际是**跳表 + 字典**。字典让 `ZSCORE` 是 O(1)；跳表按 `(score, member)` 排序，支持范围查询和排名。
  * 跳表每一层有 `P=0.25` 的概率继续向上，平均每个节点约 **1.33 个指针**，比红黑树（固定 2 个）还省（[实验 3](code/src/main/java/com/example/redis/principle/MiniSkipList.java#L178)）。
  * 查找、插入、`ZRANK`（沿途累加 `span`）都是 **O(logN)**（[rank](code/src/main/java/com/example/redis/principle/MiniSkipList.java#L106)、[实验 4](code/src/main/java/com/example/redis/principle/MiniSkipList.java#L194)）。
  * **比红黑树更合适的原因**：① 实现简单；② 范围查询顺着第 0 层链表扫就行；③ 插入不需要旋转，局部性更好。Redis 作者自己说过选跳表就是因为简单且对范围操作友好。

### Q4：Redis 的过期策略和内存淘汰策略？

* **满分话术**：
  * **过期删除**：惰性删除（访问时检查）+ 定期删除（每次抽一批带 TTL 的 key）。所以过期了不一定立刻释放内存。
  * **内存淘汰**（`maxmemory-policy`）：常见 `allkeys-lru` / `volatile-lru` / `allkeys-lfu` / `volatile-ttl` / `noeviction`。
  * Redis 的 LRU 是**近似 LRU**：每个对象头 24 位记录访问时间，淘汰时随机抽 `maxmemory-samples`（默认 5）个，删最久没访问的（[`ApproxLruDemo`](code/src/main/java/com/example/redis/principle/ApproxLruDemo.java#L20)）。抽样 5 个已经和标准 LRU 命中率接近，又省掉了双向链表的指针开销。

### Q5：全局唯一 ID 怎么用 Redis 做？

* **满分话术**（[`RedisIdWorker`](code/src/main/java/com/example/redis/common/RedisIdWorker.java#L19)、[请求 1.7](code/requests.http)）：`时间戳（相对 2022-01-01 的秒）左移 32 位 | 当天 INCR 序列号`。按天拆 key，一是 32 位序列号够用，二是方便统计日订单量。和雪花算法比：不依赖机器号，也不怕时钟回拨造成同一毫秒内重复（序列号仍然递增）。

## 2. ZSet 三个经典场景

> 代码：[`SlidingWindowRateLimiter`](code/src/main/java/com/example/redis/zset/SlidingWindowRateLimiter.java#L17)、[`FieldExpireHash`](code/src/main/java/com/example/redis/zset/FieldExpireHash.java#L25)、[`RedisDelayQueue`](code/src/main/java/com/example/redis/zset/RedisDelayQueue.java#L18)；Lua：[`sliding_window.lua`](code/src/main/resources/lua/sliding_window.lua)、[`hash_field_expire.lua`](code/src/main/resources/lua/hash_field_expire.lua)

> 对应 `java.md`：**如何用 ZSet 模拟 Hash Field 过期？如何用 ZSet 实现滑动窗口限流？（小红书一二面连环考）**

### Q1：怎么用 ZSet 做滑动窗口限流？为什么必须用 Lua？

* **满分话术**（[请求 2.1 / 2.2](code/requests.http)、脚本 [第 12~22 行](code/src/main/resources/lua/sliding_window.lua#L12)）：
  1. Key = `limit:user:{uid}:{api}`，member = 请求唯一 ID，score = 当前毫秒时间戳。
  2. 每次请求原子做三步：① `ZREMRANGEBYSCORE` 删窗口外旧记录；② `ZCARD` 计数；③ 未超限则 `ZADD` + `PEXPIRE`。
  3. **必须 Lua**：否则两个请求同时 `ZCARD` 都看到 `limit-1`，会一起放行。
  4. 时间用 `TIME` 取 Redis 服务器时间，避免多机时钟不一致。
  5. **对比固定窗口**：固定窗口用 `INCR` 按秒计数，实现简单，但有**临界突刺**——窗口交界处 0.2 秒内可能放过 2 倍请求（[burst 模式](code/src/main/java/com/example/redis/zset/ZsetDemoController.java#L50)）。滑动窗口更平滑，代价是每个请求一个 ZSet member、内存更大。
  6. 生产上常做**两级限流**：网关本地限流挡恶意流量，Redis 做集中式精确限流（`java.md` 第 149 行）。

### Q2：怎么用 ZSet 模拟 Hash 某个 Field 的过期？

* **满分话术**（[请求 2.3](code/requests.http)、[`FieldExpireHash`](code/src/main/java/com/example/redis/zset/FieldExpireHash.java#L25)）：
  * 场景：用户优惠券包是一个 Hash，每张券有效期不同；Hash 的 `EXPIRE` 只能作用整个 key。
  * 做法：数据放 Hash；另建 ZSet，member = 字段名，score = 过期时刻。
  * **惰性删除**：`get` 时发现 `score <= now`，顺手 `HDEL` + `ZREM`（[脚本 get 分支](code/src/main/resources/lua/hash_field_expire.lua#L16)）。
  * **定期删除**：定时任务 `ZRANGEBYSCORE -inf now` 一次找出所有过期字段批量删（[clean 分支](code/src/main/resources/lua/hash_field_expire.lua#L27)）——和 Redis 自己删过期 key 的策略一模一样。
  * 两个 key 要用同一个 **hash tag** `{name}`，集群下 Lua 才能操作（否则 `CROSSSLOT`）。
  * Redis 7.4 起原生支持 `HEXPIRE`，面试仍要会手写这套。

### Q3：ZSet 延迟队列怎么做？有什么局限？

* **满分话术**（[请求 2.4](code/requests.http)、[`delay_queue_poll.lua`](code/src/main/resources/lua/delay_queue_poll.lua)）：`ZADD` 时 score = 执行时刻；消费者轮询 `ZRANGEBYSCORE -inf now LIMIT 0 1` + `ZREM`，两步必须 Lua 原子，否则会重复消费。局限：① 要轮询，无到期通知；② 取出后消费者挂了任务就丢（无 ACK）。可靠性要求高时用 RabbitMQ 死信 / 延迟插件，或 Redisson `RDelayedQueue`。

## 3. 缓存穿透 / 击穿 / 雪崩

> 代码：[`CacheClient`](code/src/main/java/com/example/redis/cache/CacheClient.java#L27)、[`CacheDemoController`](code/src/main/java/com/example/redis/cache/CacheDemoController.java#L27)、[`MiniBloomFilter`](code/src/main/java/com/example/redis/principle/MiniBloomFilter.java#L16)

### Q1：什么是缓存穿透？怎么解决？

* **满分话术**（[请求 3.1~3.4](code/requests.http)）：
  * **穿透**：查询一个**数据库一定不存在**的数据，缓存没有、数据库也没有，请求每次都打到 DB。攻击者换 id 扫库时特别危险。
  * **方案一：缓存空值**（[`queryWithPassThrough`](code/src/main/java/com/example/redis/cache/CacheClient.java#L82)）：DB 查不到就往 Redis 写 `""`，TTL 短一点（本项目 2 分钟）。同一 id 只会打一次库（请求 3.2）；但攻击者每次换 id，空值缓存失效，还会在 Redis 堆垃圾 key（请求 3.3）。
  * **方案二：布隆过滤器**（请求 3.4、[`MiniBloomFilter`](code/src/main/java/com/example/redis/principle/MiniBloomFilter.java#L16)）：在最前面用位图判断“一定不存在”，不存在的直接返回。有误判（可能把不存在的判成存在，再查一次库），**没有漏判**。占内存极小（100 万元素约 1MB）。局限：不能删除；数据量涨了要重建；新增数据要同步 `add`。
  * 实践中常**两者结合**：布隆过滤器挡扫库，空值缓存挡误判漏到 DB 的个别请求。

### Q2：什么是缓存击穿？互斥锁和逻辑过期怎么选？

* **满分话术**（[请求 3.5~3.8](code/requests.http)）：
  * **击穿**：**热点 key** 过期瞬间，大量请求同时打到 DB。
  * **互斥锁**（[`queryWithMutex`](code/src/main/java/com/example/redis/cache/CacheClient.java#L102)）：只有一个线程查库重建，其他线程 sleep 重试。`dbQueries=1`，但 `costMs` 变长。适合**不能接受脏数据**的场景。
  * **逻辑过期**（[`queryWithLogicalExpire`](code/src/main/java/com/example/redis/cache/CacheClient.java#L143)）：key 永不过期，过期时间写在 value 里；发现过期后异步重建，所有线程先返回旧值。`dbQueries=1`、`costMs` 短，但短时间读到旧数据。适合**热点、能接受短暂不一致**的场景（商铺详情等）。前提是热点 key 要**预热**。
  * **黑马点评的坑**：`CacheClient` 提交异步任务后，外层 `finally` 立刻释放锁（[对照复现](code/src/main/java/com/example/redis/cache/CacheClient.java#L183)），重建期间其他线程又能拿到锁 → `dbQueries>1`（请求 3.8）。正确做法是锁只在异步任务的 `finally` 里释放。

### Q3：什么是缓存雪崩？怎么解决？

* **满分话术**（[请求 3.9 / 3.10](code/requests.http)）：
  * **雪崩**：大量 key **同时过期**，或 Redis 宕机，请求全部打到 DB。
  * 解决：① TTL 加随机值（[`setWithRandomTtl`](code/src/main/java/com/example/redis/cache/CacheClient.java#L51)），把过期时间打散；② Redis 集群 / 哨兵高可用；③ 多级缓存；④ 限流降级；⑤ 永不过期 + 逻辑过期（热点）。

### Q4：穿透、击穿、雪崩怎么区分？

* **满分话术**：穿透 = **没有的数据**（恶意或不存在的 id）；击穿 = **一个热点**刚好过期；雪崩 = **一片 key** 同时过期或缓存整体挂了。

## 4. 双写一致性

> 代码：[`ConsistencyDemoController`](code/src/main/java/com/example/redis/consistency/ConsistencyDemoController.java#L26)、[`TxShopWriter`](code/src/main/java/com/example/redis/consistency/TxShopWriter.java#L15)；对照黑马点评 `ShopServiceImpl#update`

### Q1：旁路缓存（Cache Aside）为什么推荐“先更新数据库，再删除缓存”？

* **满分话术**（[请求 4.1~4.4](code/requests.http)）：
  * **读**：查缓存 → 未命中查库 → 写回缓存。
  * **写**：更新 DB → 删除缓存（不是更新缓存）。删了让下次读回源，避免“更新缓存”时和并发读写出脏数据，也避免根本没人读的数据被白白写入。
  * **为什么不先删缓存再更新库**（请求 4.1）：删完、库还没更新时，并发读会把**旧值**写回缓存，之后一直脏到 TTL。
  * **先更新库再删缓存**在正常时序下是对的（请求 4.2）。极端时序仍可能脏（请求 4.3）：读线程查到旧值后卡住，写线程更新并删完缓存，读线程才把旧值写回。概率低，但存在。
  * **加强**：① **延迟双删**——更新后再删一次，延迟大于一次读的耗时（请求 4.4）；② 删缓存失败时发 MQ 重试；③ 强一致场景用分布式锁把读写串起来，或上 Canal 订阅 binlog 删缓存。

### Q2：在事务里删缓存有什么问题？

* **满分话术**（[请求 4.5 / 4.6](code/requests.http)、[`TxShopWriter`](code/src/main/java/com/example/redis/consistency/TxShopWriter.java#L27)）：
  * 黑马点评 `ShopServiceImpl#update` 在 `@Transactional` 方法里先 `updateById` 再 `delete` 缓存——**此时事务还没提交**。并发读可能读到旧值写回缓存，事务随后才提交 → 不一致（请求 4.5）。
  * 正确：用 `TransactionSynchronization#afterCommit`，**提交成功后再删**；事务回滚则不删（请求 4.6、[afterCommit](code/src/main/java/com/example/redis/consistency/TxShopWriter.java#L39)）。

### Q3：为什么是“删缓存”而不是“更新缓存”？

* **满分话术**：① 写多读少时，很多更新后的数据根本没人读，更新缓存浪费；② 两个写线程更新缓存的顺序可能和更新 DB 的顺序不一致，造成缓存和 DB 最终也不一致；③ 删除是幂等的，下次读自然回源。

## 5. 分布式锁与 Lua

> 代码：[`SimpleRedisLock`](code/src/main/java/com/example/redis/lock/SimpleRedisLock.java#L22)、[`LockDemoController`](code/src/main/java/com/example/redis/lock/LockDemoController.java#L23)、[`unlock.lua`](code/src/main/resources/lua/unlock.lua)；对照黑马点评 `SimpleRedisLock`

### Q1：手写分布式锁的正确姿势？

* **满分话术**：
  1. **加锁**：`SET key token NX EX ttl` 一条命令（[`tryLock`](code/src/main/java/com/example/redis/lock/SimpleRedisLock.java#L44)）。拆成 `SETNX` + `EXPIRE`，中间进程挂了锁永不过期。
  2. **token**：UUID（或 UUID+线程 id），标识“谁持有锁”。
  3. **解锁**：Lua 里 `GET` 比较 token 再 `DEL`（[`unlock.lua`](code/src/main/resources/lua/unlock.lua)）。只 `DEL` 会误删别人的锁（请求 5.1）；先 `GET` 再 `DEL` 两步非原子，GC 停顿时照样误删（请求 5.2）；Lua 才安全（请求 5.3）。
  4. **Lua 仍解决不了的问题**：业务执行时间超过 ttl，锁提前过期，A 和 B 的业务仍会重叠——这就是 Redisson **看门狗**要解决的。

### Q2：为什么要用 Lua？Lua 的限制？

* **满分话术**：Redis 执行 Lua 期间不会插入别的命令，所以多条命令变成原子操作。脚本里尽量短小；避免脚本里做大量运算或随机阻塞；集群模式下脚本操作的 key 必须在同一槽（用 hash tag `{...}`）。

### Q3：Redisson 分布式锁比自研锁强在哪？

* **满分话术**（请求 5.6~5.9）：
  1. **可重入**：用 Hash 存 `线程标识 → 重入次数`（请求 5.7，`redissonHoldCount`）。
  2. **看门狗**：`lock()` 不指定过期时间时，默认 30s，每 10s（30/3）续期；业务多久都行（请求 5.8）。`lock(10, SECONDS)` 指定了过期则不续期（请求 5.9）。
  3. **等待可中断 / 超时**：`tryLock(waitTime, leaseTime, unit)`；拿不到锁时通过 Pub/Sub 订阅释放通知，被唤醒再抢，不用空自旋。
  4. **红锁 RedLock**（多节点）：争议较大，生产更常见的是 Redisson + Redis 哨兵 / 集群，接受锁的“足够安全”而不是绝对安全。

### Q4：分布式锁的 ttl 怎么定？

* **满分话术**：自研锁只能拍一个“业务最坏耗时 + 余量”，拍短了会重叠、拍长了死锁恢复慢。Redisson 看门狗让你不用猜。锁的粒度尽量细（按用户 id、按订单 id），不要锁全局。

## 6. 秒杀与 Redis Stream

> 代码：[`SeckillService`](code/src/main/java/com/example/redis/seckill/SeckillService.java#L36)、[`seckill.lua`](code/src/main/resources/lua/seckill.lua)、[`seckill_old.lua`](code/src/main/resources/lua/seckill_old.lua)；对照黑马点评 `VoucherOrderServiceImpl`

### Q1：秒杀怎么防超卖？一人一单怎么做？

* **满分话术**（[请求 6.1 / 6.3](code/requests.http)）：
  1. **库存预热**到 Redis。
  2. **Lua 原子**（[`seckill.lua`](code/src/main/resources/lua/seckill.lua)）：判断库存 → 判断 Set 里是否已下单 → `INCRBY -1` → `SADD` 用户 → `XADD` 发消息。任一失败直接返回，不会出现“库存扣了但判定重复”的中间态。
  3. **异步落库**：消费者扣 DB 库存时用 `WHERE stock > 0` 乐观锁，表上有 `UNIQUE(user_id, voucher_id)` 兜底。
  4. 演进路线（黑马点评注释里能看到）：悲观锁 → 乐观锁 →  synchronized 一人一单 → Redisson 锁 → Lua + 阻塞队列 → Lua + Stream。

### Q2：为什么要用 Redis Stream 而不是 JVM 阻塞队列？

* **满分话术**：`ArrayBlockingQueue` 在内存里，服务重启消息就没了，也无法多实例共享。Redis Stream 是持久化的消息队列，支持**消费组**、ACK、pending-list，多个服务实例可以竞争消费。

### Q3：消费组、ACK、pending-list 是什么？

* **满分话术**（[`consumeLoop`](code/src/main/java/com/example/redis/seckill/SeckillService.java#L119)、[请求 6.4](code/requests.http)）：
  * **消费组** `XGROUP CREATE stream.orders g1 0 MKSTREAM`：组内每个消息只被一个消费者处理。启动时要先建组，否则 `XREADGROUP` 一直报错（黑马点评 README 也写了这点）。
  * **ACK** `XACK`：业务处理成功后再确认。没 ACK 的消息留在 **pending-list**。
  * **pending-list 重试**：异常时用 `XREADGROUP ... 0`（不是 `>`）把未 ACK 的捞出来重试（[`handlePendingList`](code/src/main/java/com/example/redis/seckill/SeckillService.java#L145)）。`>` 表示只读从未投递过的新消息。

### Q4：黑马点评秒杀链路为什么是断的？这对面试有什么用？

* **满分话术**（[请求 6.2](code/requests.http)）：仓库里 `VoucherOrderServiceImpl` 第 62 行加载的是 **`seckill_old.lua`**，这个脚本不 `XADD`，所以 Redis 库存扣了、用户进了下单 Set，但 Stream 没消息，**数据库不会有订单**。改成 `seckill.lua` 即可。面试可讲：① Lua 和消费者如何对齐；② 消费组没初始化会怎样；③ pending-list 如何保证不丢；④ 怎么用实验证明链路通了（`luaOk == dbOrders == stock`）。

### Q5：Redis 主从 / 哨兵 / 集群了解吗？

* **满分话术**（本模块不部署，只背结论）：
  * **主从**：读写分离、副本备份；默认异步复制，主宕机可能丢一小段数据。
  * **哨兵**：监控主从，主挂了自动选新主，客户端经哨兵发现新地址。
  * **集群**：数据按槽（16384）分片，水平扩容；Lua 的 key 必须同槽。
  * 分布式锁在主从切换时可能丢（主还没同步锁 key 就挂了）——这是 RedLock 想解决的问题；多数团队接受这个风险，或用 etcd / ZooKeeper。

## 速查表

| 场景 | 方案 | 关键点 |
|---|---|---|
| 缓存对象 | String / Hash | 旁路缓存；TTL + 随机 |

| 排行榜 | ZSet | 跳表 + 字典；`ZREVRANGE` |

| Hash 字段过期 | Hash + ZSet | 惰性 + 定期；hash tag |
| 延迟任务 | ZSet | 轮询；无 ACK 就上 MQ |
| 防穿透 | 空值 / 布隆过滤器 | 两者常结合 |
| 防击穿 | 互斥锁 / 逻辑过期 | 锁不要提前释放 |
