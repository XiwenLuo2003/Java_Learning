## 1. IoC 与依赖注入

> 代码：[AnnotationDemo](code/src/main/java/com/example/demo/principle/annotation/AnnotationDemo.java)、[MiniIocDemo](code/src/main/java/com/example/demo/principle/ioc/MiniIocDemo.java)、[UserService](code/src/main/java/com/example/demo/user/UserService.java)

### Q1：什么是 IoC 和 DI？有什么好处？

* **满分话术**：
  1. **IoC（控制反转）**是一种设计思想：对象的创建和依赖关系的组装，从业务代码里“反转”给容器负责。以前是 `OrderService` 自己 `new UserDao()`，现在它只声明“我需要一个 UserDao”，由 Spring 容器创建好再给它。
  2. **DI（依赖注入）**是 IoC 的具体实现方式：容器通过构造器、setter 或字段反射，把依赖“注入”到对象里。
  3. **好处**：一是**解耦**，`OrderService` 只依赖接口，换实现不用改代码；二是**统一管理生命周期**，默认单例，避免重复创建；三是**方便扩展**，容器在创建对象的过程中可以“加料”，比如生成 AOP 代理，事务、日志都是这么加进去的；四是**方便测试**，可以注入 Mock 对象。
  4. **本质**：我自己写过一个迷你 IoC 容器（[MiniContainer](code/src/main/java/com/example/demo/principle/ioc/MiniIocDemo.java#L59)），核心就三步：扫描带 `@Component` 的类 → 反射调用构造器实例化 → 找到 `@Autowired` 字段，递归 `getBean` 后反射赋值（[createBean](code/src/main/java/com/example/demo/principle/ioc/MiniIocDemo.java#L91)）。Spring 在这个基础上加了 BeanDefinition、作用域、生命周期回调、BeanPostProcessor 扩展点等。

### Q2：注解本身是怎么“生效”的？

* **满分话术**：注解本身只是元数据，**不会执行任何逻辑**。它要生效必须满足两点：一是 `@Retention(RUNTIME)`，运行时还保留在 class 里，反射才能读到（[AnnotationDemo 的 @RateLimit](code/src/main/java/com/example/demo/principle/annotation/AnnotationDemo.java#L28)）；二是有一个“注解处理器”去读它（[AnnotationDemo#main](code/src/main/java/com/example/demo/principle/annotation/AnnotationDemo.java#L49)）。比如 `@Component` 是 Spring 启动时由 `ClassPathBeanDefinitionScanner` 扫描读取的，`@Autowired` 是 `AutowiredAnnotationBeanPostProcessor` 处理的，`@Transactional` 是事务的 AOP 切面读取的。所以注解“失效”的问题，本质都是“没有人去读它”或“读它的那段逻辑没被触发”。

### Q3：依赖注入有哪几种方式？为什么推荐构造器注入？`@Autowired` 和 `@Resource` 的区别？

* **满分话术**：
  1. 三种方式：**构造器注入**、**setter 注入**、**字段注入**（`@Autowired` 写在字段上）。
  2. **推荐构造器注入**（Spring 官方推荐，项目里的 [UserService 构造器](code/src/main/java/com/example/demo/user/UserService.java#L31) 就是这么写的）：
     * 依赖可以声明为 `final`，对象一创建就是完整的，不会出现依赖为 null 的半成品；
     * 依赖一目了然，构造器参数太多说明这个类职责过重，该拆了；
     * 不依赖反射，单元测试可以直接 `new UserService(mockMapper, mockJwt)`；
     * 循环依赖会在启动时直接暴露出来，而不是被三级缓存“悄悄”解决掉。
  3. **`@Autowired` vs `@Resource`**：
     * `@Autowired` 是 Spring 的注解，**先按类型（byType）**找，找到多个再按名字匹配，可以配合 `@Qualifier` 指定名字；
     * `@Resource` 是 JSR-250 规范（`jakarta.annotation`）的注解，**先按名字（byName）**找，找不到再按类型。

### Q4：Spring Bean 的作用域有哪些？单例 Bean 是线程安全的吗？

* **满分话术**：
  1. 作用域：`singleton`（默认，容器里只有一个）、`prototype`（每次 getBean 都新建）、Web 环境下还有 `request`、`session`、`application`。
  2. **单例 Bean 不保证线程安全**，Spring 没有做任何同步处理。是否安全取决于它有没有**可变的成员变量**：像 `UserService` 这种只持有 Mapper 等无状态依赖的 Bean，所有数据都在方法局部变量里（线程栈私有），是安全的；如果在单例里定义了 `private int count` 之类的状态并修改它，就会有并发问题。
  3. 解决办法：尽量设计成无状态；必须有状态时用 `ThreadLocal`（项目里的 [UserContext](code/src/main/java/com/example/demo/web/UserContext.java#L14)）、改为 `prototype`，或者用 `AtomicInteger`、加锁。

### Q5：`BeanFactory` 和 `ApplicationContext` 的区别？

* **满分话术**：`BeanFactory` 是最底层的容器接口，只提供 getBean 等基础能力，默认懒加载。`ApplicationContext` 继承了它，额外提供国际化、事件发布、资源加载、环境配置等企业级功能，并且**启动时就创建好所有非懒加载的单例**，能尽早暴露配置错误。实际开发用的都是 `ApplicationContext`。

## 2. AOP 原理（动态代理）

> 代码：[JdkProxyDemo](code/src/main/java/com/example/demo/principle/aop/JdkProxyDemo.java)、[CglibProxyDemo](code/src/main/java/com/example/demo/principle/aop/CglibProxyDemo.java)、[LogExecution](code/src/main/java/com/example/demo/aop/LogExecution.java)、[LogAspect](code/src/main/java/com/example/demo/aop/LogAspect.java)，观察接口 [http://localhost:8080/demo/beans](http://localhost:8080/demo/beans)（代码：[ShowcaseController#beans](code/src/main/java/com/example/demo/showcase/ShowcaseController.java#L54)）

### Q1：什么是 AOP？几个核心概念是什么？

* **满分话术**：AOP（面向切面编程）是把日志、事务、权限、监控这类**横切多个业务的通用逻辑**抽出来，在不修改业务代码的前提下“织入”到目标方法前后。核心概念：
  * **切面（Aspect）**：通用逻辑的模块化封装，比如 [LogAspect](code/src/main/java/com/example/demo/aop/LogAspect.java#L30)；
  * **切点（Pointcut）**：在哪些方法上增强，比如 `@annotation(logExecution)` 匹配所有贴了 [@LogExecution](code/src/main/java/com/example/demo/aop/LogExecution.java#L16) 的方法；
  * **通知（Advice）**：增强什么、什么时机，分 `@Before`、`@After`、`@AfterReturning`、`@AfterThrowing`、`@Around`（项目里用的是 [@Around](code/src/main/java/com/example/demo/aop/LogAspect.java#L35)）；
  * **连接点（JoinPoint）**：程序执行中可以被增强的点，Spring AOP 里就是方法调用；
  * **织入（Weaving）**：把切面应用到目标对象、生成代理的过程，Spring 是在运行时织入。

### Q2：Spring AOP 的底层原理是什么？JDK 动态代理和 CGLIB 有什么区别？

* **满分话术**：
  1. Spring AOP 基于**动态代理**。容器里放的不是原对象，而是代理对象，调用方法时先进代理，代理执行增强逻辑后再转调原对象（手写版见 [JdkProxyDemo 的 TimingHandler](code/src/main/java/com/example/demo/principle/aop/JdkProxyDemo.java#L58)）。
  2. **代理在什么时候生成**：在 Bean 生命周期的**初始化之后**，由 `AnnotationAwareAspectJAutoProxyCreator`（一个 BeanPostProcessor）的 `postProcessAfterInitialization` 检查这个 Bean 是否有方法匹配某个切点，匹配就生成代理替换掉原对象（对应 [LifecycleBeanPostProcessor 第 8 步](code/src/main/java/com/example/demo/lifecycle/LifecycleBeanPostProcessor.java#L32)）。
  3. **两种代理方式**：

     | | JDK 动态代理 | CGLIB |
     |---|---|---|
     | 原理 | 运行时生成实现了**同一接口**的代理类 | 运行时生成目标类的**子类**，重写方法 |
     | 要求 | 目标类必须实现接口 | 类和方法不能是 final |
     | 代理对象能否强转成实现类 | 不能 | 能 |
     | 典型例子 | MyBatis 的 Mapper 接口代理（[UserMapper](code/src/main/java/com/example/demo/user/UserMapper.java#L12)） | Spring 的 `UserService$$SpringCGLIB$$0` |
     | 演示代码 | [JdkProxyDemo#main](code/src/main/java/com/example/demo/principle/aop/JdkProxyDemo.java#L80) | [CglibProxyDemo#main](code/src/main/java/com/example/demo/principle/aop/CglibProxyDemo.java#L55) |

  4. **Spring Boot 2.x 起默认用 CGLIB**（`spring.aop.proxy-target-class=true`），原因是用 JDK 代理时，如果有人按实现类类型注入就会报错，CGLIB 没有这个问题。

### Q3：通知的执行顺序是怎样的？

* **满分话术**：Spring 5.2.7 之后，同一个切面内的顺序是：`@Around` 前半段 → `@Before` → **目标方法** → `@AfterReturning`（正常返回）或 `@AfterThrowing`（抛异常）→ `@After`（类似 finally，一定执行）→ `@Around` 后半段。多个切面之间用 `@Order` 控制，数字越小越先进入、越后退出，像洋葱一样一层套一层。

### Q4：为什么同一个类里方法自调用，AOP（包括 `@Transactional`）会失效？怎么解决？

* **满分话术**：
  1. **原因**：Spring AOP 的代理对象内部持有一个独立的原对象（target），增强完之后调用的是 `target.method()`。目标方法内部再用 `this.otherMethod()` 调用时，`this` 指向的是原对象而不是代理，所以这次调用**根本没经过代理**，增强逻辑也就不会执行。
  2. **我写过的验证**：[CglibProxyDemo](code/src/main/java/com/example/demo/principle/aop/CglibProxyDemo.java#L56) 里对比了两种写法。用 `invokeSuper` 时代理对象本身就是业务对象，内部调用也能被拦截；而 [Spring AOP 风格的“代理 + 独立 target”](code/src/main/java/com/example/demo/principle/aop/CglibProxyDemo.java#L65)，内部调用就拦截不到。项目里的 [TxDemoService#selfInvocation](code/src/main/java/com/example/demo/tx/TxDemoService.java#L49) 也复现了事务因此失效（演示：[/demo/tx/self-invocation](http://localhost:8080/demo/tx/self-invocation)）。
  3. **解决办法**：
     * 把方法拆到另一个 Bean 里，跨 Bean 调用（最推荐，职责也更清晰）；
     * 注入自己的代理：[`@Autowired @Lazy private TxDemoService self;`](code/src/main/java/com/example/demo/tx/TxDemoService.java#L31)，然后 [`self.method()`](code/src/main/java/com/example/demo/tx/TxDemoService.java#L54)；
     * `AopContext.currentProxy()` 获取当前代理，需要开启 `@EnableAspectJAutoProxy(exposeProxy = true)`。

### Q5：Spring AOP 和 AspectJ 有什么区别？

* **满分话术**：Spring AOP 是**运行时**基于动态代理织入，只能增强 Spring Bean 的方法调用，简单够用；AspectJ 是**编译期或类加载期**直接修改字节码织入，能增强字段访问、构造器、静态方法、私有方法，也没有自调用问题，但需要专门的编译器或 Agent。Spring 只是借用了 AspectJ 的注解语法（`@Aspect`、`@Around`、切点表达式），底层还是自己的代理。

## 3. Bean 生命周期与循环依赖

> 代码：[LifecycleBean](code/src/main/java/com/example/demo/lifecycle/LifecycleBean.java)、[LifecycleBeanPostProcessor](code/src/main/java/com/example/demo/lifecycle/LifecycleBeanPostProcessor.java)、[CircularA](code/src/main/java/com/example/demo/lifecycle/CircularA.java)、[CircularB](code/src/main/java/com/example/demo/lifecycle/CircularB.java)、[StartupRunner](code/src/main/java/com/example/demo/lifecycle/StartupRunner.java#L23)、[MiniIocDemo](code/src/main/java/com/example/demo/principle/ioc/MiniIocDemo.java)

### Q1：讲一下 Spring Bean 的生命周期？

* **满分话术**：可以概括为“**实例化 → 属性填充 → 初始化 → 使用 → 销毁**”五个阶段，其中初始化最细（项目里的 [LifecycleBean](code/src/main/java/com/example/demo/lifecycle/LifecycleBean.java#L34) 会按顺序打印每一步）：
  1. **实例化**（`createBeanInstance`）：通过反射调用构造器创建对象，此时属性都是空的。
  2. **属性填充**（`populateBean`）：注入 `@Autowired`、`@Value` 依赖（[第 2 步](code/src/main/java/com/example/demo/lifecycle/LifecycleBean.java#L43)）。
  3. **初始化**（`initializeBean`）：
     * 回调各种 **Aware 接口**：`BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware`，让 Bean 拿到容器信息；
     * **BeanPostProcessor 前置处理**（[postProcessBeforeInitialization](code/src/main/java/com/example/demo/lifecycle/LifecycleBeanPostProcessor.java#L24)），`@PostConstruct` 就是在这一步被 `CommonAnnotationBeanPostProcessor` 调用的（[第 6 步](code/src/main/java/com/example/demo/lifecycle/LifecycleBean.java#L58)）；
     * `InitializingBean#afterPropertiesSet`；
     * 自定义的 `init-method`（`@Bean(initMethod = ...)`）；
     * **BeanPostProcessor 后置处理**（[postProcessAfterInitialization](code/src/main/java/com/example/demo/lifecycle/LifecycleBeanPostProcessor.java#L32)），**AOP 代理就在这里生成**。
  4. **使用**：Bean 放入单例池（一级缓存），供业务使用。
  5. **销毁**：容器关闭时依次执行 `@PreDestroy`（[第 9 步](code/src/main/java/com/example/demo/lifecycle/LifecycleBean.java#L68)）→ `DisposableBean#destroy` → 自定义 `destroy-method`。

  **记忆技巧**：BeanPostProcessor 是 Spring 最重要的扩展点，`@Autowired`、`@PostConstruct`、AOP 背后都是它，它像“夹子”一样夹住了初始化方法。

### Q2：Spring 是怎么解决循环依赖的？三级缓存分别存什么？

* **满分话术**：
  1. **场景**：A 依赖 B，B 又依赖 A（[CircularA](code/src/main/java/com/example/demo/lifecycle/CircularA.java#L20) ⇄ [CircularB](code/src/main/java/com/example/demo/lifecycle/CircularB.java)）。创建 A 时要注入 B，创建 B 时又要注入 A，如果不处理就会无限递归。
  2. **核心思路**：**提前暴露半成品**。A 实例化完成后（还没注入属性），就先把它的引用放进缓存；B 注入 A 时直接从缓存拿到这个半成品，B 完成创建后再回来完成 A。因为是同一个对象引用，A 后续被填充完整，B 拿到的那个 A 也就是完整的了（手写版：[MiniIocDemo 的两级缓存](code/src/main/java/com/example/demo/principle/ioc/MiniIocDemo.java#L61)）。
  3. **三级缓存**（都在 `DefaultSingletonBeanRegistry` 里）：
     * **一级 `singletonObjects`**：完整的成品 Bean；
     * **二级 `earlySingletonObjects`**：提前暴露的早期引用（可能已经是代理对象）；
     * **三级 `singletonFactories`**：一个 `ObjectFactory` 工厂（lambda：`() -> getEarlyBeanReference(beanName, mbd, bean)`），调用它时如果这个 Bean 需要 AOP，就**提前生成代理**并返回。
  4. **流程**：创建 A → 实例化后把 A 的工厂放进三级缓存 → 注入 B → 创建 B → B 注入 A 时依次查一、二、三级缓存，在三级缓存找到工厂，调用工厂得到 A 的早期引用（需要代理就是代理），放进二级缓存并删除三级 → B 完成，放进一级 → A 注入 B 完成 → A 初始化完成，放进一级。

### Q3：为什么要三级缓存？二级不够吗？

* **满分话术**：如果没有 AOP，二级就够了（我手写的 [MiniIocDemo](code/src/main/java/com/example/demo/principle/ioc/MiniIocDemo.java#L61) 就只用了两级）。问题出在**代理**：B 拿到的 A 必须是最终放进容器的那个对象，如果 A 需要被代理，B 拿到的就应该是代理而不是原对象。
  * 只用二级的话，就只能在**每个 Bean 实例化后立刻生成代理**放进去，但这违背了 Spring 的设计：正常情况下代理是在**初始化的最后一步**（BeanPostProcessor 后置处理）才生成的。
  * 三级缓存存的是一个**工厂**，只有**真的发生循环依赖、有人来要早期引用时**，才调用它提前生成代理；没有循环依赖的 Bean 照常在初始化最后才生成代理。也就是说，三级缓存是为了**延迟代理的创建**，同时保证循环依赖中拿到的引用和最终容器里的是同一个对象。

### Q4：哪些循环依赖解决不了？

* **满分话术**：
  1. **构造器注入的循环依赖**：A 的构造器需要 B，B 的构造器需要 A，A 连实例都创建不出来，就没有半成品可以暴露，启动直接报 `BeanCurrentlyInCreationException`（可以把 [CircularA](code/src/main/java/com/example/demo/lifecycle/CircularA.java) / [CircularB](code/src/main/java/com/example/demo/lifecycle/CircularB.java) 改成构造器注入试试）。可以用 `@Lazy` 注入一个延迟代理来绕开。
  2. **prototype 作用域的循环依赖**：原型 Bean 不进缓存，每次都新建，无法提前暴露。
  3. 另外，**Spring Boot 2.6 起默认禁止循环依赖**（`spring.main.allow-circular-references=false`，项目里为了演示在 [application.yml](code/src/main/resources/application.yml#L21) 打开了），出现了就启动失败。官方的态度是：循环依赖本身就是设计问题，应该通过拆分职责、抽取第三个类来消除，而不是依赖三级缓存兜底。

## 4. 自动配置原理

> 代码：[DemoApplication](code/src/main/java/com/example/demo/DemoApplication.java#L15)、[GreetingAutoConfiguration](code/src/main/java/com/example/starter/GreetingAutoConfiguration.java)、[GreetingProperties](code/src/main/java/com/example/starter/GreetingProperties.java)、[GreetingService](code/src/main/java/com/example/starter/GreetingService.java)、[AutoConfiguration.imports](code/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports)，观察接口 [http://localhost:8080/demo/greeting](http://localhost:8080/demo/greeting)（代码：[ShowcaseController#greeting](code/src/main/java/com/example/demo/showcase/ShowcaseController.java#L65)）

### Q1：讲一下 Spring Boot 自动配置的原理？（高频）

* **满分话术**：
  1. **入口**：[`@SpringBootApplication`](code/src/main/java/com/example/demo/DemoApplication.java#L15) 是三个注解的组合：`@SpringBootConfiguration`（本质是 `@Configuration`）、`@ComponentScan`（扫描启动类所在包及子包）、`@EnableAutoConfiguration`（自动配置的开关）。
  2. **加载候选配置类**：`@EnableAutoConfiguration` 通过 `@Import(AutoConfigurationImportSelector.class)` 导入了一个选择器。它会读取 classpath 下**所有 jar 包**里的 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 文件（Spring Boot 2.7 之前是 `META-INF/spring.factories` 里 `EnableAutoConfiguration` 这个 key），拿到一百多个自动配置类的全类名。
  3. **去重和排除**：去掉重复的，再去掉 `@SpringBootApplication(exclude = ...)` 或 `spring.autoconfigure.exclude` 里排除的。
  4. **按条件过滤**：每个自动配置类上都有条件注解，只有条件都满足才生效。比如 `DataSourceAutoConfiguration` 要求 classpath 里有 `DataSource` 类（`@ConditionalOnClass`），所以引入了 jdbc 依赖、配好 url，就自动创建出 `HikariDataSource`。
  5. **注册 Bean**：生效的配置类里的 `@Bean` 方法被注册进容器。这些 `@Bean` 通常带 `@ConditionalOnMissingBean`，意思是“用户自己没定义我才创建”，所以**用户的配置可以覆盖默认配置**，这就是“约定优于配置”。
  6. **一个细节**：`AutoConfigurationImportSelector` 实现的是 `DeferredImportSelector`，会**延迟到用户自己的配置类全部解析完之后**才处理，这样 `@ConditionalOnMissingBean` 才能准确判断用户有没有定义这个 Bean。
* **项目里的验证**：我写了一个 [GreetingAutoConfiguration](code/src/main/java/com/example/starter/GreetingAutoConfiguration.java#L33)，放在启动类扫描范围之外的 `com.example.starter` 包里，只在 [.imports 文件](code/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports) 里登记了一行全类名，它照样生效了，这就是第三方 starter 被加载的方式。把 [application.yml](code/src/main/resources/application.yml#L33) 里的 `demo.greeting.enabled` 设成 false，`@ConditionalOnProperty` 不满足，`GreetingService` 就不存在了。

### Q2：常用的条件注解有哪些？

* **满分话术**：
  * `@ConditionalOnClass` / `@ConditionalOnMissingClass`：classpath 里有 / 没有某个类（判断有没有引入某个依赖）；
  * `@ConditionalOnBean` / `@ConditionalOnMissingBean`：容器里有 / 没有某个 Bean（实现“用户配置优先”，见 [greetingService()](code/src/main/java/com/example/starter/GreetingAutoConfiguration.java#L37)）；
  * `@ConditionalOnProperty`：配置文件里某个属性等于某个值（实现功能开关）；
  * `@ConditionalOnWebApplication`：当前是 Web 应用。
  * 排查技巧：配置 `debug: true` 启动，控制台会打印 `CONDITIONS EVALUATION REPORT`，列出每个自动配置类生效或不生效的原因。

### Q3：如何自定义一个 starter？

* **满分话术**（对照 `com.example.starter` 包）：
  1. 写一个 `XxxProperties` 类，用 `@ConfigurationProperties(prefix = "xxx")` 绑定配置（[GreetingProperties](code/src/main/java/com/example/starter/GreetingProperties.java#L10)）；
  2. 写功能类 `XxxService`，不加 Spring 注解（[GreetingService](code/src/main/java/com/example/starter/GreetingService.java)）；
  3. 写自动配置类 `XxxAutoConfiguration`：加 `@AutoConfiguration`、条件注解、`@EnableConfigurationProperties(XxxProperties.class)`，里面用 `@Bean @ConditionalOnMissingBean` 注册 `XxxService`（[GreetingAutoConfiguration](code/src/main/java/com/example/starter/GreetingAutoConfiguration.java#L33)）；
  4. 在 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 里写上自动配置类的全类名（[本项目的 .imports](code/src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports)）；
  5. 命名规范：官方叫 `spring-boot-starter-xxx`，第三方叫 `xxx-spring-boot-starter`。

### Q4：`@Value` 和 `@ConfigurationProperties` 的区别？

* **满分话术**：`@Value("${demo.jwt.secret}")` 一次注入一个配置项，适合零散的少量配置（项目里 [JwtUtil 构造器](code/src/main/java/com/example/demo/web/JwtUtil.java#L33) 用的就是它）；`@ConfigurationProperties(prefix = "demo.greeting")` 把一组配置批量绑定到一个对象上，支持松散绑定（`ttl-minutes` 对应 `ttlMinutes`）、类型转换、JSR-303 校验和 IDE 提示，配置项多的时候更清晰（项目里 [GreetingProperties](code/src/main/java/com/example/starter/GreetingProperties.java#L10) 用的就是它）。

## 5. Filter / Interceptor / AOP 与 JWT 统一鉴权

> 代码：[TraceFilter](code/src/main/java/com/example/demo/web/TraceFilter.java)、[LoginInterceptor](code/src/main/java/com/example/demo/web/LoginInterceptor.java)、[WebConfig](code/src/main/java/com/example/demo/web/WebConfig.java)、[JwtUtil](code/src/main/java/com/example/demo/web/JwtUtil.java)、[UserContext](code/src/main/java/com/example/demo/web/UserContext.java)，请求用 [requests.http](code/requests.http) 第 1 组

### Q1：Filter、Interceptor、AOP 有什么区别？

* **满分话术**：三者都能在业务前后加逻辑，区别在于**所处层次**不同：

  | | Filter（过滤器） | Interceptor（拦截器） | AOP（切面） |
  |---|---|---|---|
  | 所属规范 | Servlet 规范 | Spring MVC | Spring |
  | 谁来调用 | Tomcat | DispatcherServlet | Spring 代理对象 |
  | 作用范围 | 所有请求，包括静态资源 | 进入 DispatcherServlet 并匹配到 Controller 的请求 | 任意 Spring Bean 的方法，不限于 Web |
  | 能拿到什么 | `ServletRequest` / `ServletResponse` | request、response、要执行的 `HandlerMethod`（能读 Controller 方法上的注解） | 方法参数、返回值、异常、方法上的注解 |
  | 抛出的异常能否被 `@RestControllerAdvice` 捕获 | **不能** | 能 | 能 |
  | 典型用途 | 字符编码、跨域、traceId、XSS 过滤 | 登录鉴权、权限校验 | 日志、事务、缓存、限流 |
  | 项目代码 | [TraceFilter#doFilter](code/src/main/java/com/example/demo/web/TraceFilter.java#L32) | [LoginInterceptor#preHandle](code/src/main/java/com/example/demo/web/LoginInterceptor.java#L41) | [LogAspect#around](code/src/main/java/com/example/demo/aop/LogAspect.java#L35) |

* **执行顺序**：`Filter → DispatcherServlet → Interceptor#preHandle → AOP 代理 → Controller/Service 方法 → Interceptor#postHandle → Interceptor#afterCompletion → Filter 收尾`。调用登录接口时，控制台日志会依次打印 `[Filter]`、`[Interceptor]`、`[AOP]`。
* **选择原则**：和业务无关、所有请求都要做的放 Filter；和登录用户、接口权限相关的放 Interceptor；和具体业务方法相关的放 AOP。

### Q2：项目里统一登录鉴权是怎么做的？（小红书一面原题）

* **满分话术**：
  1. **登录**：用户提交用户名和密码，校验通过后用 JWT 签发一个 token 返回给前端（[UserService#login](code/src/main/java/com/example/demo/user/UserService.java#L37) → [JwtUtil#createToken](code/src/main/java/com/example/demo/web/JwtUtil.java#L39)）。注意用户不存在和密码错误返回同一个提示，防止被人探测哪些用户名已注册。
  2. **携带**：前端之后每次请求都在请求头带 `Authorization: Bearer <token>`。
  3. **拦截**：实现 `HandlerInterceptor`，在 [preHandle](code/src/main/java/com/example/demo/web/LoginInterceptor.java#L41) 里取出请求头、验签并校验过期时间（[JwtUtil#parseUserId](code/src/main/java/com/example/demo/web/JwtUtil.java#L51)），失败直接抛 401 业务异常，由全局异常处理器统一返回；成功就把 userId 放进 `ThreadLocal`（[UserContext](code/src/main/java/com/example/demo/web/UserContext.java#L14)）。
  4. **配置路径**：在 [WebConfig#addInterceptors](code/src/main/java/com/example/demo/web/WebConfig.java#L30) 里拦截 `/api/**`，放行 `/api/auth/login` 等白名单。
  5. **使用**：Service 里直接 `UserContext.getUserId()` 拿当前用户，不用一层层传参。
  6. **清理**：在 [afterCompletion](code/src/main/java/com/example/demo/web/LoginInterceptor.java#L58) 里 `ThreadLocal.remove()`，因为 Tomcat 线程是复用的，不清理会**串号**（下一个请求读到上一个用户的 id），还会**内存泄漏**。
  7. **进阶**：如果要做细粒度权限，可以自定义 `@RequireRole("admin")` 注解贴在 Controller 方法上，拦截器里通过 `HandlerMethod` 读取注解判断。

### Q3：JWT 的结构是什么？和 Session 比有什么优缺点？

* **满分话术**：
  1. **结构**：`Header.Payload.Signature` 三段 Base64URL 用点连接。Header 说明签名算法（如 HS256），Payload 放 userId、过期时间等声明，Signature 是用服务端密钥对前两段的签名（见 [JwtUtil](code/src/main/java/com/example/demo/web/JwtUtil.java)）。
  2. **注意**：Payload 只是 **Base64 编码，不是加密**，任何人都能解码看到，所以不能放密码等敏感信息。它的安全性来自签名：别人改了 Payload，签名就对不上。
  3. **优点**：服务端**无状态**，不用存储 token，靠验签就能判断真伪，天然支持多实例横向扩展；也适合跨服务、跨域传递身份。
  4. **缺点**：签发后**无法主动作废**（用户改密码、被封号、主动登出时，旧 token 在过期前依然有效）；token 比 Session ID 长，每次请求都要传。
  5. **对比**：传统 Session 是把用户信息存在服务端内存、给客户端一个 Session ID，多实例部署时要做 Session 共享。黑马点评的做法是生成随机 token 存进 Redis（见 [repos/README.md](../repos/README.md)），本质是“分布式 Session”，可以随时删除使其失效，但每次请求都要查一次 Redis。

### Q4：JWT 怎么实现主动失效和自动续期？

* **满分话术**：
  * **主动失效**：一是**黑名单**，登出时把 token 的唯一 ID（jti）存进 Redis，过期时间设为 token 剩余有效期，拦截器验签后再查一下黑名单；二是**版本号**，Redis 里存用户的 tokenVersion，签发时写进 Payload，改密码时版本号加一，旧 token 就对不上了。
  * **自动续期**：用**双 token**，access token 有效期短（如 30 分钟），refresh token 有效期长（如 7 天）并存进 Redis。access token 过期后，前端用 refresh token 换一个新的 access token，用户无感知；登出时删掉 refresh token 即可。

### Q5：ThreadLocal 为什么必须 remove？

* **满分话术**：每个线程内部有一个 `ThreadLocalMap`，key 是 ThreadLocal 对象的**弱引用**，value 是**强引用**。Tomcat 的工作线程是池化的、长期存活的，如果用完不 remove：一是**数据串号**，线程被下一个请求复用时会读到上一个用户的数据；二是**内存泄漏**，ThreadLocal 对象被回收后 key 变成 null，但 value 还被线程强引用着，一直无法回收。所以项目里在拦截器的 [afterCompletion](code/src/main/java/com/example/demo/web/LoginInterceptor.java#L58) 里统一调用 [UserContext.clear()](code/src/main/java/com/example/demo/web/UserContext.java#L28)，它无论请求成功还是失败都会执行。另外，`@Async` 或线程池里的子线程拿不到父线程的 ThreadLocal，需要手动传参。

## 6. @Transactional 与失效场景

> 代码：[TxDemoService](code/src/main/java/com/example/demo/tx/TxDemoService.java)、[TxInnerService](code/src/main/java/com/example/demo/tx/TxInnerService.java)、[TxDemoController](code/src/main/java/com/example/demo/tx/TxDemoController.java#L65)，场景列表 [http://localhost:8080/demo/tx](http://localhost:8080/demo/tx)

### Q1：`@Transactional` 的原理是什么？

* **满分话术**：
  1. `@Transactional` 是**基于 AOP 实现**的。容器启动时，给带这个注解的 Bean 生成代理，增强逻辑在 `TransactionInterceptor` 里。
  2. **调用流程**：代理拦截到方法调用 → 通过 `PlatformTransactionManager`（JDBC 下是 `DataSourceTransactionManager`）从连接池拿一个连接，`setAutoCommit(false)` → 把这个连接**绑定到当前线程**（`TransactionSynchronizationManager` 里的 ThreadLocal）→ 执行业务方法，MyBatis、JdbcTemplate 执行 SQL 时会从当前线程拿这个连接，所以多条 SQL 共用一个事务 → 方法正常返回就 `commit`，抛出异常就判断是否需要 `rollback` → 最后解绑连接、归还连接池。
  3. 从这个原理可以推出所有失效场景：**没经过代理**、**换了线程**、**异常没抛到代理**，事务都会失效。

### Q2：`@Transactional` 有哪些失效场景？（高频）

* **满分话术**（前 6 个在项目里都能直接复现）：

  | 场景 | 原因 | 代码 | 演示（表里剩余行数） |
  |---|---|---|---|
  | **同类方法自调用** | `this` 是原对象，没经过代理 | [selfInvocation](code/src/main/java/com/example/demo/tx/TxDemoService.java#L49) | [self-invocation](http://localhost:8080/demo/tx/self-invocation)（1，失效） |
  | **抛出受检异常** | 默认只对 `RuntimeException` 和 `Error` 回滚 | [checkedException](code/src/main/java/com/example/demo/tx/TxDemoService.java#L68) | [checked-exception](http://localhost:8080/demo/tx/checked-exception)（1，失效） |
  | **异常被 catch 吞掉** | 代理是靠“方法抛出异常”判断回滚的，吞掉就以为成功了 | [swallowException](code/src/main/java/com/example/demo/tx/TxDemoService.java#L84) | [swallow](http://localhost:8080/demo/tx/swallow)（1，失效） |
  | **多线程** | 事务连接绑定在当前线程，子线程拿到的是另一个自动提交的连接 | [multiThread](code/src/main/java/com/example/demo/tx/TxDemoService.java#L97) | [multi-thread](http://localhost:8080/demo/tx/multi-thread)（1，子线程的写入已提交） |
  | **内层 REQUIRES_NEW** | 内层是独立事务，外层回滚影响不到它（这是特性不是 bug，但常被误用） | [requiresNew](code/src/main/java/com/example/demo/tx/TxDemoService.java#L109) → [insertInNewTransaction](code/src/main/java/com/example/demo/tx/TxInnerService.java#L22) | [requires-new](http://localhost:8080/demo/tx/requires-new)（1） |
  | **内层失败被外层 catch** | 内层把共享事务标记为 rollback-only，外层提交时整体回滚并抛 `UnexpectedRollbackException` | [rollbackOnly](code/src/main/java/com/example/demo/tx/TxDemoService.java#L121) → [insertThenFail](code/src/main/java/com/example/demo/tx/TxInnerService.java#L28) | [rollback-only](http://localhost:8080/demo/tx/rollback-only)（0，但调用方收到异常） |
  | 方法是 `private` / `final` / `static` | CGLIB 子类无法重写这些方法（Spring 6 之前非 public 方法也不生效） | — | — |
  | 类没交给 Spring 管理 | 自己 `new` 出来的对象没有代理 | — | — |
  | 传播行为配置成不支持事务 | 如 `NOT_SUPPORTED`、`NEVER`、`SUPPORTS`（外层无事务时） | — | — |
  | 数据库引擎不支持事务 | MySQL 的 MyISAM 不支持事务，要用 InnoDB | — | — |

* **对应的修复**：
  * 自调用：拆到另一个 Bean，或注入自己的代理（[selfInvocationFixed](code/src/main/java/com/example/demo/tx/TxDemoService.java#L54)，演示 [self-invocation-fixed](http://localhost:8080/demo/tx/self-invocation-fixed)）；
  * 受检异常：统一写 `@Transactional(rollbackFor = Exception.class)`（[checkedExceptionFixed](code/src/main/java/com/example/demo/tx/TxDemoService.java#L75)，演示 [checked-exception-fixed](http://localhost:8080/demo/tx/checked-exception-fixed)），阿里规范也要求这样写；
  * catch 了异常：要么重新抛出，要么手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。

### Q3：事务传播行为有哪些？

* **满分话术**：传播行为解决的是“**一个事务方法调用另一个事务方法时，事务怎么处理**”，一共 7 种，重点掌握前 3 种：
  * **`REQUIRED`（默认）**：有事务就加入，没有就新建。内外层是同一个事务，一起提交、一起回滚。
  * **`REQUIRES_NEW`**：总是新建事务，外层事务先挂起。内外层互不影响，典型用途是“不管业务成功与否都要落库的操作日志”。
  * **`NESTED`**：有事务就在里面建一个**保存点**（savepoint）。内层回滚只回到保存点，不影响外层；外层回滚则内层一起回滚。
  * `SUPPORTS`：有就加入，没有就以非事务方式执行；`NOT_SUPPORTED`：以非事务方式执行，有事务就挂起；`MANDATORY`：必须在事务中，否则抛异常；`NEVER`：必须不在事务中，否则抛异常。
* **注意**：传播行为同样依赖代理，内层方法必须在**另一个 Bean** 里，项目里因此专门写了 [TxInnerService](code/src/main/java/com/example/demo/tx/TxInnerService.java#L12)。

### Q4：什么是大事务？有什么危害？怎么优化？

* **满分话术**：大事务指一个事务执行时间过长，比如在事务里做了远程调用、批量处理、复杂计算。危害：**长时间占用数据库连接**，并发一高连接池就被耗尽，其他请求全部阻塞；长时间持有行锁导致锁等待和死锁；undo log 堆积；回滚代价大。优化办法：
  * 把查询、校验、远程调用等**挪到事务外面**，事务里只保留必要的写操作；
  * 用编程式事务 `TransactionTemplate` 精确控制事务边界，代替整个方法加 `@Transactional`；
  * 耗时的批量操作改成**异步**：快速校验参数、落库后返回 `202 Accepted`，后台再慢慢处理（这正是 [学习路线](../java.md) 里项目亮点 1 的思路）。

### Q5：`@Transactional` 的隔离级别和 MySQL 的隔离级别是什么关系？

* **满分话术**：`@Transactional(isolation = ...)` 默认是 `Isolation.DEFAULT`，即**使用数据库自身的隔离级别**，MySQL InnoDB 默认是**可重复读（RR）**。如果显式指定了，Spring 会在开启事务时对这个连接执行 `SET TRANSACTION ISOLATION LEVEL ...`，只对当前事务生效。隔离级别本身的原理（MVCC、ReadView）见 [MySQL 模块](../04-mysql/八股.md)。

## 7. 全局异常处理

> 代码：[Result](code/src/main/java/com/example/demo/common/Result.java#L7)、[BizException](code/src/main/java/com/example/demo/common/BizException.java#L9)、[GlobalExceptionHandler](code/src/main/java/com/example/demo/common/GlobalExceptionHandler.java#L31)，请求用 [requests.http](code/requests.http) 2.4、2.5、2.9、2.10

### Q1：项目里怎么做全局异常处理的？原理是什么？

* **满分话术**：
  1. **做法**：定义一个类加 `@RestControllerAdvice`（等于 `@ControllerAdvice` + `@ResponseBody`），里面用 `@ExceptionHandler(XxxException.class)` 为不同异常写处理方法，统一转换成 `{code, msg, data}` 格式的返回体（[Result](code/src/main/java/com/example/demo/common/Result.java#L7)），Controller 和 Service 里就不用到处 try-catch。
  2. **分类处理**：
     * **业务异常** `BizException`：可预期的错误（用户不存在、密码错误、未登录），带上 HTTP 状态码和提示信息，直接返回给前端（[handleBiz](code/src/main/java/com/example/demo/common/GlobalExceptionHandler.java#L36)）；
     * **参数校验异常**：`@Valid` 失败抛的 `MethodArgumentNotValidException`，把每个字段的错误拼起来返回 400（[handleValidation](code/src/main/java/com/example/demo/common/GlobalExceptionHandler.java#L45)）；
     * **兜底** `Exception`：未预期的系统异常，记录完整堆栈，但只给前端返回“系统繁忙”，**不暴露内部细节**（比如 SQL 报错信息）（[handleUnknown](code/src/main/java/com/example/demo/common/GlobalExceptionHandler.java#L87)）。
  3. **原理**：DispatcherServlet 在调用 Controller（以及拦截器）时会 catch 住异常，交给 `HandlerExceptionResolver` 链处理，其中 `ExceptionHandlerExceptionResolver` 负责找到 `@ControllerAdvice` 里匹配的 `@ExceptionHandler` 方法。匹配规则是**异常类型继承关系最近的优先**，所以兜底的 `Exception` 不会抢走 `BizException`。

### Q2：Filter 里抛的异常能被全局异常处理器捕获吗？

* **满分话术**：**不能**。全局异常处理是 DispatcherServlet 内部的机制，而 Filter 在 DispatcherServlet 外面执行（[TraceFilter](code/src/main/java/com/example/demo/web/TraceFilter.java#L32)），Filter 抛出的异常会直接交给 Tomcat，最后由 Spring Boot 默认的 `/error`（`BasicErrorController`）处理，返回的格式和我们统一的返回体不一样。解决办法：在 Filter 里自己 try-catch 并直接写响应；或者在 Filter 里注入 `HandlerExceptionResolver`，手动调用 `resolveException` 交给全局异常处理。这也是**登录鉴权更推荐放在拦截器而不是 Filter** 的原因之一。

### Q3：为什么业务异常要继承 `RuntimeException`？

* **满分话术**：一是业务代码不用到处写 `throws`，代码更干净；二是 `@Transactional` **默认只对 RuntimeException 回滚**，业务异常继承它（[BizException](code/src/main/java/com/example/demo/common/BizException.java#L9)），抛出时事务就会自动回滚，不用每个地方都写 `rollbackFor`。

## 高频追问速查

| 问题 | 一句话答案 |
|---|---|
| 注解为什么能生效？ | 注解只是元数据，`@Retention(RUNTIME)` 保留到运行期，由 Spring 的扫描器或 BeanPostProcessor 用反射读取后执行逻辑 |
| Spring Boot 默认用哪种代理？ | CGLIB（2.x 起 `proxy-target-class=true`） |
| AOP 代理在生命周期哪一步生成？ | 初始化之后，BeanPostProcessor 的 `postProcessAfterInitialization`；发生循环依赖时会通过三级缓存提前生成 |
| MyBatis 的 Mapper 接口没有实现类为什么能用？ | MyBatis 为每个 Mapper 接口生成了 JDK 动态代理（MapperProxy），调用方法时执行对应 SQL（[UserMapper](code/src/main/java/com/example/demo/user/UserMapper.java#L12)） |
| 构造器注入的循环依赖怎么办？ | 用 `@Lazy` 注入延迟代理，或者重构消除循环依赖 |
| 自动配置读的是哪个文件？ | Boot 2.7+：`META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`；之前：`META-INF/spring.factories` |
| 怎么让自己的 Bean 覆盖自动配置的？ | 自己定义一个同类型的 `@Bean`，自动配置上的 `@ConditionalOnMissingBean` 就不满足了 |
| 拦截器 `postHandle` 和 `afterCompletion` 的区别？ | `postHandle` 在 Controller 正常返回后执行，抛异常就不执行；`afterCompletion` 无论成败都执行，适合做清理 |
| `@Transactional` 加在类上和方法上？ | 类上对所有 public 方法生效，方法上的配置优先级更高 |
| 切面里打印参数要注意什么？ | 密码、手机号、身份证等敏感字段要脱敏（项目里的 [LogAspect](code/src/main/java/com/example/demo/aop/LogAspect.java#L35) 为了演示直接打印了） |
