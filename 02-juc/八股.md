## 1. 线程的 6 种状态及切换

> 代码：[ThreadStateDemo](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L22)

### Q1：线程有哪几种状态？怎么转换的？（高频）

* **满分话术**：`Thread.State` 枚举定义了 6 种状态，[ThreadStateDemo](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L22) 把每一种都复现了出来：
  | 状态 | 含义 | 怎么进入 | 代码 |
  |---|---|---|---|
  | `NEW` | 创建了，还没 `start()` | `new Thread()` | [第 27 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L27) |
  | `RUNNABLE` | 可运行，包括操作系统的“就绪”和“运行中”，**阻塞在 IO 上也算** | `start()` | [第 31 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L31) |
  | `BLOCKED` | 等待进入 `synchronized` | 抢 Monitor 锁失败 | [第 46 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L46) |
  | `WAITING` | 无限期等待，要别人唤醒 | `wait()`、`join()`、`LockSupport.park()` | [第 59 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L59) |
  | `TIMED_WAITING` | 有超时的等待 | `sleep(ms)`、`wait(ms)`、`join(ms)`、`parkNanos` | [第 77 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L77) |
  | `TERMINATED` | `run()` 执行完或抛出异常 | — | [第 42 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L42) |

  转换：`NEW → start() → RUNNABLE`；`RUNNABLE` 抢 synchronized 失败 → `BLOCKED`，抢到 → `RUNNABLE`；`RUNNABLE` 调 `wait/join/park` → `WAITING`，被 `notify`/目标线程结束/`unpark` → `RUNNABLE`（从 `wait` 醒来还要重新抢锁，抢不到就是 `BLOCKED`）；带超时的版本对应 `TIMED_WAITING`；`run` 结束 → `TERMINATED`。
* **两个加分点**：
  1. **抢 `ReentrantLock` 失败是 `WAITING`，不是 `BLOCKED`**（[第 84 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L84)）。因为 AQS 是用 `LockSupport.park` 挂起线程的，`BLOCKED` 专指等待 synchronized 的 Monitor。jstack 里看到大量 `WAITING (parking)` 通常是在等 JUC 的锁或队列。
  2. Java 没有 `RUNNING` 状态。线程在做网络 IO 读阻塞时 Java 层面仍是 `RUNNABLE`，所以 jstack 看到一堆 `RUNNABLE` 不一定在消耗 CPU。

### Q2：`sleep` 和 `wait` 的区别？

* **满分话术**：
  | | `Thread.sleep(ms)` | `Object.wait()` |
  |---|---|---|
  | 所属 | `Thread` 的静态方法 | `Object` 的实例方法 |
  | 是否释放锁 | **不释放** | **释放**锁，被唤醒后要重新抢锁 |
  | 使用前提 | 任何地方都能调 | 必须在 `synchronized` 块里，否则 `IllegalMonitorStateException` |
  | 唤醒方式 | 时间到自动醒 | `notify`/`notifyAll`，或超时 |
  | 用途 | 暂停执行 | 线程间协作（等条件满足） |

  `wait` 必须放在 `while` 循环里判断条件，因为存在**虚假唤醒**，而且被唤醒时条件可能已经被别的线程改了。

### Q3：`park/unpark` 和 `wait/notify` 有什么区别？

* **满分话术**：`LockSupport.park/unpark` 是 JUC 的基础（AQS 用它挂起和唤醒线程）。区别：一是**不需要持有锁**；二是 `unpark` 可以**指定唤醒哪个线程**，`notify` 只能随机唤醒一个；三是 `unpark` 发的是一张“**许可证**”（最多存 1 张），**先 unpark 后 park 不会阻塞**，而先 `notify` 后 `wait` 会永远等下去（[第 106 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L106)）。这个特性让 AQS 不用担心“唤醒信号丢失”。

### Q4：`start()` 和 `run()` 的区别？怎么停止一个线程？

* **满分话术**：`start()` 会让 JVM 创建一个新线程，在新线程里执行 `run()`；直接调 `run()` 只是在当前线程里调用一个普通方法。同一个线程 `start` 两次抛 `IllegalThreadStateException`（[第 116 行](code/src/main/java/com/example/juc/state/ThreadStateDemo.java#L116)）。停止线程用**中断**：调 `thread.interrupt()` 设置中断标志，线程里循环检查 `Thread.currentThread().isInterrupted()` 自己退出；如果线程正在 `sleep`/`wait`/`join`，会立刻抛 `InterruptedException`（同时清除中断标志，catch 后通常要重新 `interrupt()` 一下）。`stop()` 已废弃，它会强行释放所有锁，导致数据不一致。

## 2. synchronized：Monitor 原理与锁升级

> 代码：[SyncCounterDemo](code/src/main/java/com/example/juc/sync/SyncCounterDemo.java#L16)、[LockUpgradeDemo](code/src/main/java/com/example/juc/sync/LockUpgradeDemo.java#L20)

### Q1：synchronized 的底层原理是什么？（高频）

* **满分话术**：
  1. **字节码层面**：同步代码块编译成 `monitorenter` 和 `monitorexit` 指令，而且有**两个 `monitorexit`**，第二个在异常处理路径上，保证抛异常也能释放锁；同步方法则是在方法的访问标志里加 `ACC_SYNCHRONIZED`，JVM 调用时自动加锁（可以对 [SyncCounterDemo](code/src/main/java/com/example/juc/sync/SyncCounterDemo.java#L16) 的 class 文件执行 `javap -c -v` 查看）。
  2. **Monitor**：每个 Java 对象都可以关联一个监视器锁，HotSpot 里是 C++ 的 `ObjectMonitor`，核心字段：`_owner`（持有锁的线程）、`_recursions`（重入次数）、`_EntryList`（抢锁失败、处于 `BLOCKED` 的线程）、`_WaitSet`（调用了 `wait`、处于 `WAITING` 的线程）。这也是为什么 `wait/notify` 必须在 synchronized 里调用 —— 它们操作的就是 Monitor 的 `_WaitSet`。
  3. **锁的是什么**：实例方法锁 `this`，静态方法锁 `类.class`，代码块锁括号里的对象。实例锁和类锁是两把不同的锁，互不阻塞（[实验 2](code/src/main/java/com/example/juc/sync/SyncCounterDemo.java#L46)）。
  4. **可重入**：同一个线程再次进入同一把锁时，发现 `_owner` 是自己，重入计数 +1 即可（[outer → inner](code/src/main/java/com/example/juc/sync/SyncCounterDemo.java#L73)）。
  5. **为什么需要它**：`count++` 是读、加、写三条字节码，多线程交错执行会少加（[实验 1](code/src/main/java/com/example/juc/sync/SyncCounterDemo.java#L32)）。synchronized 同时保证**原子性、可见性、有序性**。

### Q2：synchronized 的锁升级过程？（高频）

* **满分话术**：JDK 6 为了减少重量级锁的开销，引入了锁升级，状态记录在对象头的 **Mark Word** 里（最低 2 位是锁标志）：
  1. **无锁**（01）：Mark Word 存 hashCode 和 GC 分代年龄。
  2. **偏向锁**（101）：第一个线程加锁时把自己的线程 ID 写进 Mark Word，之后这个线程再加锁只要比较一下 ID，连 CAS 都不用。适合“始终只有一个线程用”的场景。**JDK 15 起默认关闭，JDK 18 彻底移除**，因为现代应用里这种场景少，而偏向锁的撤销需要等到安全点，代价很高。
  3. **轻量级锁**（00）：有第二个线程来，但是**交替执行、没有真正竞争**。线程在自己的栈帧里建一个 Lock Record，用 **CAS** 把 Mark Word 换成指向 Lock Record 的指针。不需要操作系统介入。
  4. **重量级锁**（10）：**真正的竞争**出现（CAS 自旋一定次数仍失败），膨胀成重量级锁，Mark Word 指向 `ObjectMonitor`，抢不到锁的线程被操作系统**挂起**（用户态 → 内核态切换，开销大）。
  
  锁一般只升级不降级（HotSpot 在 GC 时可以对空闲的 Monitor 做“降级”/deflation，面试说“基本只升不降”即可）。
* **项目里的观察**：[LockUpgradeDemo](code/src/main/java/com/example/juc/sync/LockUpgradeDemo.java#L20) 用 JOL 打印对象头，在 JDK 17 上依次看到 `non-biasable`（无锁）→ `thin lock`（轻量级锁）→ 释放后回到无锁 → 有竞争后 `fat lock`（重量级锁）。另外调用过 `wait` 的对象会直接是重量级锁（[第 48 行](code/src/main/java/com/example/juc/sync/LockUpgradeDemo.java#L48)），因为只有 `ObjectMonitor` 才有 `_WaitSet`。
* **其他优化**：**自适应自旋**（根据上次自旋是否成功调整自旋次数）、**锁消除**（JIT 通过逃逸分析发现锁对象不会被其他线程访问，直接去掉锁）、**锁粗化**（循环里反复加锁解锁，合并成一次）。

## 3. volatile 与 Java 内存模型

> 代码：[VolatileDemo](code/src/main/java/com/example/juc/sync/VolatileDemo.java#L8)

### Q1：volatile 有什么作用？能保证原子性吗？（高频）

* **满分话术**：
  1. **可见性**：Java 内存模型（JMM）里每个线程有自己的工作内存（CPU 缓存、寄存器的抽象），普通变量的修改不保证其他线程立刻看到。volatile 变量的写会立刻刷回主内存，读会直接从主内存读。实验里，普通变量 `while (!plainStop)` 的线程大概率停不下来 —— JIT 把循环条件提到循环外只读了一次（[第 20 行](code/src/main/java/com/example/juc/sync/VolatileDemo.java#L20)）；volatile 版本能正常停下。
  2. **禁止指令重排序**：编译器和 CPU 会为了性能重排指令，volatile 读写前后会插入**内存屏障**，禁止相关的重排。典型应用是**双重检查锁单例**（[Singleton](code/src/main/java/com/example/juc/sync/VolatileDemo.java#L71)）：`instance = new Singleton()` 分为分配内存、初始化、赋值引用三步，后两步可能被重排，其他线程拿到一个还没初始化完的对象。给 `instance` 加 volatile 就能避免（[第 72 行](code/src/main/java/com/example/juc/sync/VolatileDemo.java#L72)）。
  3. **不保证原子性**：`volatileCount++` 依然是读、加、写三步，4 个线程各加 10 万次结果小于 40 万（[实验 2](code/src/main/java/com/example/juc/sync/VolatileDemo.java#L44)）。要原子性用 `synchronized` 或 `AtomicInteger`。
* **适用场景**：一写多读的状态标志（如 `running`、配置开关）、DCL 单例。

### Q2：什么是 happens-before？

* **满分话术**：JMM 用 happens-before 规则描述“一个操作的结果对另一个操作可见”，常用的几条：**程序顺序规则**（同一线程内，前面的操作 happens-before 后面的）、**锁规则**（解锁 happens-before 之后对同一把锁的加锁）、**volatile 规则**（对 volatile 变量的写 happens-before 之后对它的读）、**线程启动规则**（`start()` happens-before 线程内的所有操作）、**线程终止规则**（线程内所有操作 happens-before 其他线程 `join()` 返回）、**传递性**。所以 synchronized 和 volatile 都能保证可见性，是由这些规则定义的。

## 4. ReentrantLock 与 AQS

> 代码：[MiniAqsLock](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L17)、[ReentrantLockDemo](code/src/main/java/com/example/juc/lock/ReentrantLockDemo.java#L14)、[ConditionBufferDemo](code/src/main/java/com/example/juc/lock/ConditionBufferDemo.java#L19)

### Q1：讲一下 AQS 的原理？（高频）

* **满分话术**：AQS（`AbstractQueuedSynchronizer`）是 JUC 里锁和同步器的基础框架，`ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReentrantReadWriteLock` 都基于它。核心是“**一个状态 + 一个队列**”：
  1. **`volatile int state`**：同步状态，用 **CAS** 修改。含义由子类定义：`ReentrantLock` 里是重入次数（0 表示没人持有），`Semaphore` 里是剩余许可数，`CountDownLatch` 里是剩余计数（[MiniAqsLock 第 55 行的 CAS](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L55)）。
  2. **CLH 变体的双向等待队列**：抢不到锁的线程包装成 `Node` 加入队尾，然后 `LockSupport.park` 挂起（[第 42 行](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L42)）。
  3. **释放**：持锁线程把 state 减到 0 后，`unpark` 唤醒队头的下一个节点，被唤醒的线程再去 CAS 抢锁（[第 84 行](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L84)）。
  4. **模板方法模式**：AQS 实现了排队、挂起、唤醒这些通用逻辑（`acquire`、`release`），子类只需要重写 `tryAcquire`、`tryRelease`（独占）或 `tryAcquireShared`、`tryReleaseShared`（共享）来定义“怎样算抢到”。
* **我写过的迷你版**：[MiniAqsLock](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L17) 保留了这个骨架：[lock()](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L29) 先 `tryAcquire`，失败就入队，只有队头线程才有资格抢锁，抢不到就 park；被唤醒或虚假唤醒后回到循环开头重新检查。4 个线程各加 10 万次，结果正好 40 万。

### Q2：公平锁和非公平锁的区别？ReentrantLock 默认是哪种？为什么？

* **满分话术**：
  1. **区别只有一行代码**：公平锁在 `tryAcquire` 里多了一个 `hasQueuedPredecessors()` 判断 —— 队列里有人在等，自己就不抢，乖乖排队；非公平锁不管队列，**直接 CAS 抢**，抢到就算插队成功（[第 52 行](code/src/main/java/com/example/juc/lock/MiniAqsLock.java#L52)）。另外非公平锁在 `lock()` 一进来就先 CAS 抢一次。
  2. **默认非公平**，因为**吞吐量更高**：锁刚释放时，正在 CPU 上运行的线程直接抢到，省掉了“唤醒队头线程 → 线程被调度上 CPU”这段上下文切换的时间。代价是可能出现线程**饥饿**。
  3. **实测**（[实验 3](code/src/main/java/com/example/juc/lock/ReentrantLockDemo.java#L74)）：5 个线程各抢 3 次，公平锁的获取顺序是 `A B C D E A B C D E …` 轮流；非公平锁经常是同一个线程连续拿到（刚释放又立刻抢回来）。

### Q3：synchronized 和 ReentrantLock 有什么区别？（快手一面、小红书一面原题）

* **满分话术**：
  | | synchronized | ReentrantLock |
  |---|---|---|
  | 实现 | JVM 关键字，Monitor | JDK 类，基于 AQS |
  | 加锁释放 | 自动，异常时也会自动释放 | 手动 `lock()`，**必须在 finally 里 `unlock()`** |
  | 可重入 | 是 | 是 |
  | 公平锁 | 只有非公平 | 可选公平 / 非公平 |
  | 尝试加锁 / 超时 | 不支持，抢不到就一直等 | `tryLock()`、`tryLock(timeout)`（[实验 1](code/src/main/java/com/example/juc/lock/ReentrantLockDemo.java#L23)） |
  | 可中断 | 等锁时不响应中断 | `lockInterruptibly()`（[实验 2](code/src/main/java/com/example/juc/lock/ReentrantLockDemo.java#L47)） |
  | 条件队列 | 只有一个（`wait/notify`） | 可以绑定多个 `Condition`，精准唤醒 |
  | 等锁的线程状态 | `BLOCKED` | `WAITING` |

  **怎么选**：普通场景用 synchronized，代码简单不会忘记解锁，JDK 6 之后性能也不差；需要超时、可中断、公平锁、多个条件队列时用 ReentrantLock。

### Q4：Condition 是怎么用的？原理是什么？

* **满分话术**：`Condition` 是 ReentrantLock 版的 `wait/notify`：`await()` 释放锁并等待，`signal()` 唤醒一个等待者。区别是一把锁可以创建**多个 Condition**。经典例子是有界缓冲区（[BoundedBuffer](code/src/main/java/com/example/juc/lock/ConditionBufferDemo.java#L21)，JDK 文档的官方示例，`ArrayBlockingQueue` 是同样的结构）：生产者在 `notFull` 上等（[第 37 行](code/src/main/java/com/example/juc/lock/ConditionBufferDemo.java#L37)），消费者在 `notEmpty` 上等，放入元素后只 `notEmpty.signal()` 唤醒消费者（[第 44 行](code/src/main/java/com/example/juc/lock/ConditionBufferDemo.java#L44)），不会把其他生产者也叫醒。原理：每个 Condition（AQS 的 `ConditionObject`）有一条自己的**条件队列**；`await` 把线程加入条件队列、完全释放锁、park；`signal` 把条件队列的头节点**转移到 AQS 的同步队列**，等它重新抢到锁后从 `await` 返回。

## 5. CAS 与原子类

> 代码：[CasDemo](code/src/main/java/com/example/juc/cas/CasDemo.java#L13)

### Q1：什么是 CAS？AtomicInteger 是怎么实现的？

* **满分话术**：
  1. **CAS（Compare And Swap）**：有三个操作数，内存地址 V、预期值 A、新值 B。只有 V 的值等于 A 时才把它改成 B，否则什么都不做，返回是否成功。整个过程由一条 CPU 原子指令完成（x86 上是 `lock cmpxchg`），**不需要加锁**，是乐观锁的实现方式。
  2. **AtomicInteger**：内部是 `volatile int value`，`incrementAndGet` 调用 `Unsafe.getAndAddInt`，就是一个“**读当前值 → CAS → 失败就重试**”的自旋循环（[源码和手写版](code/src/main/java/com/example/juc/cas/CasDemo.java#L49)）。volatile 保证读到最新值，CAS 保证写入原子。

### Q2：CAS 有什么问题？

* **满分话术**：
  1. **ABA 问题**：值从 A 改成 B 又改回 A，CAS 只比较值，以为没变过（[实验 3](code/src/main/java/com/example/juc/cas/CasDemo.java#L78)）。对计数器无所谓，但对“栈顶指针”这种引用，A 虽然还是 A，下面的结构可能已经变了。解决：**加版本号**，用 `AtomicStampedReference`，每次修改版本号 +1，比较时值和版本号都要对上（[第 86 行](code/src/main/java/com/example/juc/cas/CasDemo.java#L86)）。数据库乐观锁的 `version` 字段是同样的思路。
  2. **自旋开销**：竞争激烈时 CAS 大量失败，线程一直空转消耗 CPU（[实验 2](code/src/main/java/com/example/juc/cas/CasDemo.java#L49) 打印了重试次数）。
  3. **只能保证一个变量的原子操作**：多个变量要么用锁，要么合并成一个对象用 `AtomicReference`。

### Q3：LongAdder 为什么比 AtomicLong 快？

* **满分话术**：`AtomicLong` 所有线程 CAS 同一个变量，竞争激烈时大部分 CAS 都失败重试。`LongAdder` 用**分段**的思路：没有竞争时 CAS 一个 `base` 变量；出现竞争后，每个线程按 hash 分散到一个 `Cell` 数组的不同格子上累加，`sum()` 时把 `base` 和所有 Cell 加起来，**用空间换时间**（[实验 4](code/src/main/java/com/example/juc/cas/CasDemo.java#L101)）。代价是 `sum()` 不是强一致的快照，所以适合统计计数（QPS、访问量），不适合生成唯一序号。`ConcurrentHashMap` 的 size 计数是同一个设计。Cell 类上有 `@Contended` 注解做缓存行填充，避免**伪共享**。

## 6. 线程池

> 代码：[ThreadPoolFlowDemo](code/src/main/java/com/example/juc/pool/ThreadPoolFlowDemo.java#L33)

### Q1：线程池有哪 7 个参数？任务提交流程是什么？（快手一面、小红书一面原题）

* **满分话术**：
  1. **7 大参数**（[newPool](code/src/main/java/com/example/juc/pool/ThreadPoolFlowDemo.java#L41)）：
     * `corePoolSize` 核心线程数：常驻，空闲也不回收（除非开了 `allowCoreThreadTimeOut`）；
     * `maximumPoolSize` 最大线程数：**队列满了**才会扩到这个数；
     * `keepAliveTime` + `unit`：非核心线程空闲多久被回收；
     * `workQueue` 阻塞队列：**生产环境一定用有界队列**，防止任务堆积 OOM；
     * `threadFactory`：给线程起有意义的名字，出问题时 jstack 一眼看出是哪个池（[NamedThreadFactory](code/src/main/java/com/example/juc/pool/ThreadPoolFlowDemo.java#L101)）；
     * `handler` 拒绝策略。
  2. **提交流程**（`execute` 源码贴在 [类注释](code/src/main/java/com/example/juc/pool/ThreadPoolFlowDemo.java#L14) 里）：线程数 < 核心数 → **新建核心线程**；否则 → **放进队列**；队列满了 → **新建非核心线程**，直到最大线程数；还满 → **拒绝策略**。注意顺序是“核心 → 队列 → 非核心”，不是“核心 → 最大 → 队列”。
  3. **实测**（[实验 1](code/src/main/java/com/example/juc/pool/ThreadPoolFlowDemo.java#L51)，core=2，max=4，队列容量 2，依次提交 7 个耗时任务）：任务 1、2 → 核心线程；3、4 → 队列；5、6 → 非核心线程；7 → 拒绝。而且 **5、6 比 3、4 先执行**，后提交的反而先跑。

### Q2：有哪些拒绝策略？

* **满分话术**（[实验 2](code/src/main/java/com/example/juc/pool/ThreadPoolFlowDemo.java#L74)）：
  * `AbortPolicy`（默认）：抛 `RejectedExecutionException`；
  * `CallerRunsPolicy`：让**提交任务的线程自己执行**。好处是不丢任务，而且调用方忙着执行任务就没空继续提交，天然起到**限流**作用；
  * `DiscardPolicy`：静默丢弃，什么都不说，最危险；
  * `DiscardOldestPolicy`：丢掉队列里最老的任务，再尝试提交当前任务。
  
  生产上常**自定义拒绝策略**：记录日志、发告警，把任务持久化到数据库或 MQ，稍后重试。

### Q3：为什么不推荐用 Executors 创建线程池？

* **满分话术**：阿里规范明确禁止，原因是容易 OOM：
  * `newFixedThreadPool` / `newSingleThreadExecutor`：队列是**无界**的 `LinkedBlockingQueue`（容量 `Integer.MAX_VALUE`），任务处理不过来就无限堆积，最终 OOM。而且队列永远不满，最大线程数形同虚设（README 动手实验 4）。
  * `newCachedThreadPool`：最大线程数是 `Integer.MAX_VALUE`，队列是不存任务的 `SynchronousQueue`，任务多时会**无限创建线程**，耗尽内存或系统线程数。
  * `newScheduledThreadPool`：延迟队列无界。
  
  所以要用 `new ThreadPoolExecutor(...)` 显式指定所有参数，让使用者清楚线程池的边界。

### Q4：核心线程数设多少合适？

* **满分话术**：
  * **CPU 密集型**（计算、加解密）：`CPU 核数 + 1`，线程多了只会增加上下文切换；
  * **IO 密集型**（查数据库、调接口）：线程大部分时间在等 IO，可以多开，经验值 `2 × CPU 核数`，或者按公式 `核数 × (1 + 等待时间 / 计算时间)`；
  * 这些只是起点，最终要**压测**确定，并且最好做成**可动态调整**的（`setCorePoolSize`、`setMaximumPoolSize` 可以运行时修改，美团的动态线程池就是这个思路），同时监控活跃线程数、队列长度、拒绝次数。

### Q5：线程池里的线程是怎么复用的？怎么关闭线程池？

* **满分话术**：
  1. **复用**：每个线程被包装成一个 `Worker`，它的 `runWorker` 方法是一个循环：先执行创建时带的第一个任务，然后不断调用 `getTask()` 从队列里取任务执行。`getTask` 用 `workQueue.take()` 阻塞等待（核心线程），或者 `poll(keepAliveTime)` 超时等待（非核心线程，超时返回 null，线程就退出了 —— 这就是非核心线程的回收机制）。
  2. **关闭**：`shutdown()` 不再接收新任务，但会把队列里的任务执行完；`shutdownNow()` 不再接收新任务，中断正在执行的线程，并返回队列里还没执行的任务列表。之后可以调用 `awaitTermination` 等待关闭完成。
  3. **线程池状态**：`ctl` 变量的高 3 位存状态，低 29 位存线程数。状态有 `RUNNING → SHUTDOWN / STOP → TIDYING → TERMINATED`。

## 7. execute() vs submit()（FutureTask）

> 代码：[SubmitDemo](code/src/main/java/com/example/juc/pool/SubmitDemo.java#L28)

### Q1：`execute()` 和 `submit()` 有什么区别？`submit` 的原理？

* **满分话术**：
  1. **参数和返回值**：`execute` 只接收 `Runnable`，没有返回值；`submit` 可以接收 `Runnable` 或 `Callable`，返回一个 `Future`，可以拿结果、判断是否完成、取消任务。
  2. **原理**：`submit` 把任务包装成 **`FutureTask`**，然后**调用的还是 `execute`**（源码见 [类注释](code/src/main/java/com/example/juc/pool/SubmitDemo.java#L17)）。`FutureTask` 同时实现了 `Runnable` 和 `Future`：`run()` 执行任务，把结果或异常存进 `outcome` 字段，然后唤醒等在 `get()` 上的线程；`get()` 在任务完成前一直阻塞。
  3. **异常处理差别最大**（面试常问的坑）：
     * `execute` 的任务抛异常：异常抛出到线程里，**打印堆栈，这个工作线程直接死掉**，线程池再补一个新线程（[实验 1](code/src/main/java/com/example/juc/pool/SubmitDemo.java#L34)，能看到线程名变了）；
     * `submit` 的任务抛异常：被 `FutureTask.run` **catch 住存起来，什么都不打印**，只有调用 `future.get()` 时才包装成 `ExecutionException` 抛出（[实验 2](code/src/main/java/com/example/juc/pool/SubmitDemo.java#L44)）。如果没人调 `get`，**异常就“消失”了**。所以用 submit 时，要么一定调 `get`，要么在任务内部自己 try-catch 打日志。
  4. **`get` 一定要带超时**：`get(timeout, unit)`，否则任务卡住时调用方也会一直卡住；超时后可以 `cancel(true)` 中断任务（[实验 3](code/src/main/java/com/example/juc/pool/SubmitDemo.java#L64)）。
* **进阶**：`Future` 只能阻塞等结果；JDK 8 的 `CompletableFuture` 支持回调和编排（`thenApply`、`thenCombine`、`allOf`），并行调用多个下游服务时更好用，记得传入自定义线程池，否则默认用公共的 `ForkJoinPool`。

## 8. CountDownLatch、Semaphore、CyclicBarrier

> 代码：[SyncToolsDemo](code/src/main/java/com/example/juc/tool/SyncToolsDemo.java#L15)

### Q1：CountDownLatch、Semaphore、CyclicBarrier 分别怎么用？原理是什么？

* **满分话术**：
  | 工具 | 作用 | 场景 | 原理 | 代码 |
  |---|---|---|---|---|
  | `CountDownLatch` | **一个线程等 N 个线程**完成 | 并行调用 3 个下游服务，都返回后汇总 | AQS state 初始为 N，`countDown` 减 1，`await` 等到 0；**一次性**，不能重置 | [实验 1](code/src/main/java/com/example/juc/tool/SyncToolsDemo.java#L28) |
  | `Semaphore` | **限制同时访问**的线程数 | 下游接口最多承受 2 个并发、数据库连接数限制 | AQS state 是许可数，`acquire` 减 1（不够就排队），`release` 加 1 | [实验 2](code/src/main/java/com/example/juc/tool/SyncToolsDemo.java#L55) |

## 9. ThreadLocal 与内存泄漏

> 代码：[ThreadLocalDemo](code/src/main/java/com/example/juc/threadlocal/ThreadLocalDemo.java#L24)，在 Spring Boot 项目里的实际用法见 [05-springboot 的 UserContext](../05-springboot/code/src/main/java/com/example/demo/web/UserContext.java#L14)

### Q1：ThreadLocal 的原理是什么？（高频）

* **满分话术**：ThreadLocal 为每个线程提供一份**独立的变量副本**。关键在于值**不是存在 ThreadLocal 里**，而是存在**每个 `Thread` 对象自己的 `threadLocals` 字段**（一个 `ThreadLocalMap`）里。`threadLocal.set(v)` 等于 `Thread.currentThread().threadLocals.set(this, v)`：key 是 ThreadLocal 对象本身，value 是要存的值。不同线程访问的是各自的 Map，所以互不干扰，不需要加锁（结构图见 [类注释](code/src/main/java/com/example/juc/threadlocal/ThreadLocalDemo.java#L12)）。`ThreadLocalMap` 用**开放地址法**（线性探测）解决冲突，而不是 HashMap 的链表。
* **典型用途**：保存当前登录用户（拦截器里 set，业务代码里 get）、数据库连接和事务（Spring 的 `TransactionSynchronizationManager`）、`SimpleDateFormat` 这类线程不安全的对象。

### Q2：ThreadLocal 为什么会内存泄漏？为什么 key 要用弱引用？（高频）

* **满分话术**：
  1. **引用链**：`Thread → ThreadLocalMap → Entry → value`。Entry 继承 `WeakReference`，**key（ThreadLocal 对象）是弱引用，value 是强引用**。
  2. **泄漏过程**：外部不再引用某个 ThreadLocal 后，GC 会回收它，Entry 的 key 变成 null；但 value 还被线程强引用着，**回收不掉**，而且再也没法通过 ThreadLocal 访问到它。线程池里的线程一直存活，这块内存就一直泄漏。[实验 2](code/src/main/java/com/example/juc/threadlocal/ThreadLocalDemo.java#L66) 用反射看到：ThreadLocal 置 null 并 GC 后，`Entry.key = null`，但 10MB 的 value 还在。
  3. **为什么 key 还要用弱引用**：如果 key 是强引用，ThreadLocal 对象本身也回收不掉，泄漏更多。用弱引用至少 key 能被回收，而且 ThreadLocalMap 在之后的 `set`/`get`/`remove` 里遇到 key 为 null 的 Entry 会顺手清理（`expungeStaleEntry`）。但这是“碰巧”清理，不能指望。
  4. **正确做法**：**用完在 finally 里调用 `remove()`**（[第 48 行](code/src/main/java/com/example/juc/threadlocal/ThreadLocalDemo.java#L48)）。在 Web 项目里通常放在拦截器的 `afterCompletion` 里。

### Q3：线程池里使用 ThreadLocal 有什么问题？父子线程怎么传值？

* **满分话术**：
  1. **串号**：线程池的线程会被复用，上一个任务 set 的值没有 remove，下一个任务就读到了（[实验 1](code/src/main/java/com/example/juc/threadlocal/ThreadLocalDemo.java#L35)：请求 2 没登录，却读到了张三）。在 Web 服务里就是 A 用户看到 B 用户的数据，是严重的安全事故。
  2. **父子线程传值**：`InheritableThreadLocal` 在**创建子线程时**把父线程的值复制过去。但线程池的线程是提前创建、反复复用的，之后父线程再修改的值传不过去（[实验 3](code/src/main/java/com/example/juc/threadlocal/ThreadLocalDemo.java#L109)）。这种场景用阿里开源的 `TransmittableThreadLocal`，它在**提交任务时**捕获值、执行时回放。

## 10. 手撕：交替打印与死锁

> 代码：[AlternatePrintSync](code/src/main/java/com/example/juc/print/AlternatePrintSync.java#L14)、[AlternatePrintCondition](code/src/main/java/com/example/juc/print/AlternatePrintCondition.java#L13)、[AlternatePrintSemaphore](code/src/main/java/com/example/juc/print/AlternatePrintSemaphore.java#L11)、[DeadlockDemo](code/src/main/java/com/example/juc/deadlock/DeadlockDemo.java#L24)

### Q1：手写两个线程交替打印 1~100（小红书二面原题）

* **标准答案**：[AlternatePrintSync](code/src/main/java/com/example/juc/print/AlternatePrintSync.java#L14)（学习路线里的原题代码），要能在记事本里默写出来。三个易错点：
  1. `wait`/`notifyAll` 必须在 `synchronized` 块里、对**同一个锁对象**调用（[第 49 行](code/src/main/java/com/example/juc/print/AlternatePrintSync.java#L49)）；
  2. 被唤醒后要**重新判断**是否轮到自己，这里外层的 `while (true)` 起到了这个作用，防止虚假唤醒；
  3. 结束时**先 `notifyAll` 再 `return`**（[第 36 行](code/src/main/java/com/example/juc/print/AlternatePrintSync.java#L36)），否则对方线程永远 wait，程序无法退出（README 动手实验 1）。
* **第二种解法**：[Semaphore 版](code/src/main/java/com/example/juc/print/AlternatePrintSemaphore.java#L25)，两个信号量当“接力棒”，代码最短，每个线程循环 50 次，不需要额外的退出判断。
* **变形题**：三个线程循环打印 ABC，用 [ReentrantLock + 3 个 Condition](code/src/main/java/com/example/juc/print/AlternatePrintCondition.java#L22)，打印完只 `signal` 下一个线程（[第 35 行](code/src/main/java/com/example/juc/print/AlternatePrintCondition.java#L35)），比 `notifyAll` 少了无效竞争；条件判断必须用 `while`（[第 27 行](code/src/main/java/com/example/juc/print/AlternatePrintCondition.java#L27)）。

### Q2：什么是死锁？怎么避免？怎么排查？

* **满分话术**：
  1. **定义**：两个或多个线程互相持有对方需要的锁，又都在等对方释放，永远等下去（[DeadlockDemo](code/src/main/java/com/example/juc/deadlock/DeadlockDemo.java#L24)：A 拿着锁 1 等锁 2，B 拿着锁 2 等锁 1）。
  2. **四个必要条件**：互斥、持有并等待、不可剥夺、循环等待。破坏任意一个就不会死锁。
  3. **避免**：最常用的是**固定加锁顺序**（比如转账时总是先锁 id 小的账户），破坏循环等待；或者用 `tryLock(timeout)`，拿不到就释放已有的锁过会儿重试，破坏不可剥夺；另外缩小锁范围，避免在持锁时调用外部方法。
  4. **排查**：`jps -l` 找到进程 pid，`jstack <pid>`，输出末尾有 `Found one Java-level deadlock`，列出每个线程持有哪把锁、在等哪把锁，以及代码行号。程序内部也可以用 `ThreadMXBean.findDeadlockedThreads()` 检测（[第 51 行](code/src/main/java/com/example/juc/deadlock/DeadlockDemo.java#L51)），jstack 背后用的就是这套接口。完整的排查练习见 [03-jvm](../03-jvm/code/README.md)。

## 高频追问速查

| 问题 | 一句话答案 |
|---|---|
| 创建线程有几种方式？ | 继承 Thread、实现 Runnable、实现 Callable + FutureTask、线程池；本质上只有 `new Thread().start()` 一种，其他都是提供任务 |
| `notify` 和 `notifyAll` 的区别？ | `notify` 随机唤醒一个等待者，可能唤醒的不是你想要的，导致所有线程都在等；一般用 `notifyAll` 或 Condition 精准唤醒 |
| `yield` 有什么用？ | 提示调度器让出 CPU，线程从运行回到就绪，状态仍是 RUNNABLE，不释放锁，不保证生效 |
| 守护线程是什么？ | 为其他线程服务的后台线程（如 GC 线程），所有非守护线程结束后 JVM 直接退出，不等守护线程 |
| synchronized 能修饰构造器吗？ | 不能，构造期间对象还没发布，不存在并发问题 |
| 读写锁 `ReentrantReadWriteLock`？ | 读读共享、读写互斥、写写互斥，适合读多写少；state 高 16 位记读锁、低 16 位记写锁；写锁可以降级为读锁，读锁不能升级 |
| `StampedLock` 的优势？ | 支持乐观读：读的时候不加锁只拿一个版本戳，读完校验版本有没有变，变了再升级为悲观读锁；不可重入 |
| 阻塞队列有哪些？ | `ArrayBlockingQueue`（数组、有界、一把锁）、`LinkedBlockingQueue`（链表、默认无界、两把锁）、`SynchronousQueue`（不存元素，直接交接）、`PriorityBlockingQueue`、`DelayQueue` |
| 线程池里一个任务抛异常，其他任务受影响吗？ | 不影响，`execute` 的话那个工作线程死掉，线程池补一个新的；`submit` 的话异常被存进 Future |
| 什么是伪共享？ | 多个线程修改同一个 CPU 缓存行（64 字节）上的不同变量，互相让对方缓存失效；用 `@Contended` 或手动填充字段解决 |
| `ConcurrentHashMap` 原理？ | 见 [01-collection 第 6 节](../01-collection/八股.md#6-concurrenthashmap-并发安全原理) |
