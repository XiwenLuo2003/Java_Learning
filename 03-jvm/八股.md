## 1. 运行时数据区

> 代码：[HeapOomDemo](code/src/main/java/com/example/jvm/oom/HeapOomDemo.java#L20)、[StackOverflowDemo](code/src/main/java/com/example/jvm/oom/StackOverflowDemo.java#L12)、[MetaspaceOomDemo](code/src/main/java/com/example/jvm/oom/MetaspaceOomDemo.java#L20)、[DirectMemoryOomDemo](code/src/main/java/com/example/jvm/oom/DirectMemoryOomDemo.java#L18)

### Q1：JVM 运行时数据区有哪些？哪些是线程私有的？哪些会 OOM？（高频）

* **满分话术**：
  | 区域 | 线程 | 存什么 | 异常 | 复现 |
  |---|---|---|---|---|
  | **程序计数器** | 私有 | 当前线程执行到的字节码行号，线程切换回来靠它恢复 | **唯一不会 OOM 的区域** | — |
  | **虚拟机栈** | 私有 | 每次方法调用压入一个**栈帧**：局部变量表、操作数栈、动态链接、方法返回地址 | 递归太深 `StackOverflowError`；线程太多无法再分配栈 `OOM: unable to create native thread` | [StackOverflowDemo](code/src/main/java/com/example/jvm/oom/StackOverflowDemo.java#L12) |
  | **本地方法栈** | 私有 | 为 native 方法服务，HotSpot 里和虚拟机栈合二为一 | 同上 | — |
  | **堆** | 共享 | 几乎所有对象实例和数组，GC 的主要区域 | `OOM: Java heap space` | [HeapOomDemo](code/src/main/java/com/example/jvm/oom/HeapOomDemo.java#L20) |
  | **方法区**（JDK 8+ 实现为**元空间**） | 共享 | 类的元数据（结构、方法、字段）、运行时常量池、JIT 编译后的代码 | `OOM: Metaspace` | [MetaspaceOomDemo](code/src/main/java/com/example/jvm/oom/MetaspaceOomDemo.java#L20) |
  | 直接内存（不属于运行时数据区） | 共享 | NIO `allocateDirect` 在堆外分配 | `OOM: Direct buffer memory` | [DirectMemoryOomDemo](code/src/main/java/com/example/jvm/oom/DirectMemoryOomDemo.java#L18) |

  **记忆口诀**：线程私有的三个（程序计数器、两个栈）随线程生灭，不需要 GC；共享的堆和方法区是 GC 管理的地方。

### Q2：堆的结构是怎样的？

* **满分话术**：基于**分代收集理论**（绝大多数对象朝生夕灭；熬过越多次 GC 的对象越难死），堆分为**新生代**和**老年代**，默认比例 1 : 2（`-XX:NewRatio=2`）。新生代又分为一个 **Eden** 和两个 **Survivor**（From、To），默认 8 : 1 : 1（`-XX:SurvivorRatio=8`）。新对象在 Eden 分配，Minor GC 时把 Eden 和 From 里存活的对象复制到 To，然后两个 Survivor 交换角色，所以任何时刻总有一个 Survivor 是空的（复制算法）。G1 在物理上不再划分连续的新生代和老年代，而是把堆切成很多 Region，每个 Region 逻辑上属于某一代。
* **实测**：[AllocationDemo](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L15) 用 `-Xmn10m -XX:SurvivorRatio=8` 把新生代设成 Eden 8MB + 两个 Survivor 各 1MB，GC 日志的 `def new generation total 9216K` 就是 Eden + 一个 Survivor（另一个永远是空的，不计入可用空间）。

### Q3：为什么用元空间取代永久代？

* **满分话术**：JDK 7 之前方法区用**永久代**实现，它在堆里、大小固定（`-XX:MaxPermSize`），类多了很容易 `OOM: PermGen space`，而且很难确定设多大合适。JDK 8 改成**元空间**，用的是**本地内存**，默认上限只受物理内存限制，减少了 OOM；同时永久代的 GC 效率低，移出堆后 Full GC 也简化了。另外字符串常量池和静态变量在 JDK 7 就已经从永久代移到了堆里。注意元空间不设上限的话，类加载泄漏会吃光物理内存，生产上建议配 `-XX:MaxMetaspaceSize`。

### Q4：栈帧里有什么？`StackOverflowError` 和 OOM 有什么区别？

* **满分话术**：栈帧包括**局部变量表**（方法参数和局部变量，基本类型直接存值，对象存引用）、**操作数栈**（字节码运算的临时区）、**动态链接**（指向运行时常量池里该方法的引用）、**方法返回地址**。`StackOverflowError` 是**单个线程**的栈深度超过限制（递归太深）；栈相关的 OOM 是**创建新线程时**申请不到栈内存。栈帧越大（局部变量越多），同样的 `-Xss` 能递归的深度越浅（[big() 对比 small()](code/src/main/java/com/example/jvm/oom/StackOverflowDemo.java#L23)）。

## 2. 对象创建与内存分配

> 代码：[ObjectLayoutDemo](code/src/main/java/com/example/jvm/memory/ObjectLayoutDemo.java#L21)、[AllocationDemo](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L15)

### Q1：new 一个对象的过程是什么？（高频）

* **满分话术**：
  1. **类加载检查**：检查 `new` 指令的参数能否在常量池定位到类的符号引用，这个类是否已经加载、链接、初始化，没有就先执行类加载（见第 5 节）。
  2. **分配内存**：对象大小在类加载完成后就确定了。分配方式取决于堆是否规整：
     * **指针碰撞**：堆规整（用的是带压缩的收集器，如 Serial、ParNew、G1），已用和空闲内存中间有一个指针，分配就是把指针往后挪对象大小的距离；
     * **空闲列表**：堆不规整（如 CMS 的标记-清除），维护一个空闲块列表，找一块足够大的。
     * **并发安全**：多个线程同时分配会争抢同一个指针，解决办法是 **CAS + 失败重试**，或者 **TLAB**（Thread Local Allocation Buffer，每个线程在 Eden 里预先分一小块私有区域，在自己的 TLAB 里分配不用同步，用完了再 CAS 申请新的，默认开启）。
  3. **初始化零值**：把分配到的内存（不含对象头）都设为零值，所以字段不赋初值也能用（int 是 0，引用是 null）。
  4. **设置对象头**：Mark Word（hashCode、GC 分代年龄、锁状态）和类型指针（指向类元数据）。
  5. **执行 `<init>`**：按代码顺序执行实例变量赋值、实例代码块、构造器。到这一步，对象才算真正创建完成。
  
  其中第 2~5 步不是原子的，这就是 DCL 单例需要 `volatile` 的原因（见 [02-juc 第 3 节](../02-juc/八股.md#3-volatile-与-java-内存模型)）。

### Q2：对象在内存里长什么样？`new Object()` 占多少字节？

* **满分话术**：对象由三部分组成：**对象头**（Mark Word 8 字节 + 类型指针，开启指针压缩时 4 字节；数组还有 4 字节的长度）、**实例数据**（字段，JVM 会按 long/double → int → short/char → byte/boolean → 引用的顺序重排，减少空隙）、**对齐填充**（对象大小必须是 8 字节的整数倍）。所以 `new Object()` = 12 字节对象头 + 4 字节填充 = **16 字节**（[第 35 行](code/src/main/java/com/example/jvm/memory/ObjectLayoutDemo.java#L35)，JOL 实测）。64 位 JVM 默认开启**指针压缩**（`-XX:+UseCompressedOops`），把 8 字节的引用压缩成 4 字节，堆小于 32GB 时有效 —— 这也是“堆不要超过 32GB”这条经验的来源。
* **对象的访问方式**：HotSpot 用**直接指针**，栈上的引用直接指向堆里的对象，对象头里再有指针指向类元数据，访问对象只需一次寻址；另一种方式是**句柄**，引用指向句柄池，对象移动时只改句柄，但多一次寻址。

### Q3：对象的内存分配策略？什么时候进入老年代？

* **满分话术**（都在 [AllocationDemo](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L15) 里有实验）：
  1. **对象优先在 Eden 分配**，Eden 不够时触发 **Minor GC**（[minorGc](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L37)：分配了 6MB 后再分配 4MB，Eden 8MB 放不下，触发 GC）。
  2. **大对象直接进入老年代**：需要大量连续内存的对象（长字符串、大数组），避免在 Eden 和 Survivor 之间来回复制。Serial/ParNew 用 `-XX:PretenureSizeThreshold` 控制（[pretenure](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L52)）；G1 里超过 Region 一半的叫 **Humongous 对象**，单独放在连续的 Humongous Region 里。
  3. **长期存活的对象进入老年代**：对象每熬过一次 Minor GC，年龄 +1，达到 `-XX:MaxTenuringThreshold`（默认 15，因为对象头里年龄只有 4 位）就晋升（[tenure](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L64)）。
  4. **动态年龄判定**：Survivor 里相同年龄的对象大小总和超过 Survivor 的一半，年龄 ≥ 该年龄的对象直接晋升，不用等到 15。
  5. **空间分配担保**：Minor GC 后存活对象 Survivor 放不下，就由老年代“担保”直接放进去（[minorGc](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L37) 里 3 个 2MB 数组放不进 1MB 的 Survivor，全部进了老年代）。如果老年代也放不下，就触发 Full GC。

## 3. 判断垃圾与垃圾回收算法

> 代码：[ReachabilityDemo](code/src/main/java/com/example/jvm/gc/ReachabilityDemo.java#L16)、[ReferenceDemo](code/src/main/java/com/example/jvm/gc/ReferenceDemo.java#L20)

### Q1：怎么判断对象是垃圾？哪些对象可以作为 GC Roots？（高频）

* **满分话术**：
  1. **引用计数法**：每个对象有一个计数器，被引用 +1，引用失效 -1，为 0 就是垃圾。实现简单，但**无法解决循环引用**：a 引用 b、b 引用 a，外部都不引用了，计数还是 1。Java 不用它（Python 用，配合额外的循环检测）。
  2. **可达性分析**（Java 用的）：从一组 **GC Roots** 出发沿引用链遍历，走不到的对象就是垃圾。循环引用的两个对象只要从 Roots 走不到，就一起被回收（[实验 1](code/src/main/java/com/example/jvm/gc/ReachabilityDemo.java#L30)：a ⇄ b 循环引用，GC 后被回收了）。
  3. **GC Roots**：虚拟机栈中局部变量引用的对象、方法区中**类静态变量**引用的对象（[实验 2](code/src/main/java/com/example/jvm/gc/ReachabilityDemo.java#L40)）、方法区中常量引用的对象、本地方法栈中 JNI 引用的对象、被 `synchronized` 持有的对象、JVM 内部引用（基本类型的 Class 对象、系统类加载器、常驻异常对象）。
  4. **最常见的内存泄漏**：对象被静态集合之类的 GC Root 一直引用着，业务上已经不用了，但 GC 认为它还活着（[HeapOomDemo 的 CACHE](code/src/main/java/com/example/jvm/oom/HeapOomDemo.java#L23)）。

### Q2：强、软、弱、虚四种引用的区别？

* **满分话术**（[ReferenceDemo](code/src/main/java/com/example/jvm/gc/ReferenceDemo.java#L20)，`-Xmx20m` 下实测）：
  | 引用 | 回收时机 | 用途 |
  |---|---|---|
  | **强引用** `Object o = new Object()` | 只要可达，宁可 OOM 也不回收 | 平时写的都是 |
  | **软引用** `SoftReference` | **内存不够**（即将 OOM）时才回收（[第 26 行](code/src/main/java/com/example/jvm/gc/ReferenceDemo.java#L26)：8MB 软引用在 GC 后还在，再分配 12MB 时被清掉了） | 内存敏感的缓存，如图片缓存 |
  | **弱引用** `WeakReference` | **只要发生 GC** 就回收 | `ThreadLocalMap` 的 key、`WeakHashMap` |
  | **虚引用** `PhantomReference` | 随时可能被回收，`get()` 永远返回 null；对象被回收后虚引用进入 `ReferenceQueue`（[第 44 行](code/src/main/java/com/example/jvm/gc/ReferenceDemo.java#L44)） | 跟踪对象回收，做资源清理：`DirectByteBuffer` 的 `Cleaner` 就靠它释放堆外内存 |

### Q3：垃圾回收算法有哪些？

* **满分话术**：
  | 算法 | 过程 | 优点 | 缺点 | 用在 |
  |---|---|---|---|---|
  | **标记-清除** | 标记存活对象，清除未标记的 | 简单，不移动对象 | **内存碎片**；对象多时效率低 | CMS 老年代 |
  | **标记-复制** | 内存分两块，把存活对象复制到另一块，整块清空原来的 | 没有碎片，分配用指针碰撞，存活对象少时很快 | 浪费一半空间；存活对象多时复制开销大 | 新生代（Eden + 2 个 Survivor 只浪费 10%） |
  | **标记-整理** | 标记后把存活对象向一端移动，清掉边界外的 | 没有碎片，不浪费空间 | 移动对象要更新所有引用，必须暂停用户线程 | Serial Old、Parallel Old |
  | **分代收集** | 新生代存活率低用复制，老年代存活率高用标记-清除或标记-整理 | 扬长避短 | — | 几乎所有收集器 |

### Q4：Minor GC、Major GC、Full GC 的区别？什么时候触发 Full GC？什么是 STW？

* **满分话术**：
  1. **Minor GC / Young GC**：只回收新生代，Eden 满了触发，频繁但很快。
  2. **Major GC / Old GC**：只回收老年代，只有 CMS 有单独的老年代收集。
  3. **Mixed GC**：G1 特有，回收整个新生代 + 部分老年代 Region。
  4. **Full GC**：回收整个堆和方法区，停顿最长。触发条件：老年代空间不足（包括晋升失败、大对象放不下）、元空间不足、调用 `System.gc()`（只是建议）、CMS 并发失败、G1 回收速度跟不上分配速度。
  5. **STW（Stop The World）**：GC 时暂停所有用户线程，因为可达性分析需要一个**一致的快照**，不能一边分析一边改引用。线程只在**安全点**（方法调用、循环跳转、异常跳转等位置）停下来。所有收集器都有 STW，优化的方向是让它更短。

## 4. 垃圾收集器：CMS、G1、ZGC

> 代码：[AllocationDemo](code/src/main/java/com/example/jvm/gc/AllocationDemo.java#L15)（去掉 `-XX:+UseSerialGC` 就是 JDK 17 默认的 G1，对比两种日志）

### Q1：有哪些垃圾收集器？

* **满分话术**：
  | 收集器 | 回收区域 | 算法 | 特点 |
  |---|---|---|---|
  | Serial / Serial Old | 新生代 / 老年代 | 复制 / 标记-整理 | 单线程，STW；客户端、小内存场景 |
  | ParNew | 新生代 | 复制 | Serial 的多线程版，**CMS 的标准搭档**（Parallel Scavenge 不能和 CMS 配合） |
  | Parallel Scavenge / Parallel Old | 新生代 / 老年代 | 复制 / 标记-整理 | 多线程，关注**吞吐量**，**JDK 8 默认** |
  | **CMS** | 老年代 | 标记-清除 | 关注**低停顿**，并发标记和清除；JDK 9 废弃、**JDK 14 移除** |
  | **G1** | 整个堆 | Region + 复制 / 标记-整理 | 可预测停顿，**JDK 9 起默认** |
  | **ZGC** | 整个堆 | 染色指针 + 读屏障 | 停顿 < 1ms（JDK 16 后），与堆大小无关，JDK 15 正式可用 |

  查看当前用的收集器：`java -XX:+PrintCommandLineFlags -version`，或者 `jcmd <pid> VM.flags`。

### Q2：CMS 的工作流程和缺点？（高频）

* **满分话术**：
  1. **四个阶段**：
     * **初始标记**（STW）：只标记 GC Roots **直接关联**的对象，很快；
     * **并发标记**：和用户线程一起运行，从这些对象出发遍历整个引用链，耗时最长但不停顿；
     * **重新标记**（STW）：修正并发标记期间用户线程改动的引用（**增量更新**），比初始标记稍长；
     * **并发清除**：和用户线程一起清除垃圾。
     
     耗时最长的并发标记和并发清除都不停顿用户线程，所以整体停顿很短。
  2. **三个缺点**：
     * **CPU 敏感**：并发阶段占用一部分 CPU（默认 `(核数 + 3) / 4` 个线程），核数少时对用户程序影响大；
     * **浮动垃圾 + 并发失败**：并发清除时用户线程还在产生新垃圾，只能留到下次；而且必须预留空间给用户线程，老年代用到 92%（`CMSInitiatingOccupancyFraction`）就要开始回收。如果预留空间不够，就发生 **Concurrent Mode Failure**，退化成 Serial Old 单线程 Full GC，停顿非常长；
     * **内存碎片**：标记-清除算法不整理，碎片多了大对象分配不下，提前触发 Full GC（默认 Full GC 时才整理）。
  3. **注意**：JDK 14 已经移除 CMS，本项目用的 JDK 17 跑不了 CMS，面试时说清楚这一点是加分项。

### Q3：G1 的原理？和 CMS 比有什么优势？（高频）

* **满分话术**：
  1. **Region 设计**：把堆切成约 2048 个大小相等的 **Region**（1MB~32MB，2 的幂），每个 Region 可以扮演 Eden、Survivor、Old 或 **Humongous**（存放超过半个 Region 的大对象）。新生代和老年代不再是物理连续的区域，而是一组 Region 的逻辑集合，大小可以动态调整。
  2. **可预测的停顿**：用 `-XX:MaxGCPauseMillis` 设定目标停顿时间（默认 200ms）。G1 跟踪每个 Region 的**回收价值**（能回收多少空间、需要多长时间），维护一个优先列表，每次在停顿目标内**优先回收价值最大的 Region**，这就是 Garbage First 名字的由来。
  3. **回收过程**：
     * **Young GC**：Eden 满了，STW 把存活对象复制到 Survivor 或 Old Region；
     * **并发标记周期**：老年代占用达到阈值（默认堆的 45%，`InitiatingHeapOccupancyPercent`）时启动：初始标记（借 Young GC 的停顿完成）→ 并发标记 → 最终标记（STW，处理 **SATB** 记录）→ 筛选回收（STW，按价值排序，确定要回收的 Region）；
     * **Mixed GC**：回收所有新生代 + 一部分价值最高的老年代 Region，用**复制**算法把存活对象搬到空 Region。
  4. **跨 Region 引用**：每个 Region 有一个 **Remembered Set**，记录其他 Region 指向自己的引用，回收某个 Region 时不用扫描整个堆。
  5. **相比 CMS 的优势**：**停顿可预测**；整体是标记-整理、局部是复制，**没有内存碎片**；不需要预留大量空间应对并发失败；大内存（6GB 以上）下表现更好。代价是 Remembered Set 等结构占用额外内存（约 10%~20%），写屏障也有开销，小内存场景未必比 CMS 好。

### Q4：什么是三色标记？漏标是怎么产生的？CMS 和 G1 分别怎么解决？

* **满分话术**：
  1. **三色**：**白色**（还没访问，标记结束时仍是白色的就是垃圾）、**灰色**（访问过，但它引用的对象还没全部扫完）、**黑色**（它和它引用的对象都扫完了）。
  2. **漏标**：并发标记时用户线程在改引用，同时满足两个条件时，一个存活对象会被错当成垃圾回收：① 黑色对象新增了一个指向白色对象的引用；② 所有灰色对象到这个白色对象的引用被删除了。
  3. **解决**：破坏任意一个条件即可。
     * **CMS 用增量更新**：破坏条件 ①，黑色对象新增引用时记录下来，重新标记阶段把这些黑色对象当作灰色重新扫描；
     * **G1 用 SATB（原始快照）**：破坏条件 ②，删除引用时把被删的旧引用记录下来，按标记开始那一刻的快照来标记，宁可多留一些浮动垃圾，最终标记时处理的量更少、停顿更短。

### Q5：ZGC 有什么特点？怎么选收集器？

* **满分话术**：
  1. **ZGC**：目标是**停顿不超过 1ms**（JDK 16 后），而且停顿时间**不随堆大小增长**，支持 TB 级堆。核心技术是**染色指针**（把标记信息存在 64 位指针的高位，而不是对象头）和**读屏障**（读取引用时检查指针颜色，发现对象已被移动就当场修正指针），使得**对象的移动（整理）也能和用户线程并发进行**，几乎所有阶段都是并发的。JDK 21 加入了分代 ZGC。代价是吞吐量比 G1 略低。
  2. **怎么选**：
     * 小内存、单核：Serial；
     * 追求吞吐量的后台批处理：Parallel；
     * 一般 Web 服务：**G1**（JDK 9+ 默认，大多数情况不用改）；
     * 超大堆、对延迟极其敏感（如交易系统）：ZGC。

## 5. 类加载机制

> 代码：[ClassInitDemo](code/src/main/java/com/example/jvm/classload/ClassInitDemo.java#L12)、[ClassLoaderDemo](code/src/main/java/com/example/jvm/classload/ClassLoaderDemo.java#L21)

### Q1：类加载的过程是什么？什么时候会触发类的初始化？

* **满分话术**：
  1. **生命周期**：加载 → **链接**（验证 → 准备 → 解析）→ 初始化 → 使用 → 卸载。
     * **加载**：通过全限定名找到字节码（class 文件、jar、网络、动态生成都行），在方法区生成类的元数据，在堆里生成 `Class` 对象；
     * **验证**：检查字节码格式、语义是否合法，防止恶意字节码；
     * **准备**：为**静态变量**分配内存并设为**零值**（`static int a = 1` 此时 a 是 0）；但 `static final` 的编译期常量在这一步就直接赋值；
     * **解析**：把常量池里的符号引用替换为直接引用（内存地址）；
     * **初始化**：执行 `<clinit>`，即按代码顺序执行静态变量赋值和 `static` 块。**父类的 `<clinit>` 先执行**；JVM 保证多线程下只执行一次（所以静态内部类单例是线程安全的）。
  2. **主动使用才触发初始化**：`new`、读写静态字段（编译期常量除外）、调用静态方法、反射、初始化子类时先初始化父类、`main` 所在的类。
  3. **被动引用不触发**（[ClassInitDemo](code/src/main/java/com/example/jvm/classload/ClassInitDemo.java#L45)）：读取编译期常量（编译时已经内联，[第 47 行](code/src/main/java/com/example/jvm/classload/ClassInitDemo.java#L47)）、创建该类的数组（[第 50 行](code/src/main/java/com/example/jvm/classload/ClassInitDemo.java#L50)）、通过子类读父类的静态字段只初始化父类（[第 54 行](code/src/main/java/com/example/jvm/classload/ClassInitDemo.java#L54)）。
  4. **`new Child()` 的完整顺序**：父类静态块 → 子类静态块 →（每次 new 时）父类实例块 → 父类构造器 → 子类实例块 → 子类构造器。静态部分只执行一次（[第 57 行和第 60 行对比](code/src/main/java/com/example/jvm/classload/ClassInitDemo.java#L57)）。

### Q2：什么是双亲委派？为什么要这么设计？怎么打破？（高频）

* **满分话术**：
  1. **类加载器层级**（JDK 9+，[实验 1](code/src/main/java/com/example/jvm/classload/ClassLoaderDemo.java#L66)）：**启动类加载器**（Bootstrap，C++ 实现，Java 里拿到的是 null，加载 `java.base` 等核心模块）→ **平台类加载器**（Platform，JDK 8 叫扩展类加载器）→ **应用类加载器**（App，加载 classpath 上我们写的类）→ 自定义类加载器。
  2. **双亲委派**：一个类加载器收到加载请求时，先查自己加载过没有，没有就**委托给父加载器**，层层向上直到启动类加载器；只有父加载器找不到时，才自己去加载（`ClassLoader#loadClass` 源码就是这个逻辑）。
  3. **好处**：
     * **安全**：核心类只会被启动类加载器加载，自己写一个 `java.lang.String` 替换不了它（[实验 2](code/src/main/java/com/example/jvm/classload/ClassLoaderDemo.java#L78)：自定义加载器加载 String，拿到的还是同一个 Class）；而且 JVM 直接禁止定义 `java.*` 包下的类（[第 83 行](code/src/main/java/com/example/jvm/classload/ClassLoaderDemo.java#L83)，抛 `SecurityException`）；
     * **避免重复加载**：父加载器加载过的类，子加载器不会再加载一遍。
  4. **类的唯一性 = 类加载器 + 全限定名**：同一份字节码被两个加载器加载，就是两个不同的类，`instanceof` 为 false，强转报 `ClassCastException`（[实验 3](code/src/main/java/com/example/jvm/classload/ClassLoaderDemo.java#L93)）。
  5. **怎么打破**：自定义类加载器**重写 `loadClass`**（而不是只重写 `findClass`），不先委托父加载器（[IsolatedLoader](code/src/main/java/com/example/jvm/classload/ClassLoaderDemo.java#L32)）。典型场景：
     * **Tomcat**：每个 Web 应用一个 `WebappClassLoader`，优先加载自己 `WEB-INF` 下的类，两个应用可以用同一个库的不同版本，互相隔离；
     * **JDBC SPI**：`DriverManager` 由启动类加载器加载，但具体驱动在 classpath 上，启动类加载器加载不到，于是用**线程上下文类加载器**（`Thread.getContextClassLoader()`）反向委托应用类加载器去加载；
     * **热部署**：每次更新代码就换一个新的类加载器重新加载。

## 6. OOM 场景与线上排查

> 代码：[oom 包](code/src/main/java/com/example/jvm/oom/HeapOomDemo.java#L20)、[TroubleshootTarget](code/src/main/java/com/example/jvm/troubleshoot/TroubleshootTarget.java#L15)，完整的排查步骤见 [README 的“线上排查实操”](code/README.md#线上排查实操用-troubleshoottarget)

### Q1：常见的 OOM 有哪些？分别是什么原因？（高频）

* **满分话术**：
  | 报错信息 | 原因 | 典型场景 | 复现 |
  |---|---|---|---|
  | `Java heap space` | 堆满了 | 一次查全表、本地缓存无上限、集合只加不删（内存泄漏）、大文件一次读入 | [HeapOomDemo](code/src/main/java/com/example/jvm/oom/HeapOomDemo.java#L29) |
  | `GC overhead limit exceeded` | 98% 的时间在 GC，却只回收了不到 2% 的内存 | 同上，堆快满了但还没完全满 | — |
  | `Metaspace` | 类元数据太多 | CGLIB / 动态代理 / Groovy 脚本不断生成新类 | [MetaspaceOomDemo](code/src/main/java/com/example/jvm/oom/MetaspaceOomDemo.java#L52) |
  | `Direct buffer memory` | 堆外内存超过上限 | NIO、Netty 的 ByteBuffer 没释放 | [DirectMemoryOomDemo](code/src/main/java/com/example/jvm/oom/DirectMemoryOomDemo.java#L24) |
  | `unable to create native thread` | 线程数超过系统限制 | 无限创建线程（如 `newCachedThreadPool`） | 会拖垮机器，不复现 |
  | `StackOverflowError`（不是 OOM，但常一起问） | 栈深度超过限制 | 递归没有终止条件、循环引用的 `toString` | [StackOverflowDemo](code/src/main/java/com/example/jvm/oom/StackOverflowDemo.java#L17) |

### Q2：线上发生 OOM 怎么排查？（高频）

* **满分话术**：
  1. **提前准备**：生产环境一定加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=...`，OOM 时自动导出堆快照（[HeapOomDemo 的 VM 参数](code/src/main/java/com/example/jvm/oom/HeapOomDemo.java#L20)）；同时开 GC 日志。
  2. **先止血**：重启或摘掉问题实例的流量，保住服务；有 dump 文件就先拷出来。
  3. **看报错类型**：是堆、元空间还是直接内存，对应不同的方向（见 Q1）。
  4. **分析堆快照**：用 MAT / VisualVM / IDEA 打开 hprof，看**支配树**（Dominator Tree）和 **Biggest Objects**，找出占内存最多的对象，再看它的 **GC Root 引用链**，定位是哪段代码一直拉着它。比如 [TroubleshootTarget](code/src/main/java/com/example/jvm/troubleshoot/TroubleshootTarget.java#L52) 里是静态 `LEAKY_CACHE` 拉着几百个 `byte[]`。
  5. **区分泄漏和溢出**：如果是**内存泄漏**（对象不该活却一直活着），修代码；如果是**内存溢出**（对象都该活，只是确实不够），调大堆或者优化数据结构、分批处理。
  6. **没有 dump 时**：`jstat -gcutil <pid> 1000` 看老年代使用率是不是 Full GC 后也降不下来；`jmap -histo:live <pid>` 看哪种对象最多。

### Q3：Java 进程 CPU 100% 怎么排查？（小红书一二面原题）

* **满分话术**（和 [java.md](../java.md) 里的标准话术一致）：
  1. `top` 找到占 CPU 最高的 Java 进程 PID；
  2. `top -Hp <PID>` 找到这个进程里占 CPU 最高的线程 TID；
  3. `printf "%x\n" <TID>` 把线程 ID 转成十六进制；
  4. `jstack <PID> | grep -A 30 <十六进制TID>`，jstack 里线程的 `nid=0x...` 就是这个十六进制 ID，看它的堆栈：
     * 停在业务代码：**死循环、正则灾难性回溯、大量计算或序列化**（[TroubleshootTarget 的 hot-loop 线程](code/src/main/java/com/example/jvm/troubleshoot/TroubleshootTarget.java#L40)）；
     * 是 `GC task thread` 或 `VM Thread`：说明在**频繁 GC**，接着用 `jstat -gcutil` 看 GC 次数，用 `jmap` 排查内存泄漏。
  5. 多 jstack 几次（间隔几秒），一直停在同一个地方的才是问题点。
  6. 也可以直接用 Arthas 的 `thread -n 3`，一步列出最耗 CPU 的 3 个线程和堆栈。

### Q4：频繁 Full GC 怎么排查？

* **满分话术**：
  1. `jstat -gcutil <pid> 1000` 观察：`FGC` 次数快速增长，看 Full GC 后老年代（`O`）能不能降下来。
  2. **降不下来**：内存泄漏，按 Q2 分析堆快照。
  3. **能降下来但很快又满**：对象晋升太快。可能是新生代太小、Survivor 放不下导致对象过早晋升，或者有大对象直接进老年代；调整 `-Xmn`、`SurvivorRatio`，或者找出大对象的来源（比如一次查询返回几十万行）。
  4. **元空间满**：类加载过多，看 `jstat -gc` 的 `MU`/`MC`。
  5. **代码里调了 `System.gc()`**：搜代码，或加 `-XX:+DisableExplicitGC`（注意会影响 NIO 堆外内存的回收）。

### Q5：常用的排查命令和 JVM 参数？

* **满分话术**（每条命令在 [README 的排查实操](code/README.md#线上排查实操用-troubleshoottarget) 里都有对应练习）：
  | 命令 | 作用 |
  |---|---|
  | `jps -l` | 列出 Java 进程和主类 |
  | `jstat -gcutil <pid> 1000` | 每秒打印各区使用率、GC 次数和耗时 |
  | `jmap -histo:live <pid>` | 类直方图，哪种对象最多（会触发 Full GC） |
  | `jmap -dump:live,format=b,file=x.hprof <pid>` | 导出堆快照 |
  | `jstack <pid>` | 线程堆栈，查死锁、CPU 高、线程卡住 |
  | `jcmd <pid> VM.flags` / `GC.heap_info` / `Thread.print` | 万能命令，可替代上面多数命令 |
  | `jinfo -flags <pid>` | 查看 JVM 参数 |
  | Arthas `dashboard` / `thread -n 3` / `thread -b` / `trace` / `watch` | 在线诊断，不用重启 |

  | 参数 | 作用 |
  |---|---|
  | `-Xms` / `-Xmx` | 初始 / 最大堆，生产上设成一样，避免运行时扩缩容 |
  | `-Xmn` | 新生代大小 |
  | `-Xss` | 每个线程的栈大小 |
  | `-XX:MaxMetaspaceSize` | 元空间上限 |
  | `-XX:+UseG1GC` / `-XX:MaxGCPauseMillis` | 使用 G1 / 目标停顿时间 |
  | `-XX:+HeapDumpOnOutOfMemoryError` / `-XX:HeapDumpPath` | OOM 时自动导出堆快照 |
  | `-Xlog:gc*:file=gc.log` | GC 日志（JDK 9+；JDK 8 是 `-XX:+PrintGCDetails -Xloggc:gc.log`） |

## 高频追问速查

| 问题 | 一句话答案 |
|---|---|
| 对象一定分配在堆上吗？ | 不一定。JIT 的**逃逸分析**发现对象不会逃出方法时，可以**标量替换**（拆成局部变量放在栈上）；还可以据此做锁消除 |
| 字符串常量池在哪？ | JDK 7 起在堆里（之前在永久代） |
| 为什么新生代要两个 Survivor？ | 复制算法需要一块空的目标区；只有一个的话，Eden 和 Survivor 的存活对象没地方复制，会产生碎片 |
| 为什么分代年龄最大是 15？ | 对象头 Mark Word 里年龄只占 4 位 |
| 堆为什么一般不超过 32GB？ | 超过 32GB 指针压缩失效，引用从 4 字节变 8 字节，浪费内存 |
| 安全点是什么？ | 线程能安全停下来做 GC 的位置（方法调用、循环跳转、异常跳转），STW 时所有线程跑到最近的安全点停下 |
| `finalize()` 能救活对象吗？ | 能，但只能救一次，执行时机不确定，JDK 9 已废弃，不要用；资源释放用 try-with-resources 或 `Cleaner` |
| JIT 是什么？ | 热点代码（被多次调用的方法、循环）由即时编译器编译成本地机器码，之后直接执行，比解释执行快得多；HotSpot 有 C1（快速编译）和 C2（深度优化）两个编译器 |
| `-Xss` 设太大有什么问题？ | 每个线程占用更多内存，能创建的线程数变少 |
| 怎么查看 JVM 默认参数？ | `java -XX:+PrintFlagsFinal -version`，或 `jcmd <pid> VM.flags` |
