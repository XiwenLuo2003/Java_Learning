## 1. TCP

> 代码：[TcpHandshakeDemo](code/src/main/java/com/example/net/TcpHandshakeDemo.java#L9)

### Q1：三次握手每一步在干什么？为什么不能两次？

* **满分话术**（[第 11 行起](code/src/main/java/com/example/net/TcpHandshakeDemo.java#L11)）：
  1. 客户端发 **SYN**，seq=x，状态 SYN_SENT。
  2. 服务端回 **SYN+ACK**，seq=y，ack=x+1，状态 SYN_RCVD。这一步服务端要为这条连接分配资源。
  3. 客户端回 **ACK**，ack=y+1，双方进入 ESTABLISHED。
  * 不能两次的原因：服务端一收到 SYN 就分配资源。网络上一个**迟到的旧 SYN** 会让服务端建一条没有客户端的连接。第三次 ACK 用来确认“这个 SYN 是现在这次的”。
  * **SYN Flood**：攻击者只发 SYN 不回 ACK，半连接堆在 SYN_RCVD，正常用户连不上。缓解是 SYN Cookie（状态编进 seq，不占队列）、缩短超时、限流。

### Q2：四次挥手为什么是四次？TIME_WAIT 为什么等 2MSL？

* **满分话术**：
  * 关闭是单向的。A 发 FIN 只表示 A 没有数据了，B 可能还要把剩下的数据发完，所以 B 先 ACK（进入 CLOSE_WAIT），处理完再单独发 FIN。合并不了，所以是四次。
  * **TIME_WAIT** 在主动关闭的一方，等 **2MSL**（MSL 是报文最长存活时间）：
    1. 最后一个 ACK 丢了的话，对方会重发 FIN，自己还在，能再回一次；
    2. 这条连接上迟到的旧报文都会消失，同一个四元组（源 IP、源端口、目的 IP、目的端口）被复用时不会串数据。
  * 短连接很多时，让**客户端**主动关。服务器主动关，TIME_WAIT 会堆在服务器上。
  * **CLOSE_WAIT** 堆高：对方已经 FIN 了，自己的应用没有 close socket。这是代码没关连接，不是内核参数能调好的。

## 2. HTTP 状态码

> 代码：[HttpStatusServer](code/src/main/java/com/example/net/HttpStatusServer.java#L23)。运行 main，控制台会打出一条响应长什么样，以及 6 个状态码。

### Q1：一条 HTTP 响应由什么组成？

* **满分话术**：三块，中间用空行隔开。
  * **状态行**：`HTTP/1.1 200 OK`，版本、状态码、原因短语。
  * **头**：`Content-Type`、`Content-Length`、`Set-Cookie` 这种，一行一个。
  * **空行**，然后是**正文**。HEAD 请求和 204 没有正文。
  * 请求也是同样的结构：请求行（`GET /ok HTTP/1.1`）+ 头 + 空行 + 可选的正文。

### Q2：200、202、401、403、500、502 分别是什么？

* **满分话术**（跑 [HttpStatusServer](code/src/main/java/com/example/net/HttpStatusServer.java#L23)）：

  | 状态码 | 含义 | 什么时候用 |
  |---|---|---|
  | 200 | 成功，正文就是结果 | 普通查询、同步处理完 |
  | 202 Accepted | 已经收下，**还没处理完** | 参数检查通过就返回，耗时工作丢到后台。路线第 7 周的“预检 + 落库返回 202 + 异步调度”就是这个（[accepted](code/src/main/java/com/example/net/HttpStatusServer.java#L26)） |
  | 401 | 没登录 | 没有 token，或者 token 无效 |
  | 403 | 登录了，但没权限 | 普通用户访问管理员接口 |
  | 500 | 服务器自己出错 | 没抓住的异常、空指针 |
  | 502 Bad Gateway | 网关没从上游拿到合法响应 | Nginx 后面的 Java 进程挂了、连不上 |

  * 401 和 403 的差别就在于“认不认识你”和“让不让你做”。502 是上游的问题，500 是自己的问题。504 是上游太慢超时了，和 502 挨着记。

## 3. HTTPS 和 TLS

> 代码：[TlsHandshakeDemo](code/src/main/java/com/example/net/TlsHandshakeDemo.java#L18)。它不拨真实的 TLS 连接，用 JDK 的 RSA、AES-GCM、SHA256withRSA 把三件事做出来。

### Q1：HTTPS 为什么安全？

* **满分话术**：三件事叠在一起。
  1. **对称加密传数据**。AES 快，能加密大块数据。密钥只有两边知道，别人看到的是密文。
  2. **非对称加密传这把对称密钥**。服务端的公钥公开，客户端用公钥把 AES 密钥封上，只有持有私钥的服务端解得开。RSA 一次装不下 1KB（[实验 2](code/src/main/java/com/example/net/TlsHandshakeDemo.java#L40)），所以它只搬 16 字节的 AES 密钥，1MB 的数据交给 AES（[实验 3](code/src/main/java/com/example/net/TlsHandshakeDemo.java#L59)）。
  3. **数字证书防中间人**。只加密不够：中间人可以把自己的公钥冒充成服务端。证书是 CA 用自己的私钥给“服务端公钥 + 域名”签的名。客户端用系统里预装的 CA 公钥验证，对不上就断开（[实验 1](code/src/main/java/com/example/net/TlsHandshakeDemo.java#L32)）。
  * AES-GCM 还带认证标签。密文改 1 个比特，解密直接失败，不只是解出乱码。

### Q2：TLS 握手的顺序？

* **满分话术**（TLS 1.2 的主线；1.3 把往返压成 1-RTT，角色不变）：
  1. 客户端说自己支持的版本和密码套件。
  2. 服务端选定一套，交出证书。
  3. 客户端验证证书（签名、域名、有效期），生成 AES 密钥，用服务端公钥加密后送过去。
  4. 两边各自算出会话密钥，之后的 HTTP 报文全部走这把密钥。
  * 会话恢复（session ticket）让第二次连接不用把这四步重新走完。

## 4. 容器和虚拟机

### Q1：容器和虚拟机差在哪？

* **满分话术**：
  * **虚拟机**带一整套客户机操作系统，Hypervisor 做硬件级隔离。启动按分钟，一个实例按 GB 计内存。隔离强。
  * **容器**和宿主机**共用内核**，只隔离进程看到的视图（Namespace）和能用的资源量（Cgroups）。启动按秒，一个实例按 MB 计。隔离弱于虚拟机：内核漏洞可以打到宿主机。
  * Docker 是容器的一种管理工具。镜像是分层的只读文件系统，容器是镜像加上一层可写层，删容器这层就没了，所以数据要放数据卷。

## 5. Docker 隔离原理

> mall 的部署文件：[docker-compose-env.yml 的 rabbitmq](../repos/mall/document/docker/docker-compose-env.yml#L33)。日志轮转：[daemon-log.json](code/docker/daemon-log.json)。

### Q1：Namespace 和 Cgroups 各管什么？

* **满分话术**：
  * **Namespace 做视图隔离**，让进程觉得自己独占一台机器。面试点三个：
    * **PID**：容器里的 1 号进程在宿主机上只是一个普通进程，容器里 `ps` 看不到宿主机的进程；
    * **NET**：容器有自己的网卡、IP、端口。compose 里的 `5672:5672` 是把宿主机的 5672 转到这个网络命名空间的 5672；
    * **MNT**：容器有自己的挂载点。`/mydata/rabbitmq/data:/var/lib/rabbitmq` 是把宿主机目录挂进容器的挂载命名空间，容器删了数据还在。
    * 另外还有 UTS（主机名）、IPC（信号量）、USER（容器里的 root 可以映射成宿主机的普通用户）。
  * **Cgroups 做资源限制**，不管“看不看得到”，管“能用多少”：CPU 时间片、内存上限、块 IO。内存超了会被 OOM killer 杀掉，而不是挤占宿主机上别的进程到无限制。
  * 一句话：Namespace 隔离看得到什么，Cgroups 限制用得了多少。两者都是 Linux 内核的能力，Docker 只是把它们配好。

### Q2：compose 里这几项分别在干什么？

* **满分话术**（[rabbitmq 服务](../repos/mall/document/docker/docker-compose-env.yml#L33)）：
  * `image`：用哪个镜像。`rabbitmq:3.9.11-management` 带管理台。
  * `ports`：宿主机端口到容器端口。5672 是 AMQP，15672 是管理台。
  * `volumes`：数据放在宿主机，不放在容器的可写层里。
  * 同一个 compose 文件里的服务共用一个网络，可以用服务名当主机名互相访问（`mysql`、`redis`），不走宿主机端口。

## 6. Linux 排查

> 磁盘和 CPU 两条都来自路线第三部分 Q6。CPU 的 Java 靶子是 [TroubleshootTarget](../03-jvm/code/src/main/java/com/example/jvm/troubleshoot/TroubleshootTarget.java#L40)，步骤和 [03-jvm 的排查一节](../03-jvm/code/README.md) 是同一套。

### Q1：磁盘告警到 95%，怎么查？

* **满分话术**：
  1. `df -h` 看哪个挂载点满了。`df -i` 看是不是小文件把 **inode** 耗尽了（磁盘还有空间，但创建不了新文件）。
  2. `du -sh /*` 一层层往下找大目录。Docker 机器再加 `docker system df`，看镜像、容器、数据卷各占多少。
  3. 最常见的是容器标准输出没做轮转，`/var/lib/docker/containers/*/*-json.log` 把盘撑满。
  4. **不要 `rm` 一个还在被写入的日志**。进程拿着文件描述符，删了目录项，空间也不释放。`lsof | grep deleted` 能看到这种“已删除但仍被占用”的文件。用 `truncate -s 0 xxx.log` 清空。镜像用 `docker image prune` 清。
  5. 防复发：Docker 守护进程配上日志上限，[max-size 100m、最多 3 个文件](code/docker/daemon-log.json)。

### Q2：Java 进程 CPU 100%，怎么查？

* **满分话术**：
  1. `top` 找到 CPU 最高的 Java 进程，记下 PID。
  2. `top -Hp <PID>` 找到这个进程里 CPU 最高的线程，记下 TID。
  3. `printf "%x\n" <TID>` 转成十六进制。`jstack` 里的 nid 是十六进制。
  4. `jstack <PID> | grep -A 30 <十六进制 TID>` 看栈。业务死循环、正则回溯，会停在自己的代码上；栈都在 `GC task thread`，就是在频繁 GC，接着 `jstat -gcutil` 和 `jmap` 查堆。
  * 练习用 03-jvm 的 [hot-loop](../03-jvm/code/src/main/java/com/example/jvm/troubleshoot/TroubleshootTarget.java#L40)。这台机器是 Windows 的话，`top` 换成任务管理器，线程栈仍然用 `jstack`。

### Q3：这几个命令各看什么？

* **满分话术**：
  * `top`：CPU、内存、负载，谁在占。
  * `df -h`：挂载点的空间。`df -i`：inode。
  * `du -sh 目录`：这个目录实际占了多少。`df` 和 `du` 对不上时，多半有已删除但未关闭的文件。
  * `lsof -p <PID>`：这个进程打开了哪些文件和 socket。`lsof -i :8080` 看谁占着端口。
  * `ss -lntp`（老系统是 `netstat -lntp`）：谁在监听哪个端口。排查“连不上”时先确认端口到底有没有进程听。
