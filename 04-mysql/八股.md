## 1. SQL 实战

> 代码：[01_sql_practice.sql](code/01_sql_practice.sql)（10 道题，带预期结果）

### Q1：INNER JOIN、LEFT JOIN、RIGHT JOIN 有什么区别？

* **满分话术**：
  * `INNER JOIN` 只返回两张表都能匹配上的行；
  * `LEFT JOIN` 保留左表全部行，右表匹配不上的列补 NULL；`RIGHT JOIN` 反过来，实际开发一般统一写成 LEFT JOIN（[题 1](code/01_sql_practice.sql#L8)）。
  * **易错点**：LEFT JOIN 时，右表的过滤条件写在 `ON` 里只影响“能不能匹配上”，左表行全部保留；写在 `WHERE` 里是连接完成后再过滤，补出来的 NULL 行会被过滤掉，LEFT JOIN 就退化成了 INNER JOIN（[题 1.4](code/01_sql_practice.sql#L32)）。

### Q2：WHERE 和 HAVING 有什么区别？SQL 的执行顺序是什么？

* **满分话术**：
  * `WHERE` 在**分组前**过滤行，不能使用聚合函数；`HAVING` 在**分组后**过滤组，可以使用 `COUNT`、`SUM` 等聚合函数。能用 WHERE 提前过滤的条件就不要放到 HAVING，减少参与分组的数据量（[题 2](code/01_sql_practice.sql#L48)、[题 7](code/01_sql_practice.sql#L125)）。
  * 逻辑执行顺序：`FROM → ON → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`。这也解释了为什么 WHERE 里不能用 SELECT 中定义的别名，而 ORDER BY 里可以。

### Q3：`COUNT(*)`、`COUNT(1)`、`COUNT(列)` 有什么区别？

* **满分话术**：`COUNT(*)` 和 `COUNT(1)` 都是统计行数，包括 NULL，InnoDB 对两者的处理完全一样，没有性能差别；`COUNT(列)` 只统计该列**不为 NULL** 的行数，`COUNT(DISTINCT 列)` 再去重（[题 3](code/01_sql_practice.sql#L64)）。InnoDB 执行 `COUNT(*)` 会选择**最小的二级索引**来扫描，因为它比聚簇索引小得多（[05 实验 4](code/05_slow_sql.sql#L76)）。

### Q4：窗口函数用过吗？`ROW_NUMBER`、`RANK`、`DENSE_RANK` 有什么区别？

* **满分话术**：
  * 窗口函数是 MySQL 8.0 的功能，和 GROUP BY 的区别是**不会把多行合并成一行**，而是给每一行附加一个基于“窗口”计算的值。语法是 `函数() OVER (PARTITION BY 分组 ORDER BY 排序)`。
  * 三个排名函数的区别（[题 5](code/01_sql_practice.sql#L98)）：`ROW_NUMBER` 连续编号，并列也分先后（1 2 3 4）；`RANK` 并列同名次，后面跳号（1 2 2 4）；`DENSE_RANK` 并列同名次，后面不跳号（1 2 2 3）。
  * 常见用法：
    * **分组 Top N**：每个部门薪资最高的人、每个用户最近一笔订单，先 `ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)` 编号，再取 `rn = 1`（[题 4](code/01_sql_practice.sql#L73)、[题 8](code/01_sql_practice.sql#L136)）；
    * **累计值**：`SUM(x) OVER (ORDER BY 日期)`（[题 9](code/01_sql_practice.sql#L151)）；
    * **连续 N 天**：日期减去组内序号，连续的日期会得到同一个值，再按这个值分组计数（[题 10](code/01_sql_practice.sql#L170)）。

## 2. 索引底层：B+ 树

> 代码：[02_index.sql 实验 1](code/02_index.sql#L17)

### Q1：MySQL 索引为什么用 B+ 树？为什么不用二叉树、红黑树、B 树、Hash？

* **满分话术**：核心目标是**减少磁盘 IO**，同时**支持范围查询**。
  * **二叉搜索树 / 红黑树**：每个节点只有两个分叉，千万数据树高二十多层，每层一次磁盘 IO，太慢；普通二叉树在有序插入时还会退化成链表。
  * **Hash 索引**：等值查询是 O(1)，但不支持范围查询和排序，也不支持最左前缀。
  * **B 树**：多路平衡树，但每个节点都存整行数据，一页能放的键少，树就更高；范围查询需要中序遍历，在不同层之间来回跳。
  * **B+ 树**：非叶子节点**只存键和页指针**，一个 16KB 的页能放上千个键，扇出极大，3 层就能存两千万行；**数据全在叶子节点**，每次查询路径长度一样，性能稳定；叶子节点用**双向链表**串起来，范围查询和排序找到起点顺着链表扫就行。

### Q2：一棵 3 层 B+ 树大概能存多少数据？

* **满分话术**（[实验 1](code/02_index.sql#L17)）：InnoDB 一页 16KB。非叶子节点存“主键 + 页指针”，BIGINT 主键 8 字节加指针 6 字节共 14 字节，一页约存 16384 / 14 ≈ 1170 个指针。假设一行数据 1KB，叶子节点一页存 16 行。所以 3 层能存 1170 × 1170 × 16 ≈ **2190 万行**。根节点通常常驻内存，主键查询实际只需要 1~2 次磁盘 IO。

### Q3：主键为什么推荐用自增 ID，而不是 UUID？

* **满分话术**：聚簇索引的叶子节点按主键顺序存放数据。
  * **自增 ID** 每次都追加到最后一页的末尾，页写满了就开新页，写入是顺序的；
  * **UUID** 是随机的，新数据可能要插到某个已满的页中间，触发**页分裂**（一页拆成两页、移动数据），产生大量随机 IO 和碎片；
  * 另外，**每个二级索引的叶子节点都存了主键值**，UUID 是 36 字符的字符串，比 8 字节的 BIGINT 大得多，所有二级索引都会跟着变大。
  * 分布式场景下不能用数据库自增，可以用**雪花算法**这类趋势递增的 ID（黑马点评的 `RedisIdWorker` 也是“时间戳 + 序列号”的趋势递增思路）。

## 3. 聚簇索引、回表、覆盖索引、索引下推

> 代码：[02_index.sql 实验 2、3](code/02_index.sql#L28)、[实验 4.6](code/02_index.sql#L79)

### Q1：聚簇索引和非聚簇索引有什么区别？什么是回表？什么是覆盖索引？

* **满分话术**：
  * **聚簇索引（主键索引）**：叶子节点存放**整行数据**，数据本身就按主键组织，一张表只有一个。没有主键时 InnoDB 选第一个非空唯一索引，再没有就用隐藏的 row_id。
  * **非聚簇索引（二级索引）**：叶子节点只存**索引列的值 + 主键值**。
  * **回表**：用二级索引查整行时，先在二级索引树找到主键，再拿主键去聚簇索引树查整行，多走了一棵树（[实验 2.2](code/02_index.sql#L34)：`SELECT * WHERE name = ?`）。
  * **覆盖索引**：查询的列全部在二级索引里（包括主键），就不需要回表，EXPLAIN 的 Extra 显示 `Using index`（[实验 3.1](code/02_index.sql#L42)）。多查一个不在索引里的列，就又要回表了（[实验 3.2](code/02_index.sql#L46)）。这也是不建议 `SELECT *` 的原因之一。

### Q2：什么是索引下推（ICP）？

* **满分话术**：MySQL 5.6 引入的优化。以联合索引 `(city, age, name)`、条件 `city = '北京' AND name = 'user5'` 为例（[实验 4.6](code/02_index.sql#L79)）：
  * 没有索引下推时，存储引擎只能用 `city` 定位，把所有北京的记录都回表取出整行，交给 Server 层再判断 `name`；
  * 有索引下推后，存储引擎在遍历二级索引时，**直接用索引里已有的 name 先过滤**，只有满足条件的才回表，大大减少回表次数。EXPLAIN 的 Extra 显示 `Using index condition`。

## 4. 联合索引、最左前缀与索引失效

> 代码：[02_index.sql 实验 4~7](code/02_index.sql#L54)、[05_slow_sql.sql 实验 3](code/05_slow_sql.sql#L54)

### Q1：什么是最左前缀原则？怎么判断联合索引用了几列？

* **满分话术**：
  * 联合索引 `(city, age, name)` 的 B+ 树**先按 city 排序，city 相同再按 age，age 相同再按 name**。所以只有从最左边的列开始、连续地使用，才能利用这个有序性来定位（[实验 4](code/02_index.sql#L54)）：
    * `city = ?` ✓，`city = ? AND age = ?` ✓，三列都用 ✓；
    * 只有 `age = ?` ✗：age 只在 city 相同时才有序，全局是乱的（[实验 4.5](code/02_index.sql#L73)）。MySQL 8.0.13 的“索引跳跃扫描”在最左列区分度很低时能部分弥补；
    * `city = ? AND name = ?`：只有 city 能用来定位，name 通过索引下推过滤（[实验 4.6](code/02_index.sql#L79)）。
  * WHERE 里条件的**书写顺序无所谓**，优化器会自动调整（[实验 4.4](code/02_index.sql#L70)）。
  * **看 key_len 判断用了几列**（[计算规则](code/02_index.sql#L87)）：utf8mb4 的 `VARCHAR(n)` 是 n × 4 + 2，INT 是 4，允许 NULL 再加 1。实验里 city、city + age、三列全用的 key_len 分别是 82、86、288。

### Q2：范围查询对联合索引有什么影响？为什么说“等值在前，范围在后”？

* **满分话术**：联合索引中某一列用了范围查询（`>`、`<`、`BETWEEN`、`LIKE 'x%'`），**它后面的列就无法用于定位**了，因为在这个范围内后面的列不是整体有序的（[实验 4.7](code/02_index.sql#L83)：`city = ? AND age > ? AND name = ?` 的 key_len 只有 86）。
  * 所以建联合索引时，**等值查询的列放前面，范围查询的列放后面**。比如 `WHERE city = '北京' AND create_time BETWEEN ...`：
    * 建 `(city, create_time)`：先定位北京，北京的数据里 create_time 有序，直接取一段，扫描约 2000 行；
    * 建 `(create_time, city)`：时间是范围，所有城市这一周的约 1 万行都要扫一遍再过滤城市。
  * 实测对比见 [05 实验 3](code/05_slow_sql.sql#L54)。

### Q3：索引失效的常见场景有哪些？

* **满分话术**（[实验 5](code/02_index.sql#L93)，每组都有失效写法和正确写法的对比）：

  | 场景 | 例子 | 原因 |
  |---|---|---|
  | 对索引列使用函数 | `WHERE LEFT(name, 6) = 'user99'`（[5.1](code/02_index.sql#L96)） | 索引存的是原值，函数计算后的值在 B+ 树里是无序的 |
  | 对索引列做运算 | `WHERE id + 1 = 100`（[5.2](code/02_index.sql#L100)） | 同上，应该改成 `id = 99` |
  | 隐式类型转换 | 字符串列 `phone = 13800000100`（[5.3](code/02_index.sql#L104)） | MySQL 把字符串列转成数字再比较，相当于对索引列用了函数；反过来数字列和字符串常量比较不会失效 |
  | LIKE 以 % 开头 | `WHERE name LIKE '%99'`（[5.4](code/02_index.sql#L110)） | B+ 树按前缀有序，不知道从哪开始找 |
  | OR 连接了没索引的列 | `name = ? OR remark = ?`（[5.5](code/02_index.sql#L114)） | 有一边要全表扫描，干脆全部全表扫描；两边都有索引时可以 index_merge |
  | 不满足最左前缀 | 联合索引只用了后面的列（[4.5](code/02_index.sql#L73)） | 见 Q1 |
  | 优化器认为全表扫描更快 | `SELECT * WHERE city = '北京'`，北京占 20%（[4.1](code/02_index.sql#L58)） | 回表成本太高，优化器按成本选择，不是 bug |

### Q4：索引是不是越多越好？怎么设计索引？

* **满分话术**：不是。索引会占用磁盘空间，而且每次增删改都要同步维护所有索引，写入变慢。设计原则：
  * 给 **WHERE、JOIN、ORDER BY、GROUP BY** 里频繁使用的列建索引；
  * 优先选**区分度高**的列（比如手机号，而不是性别）；
  * 多个条件经常一起查时建**联合索引**，并按“等值在前、范围在后、区分度高的在前”排序，同时考虑能否做成**覆盖索引**；
  * 用联合索引代替多个单列索引，`(a, b)` 已经能覆盖只查 `a` 的场景；
  * 长字符串可以建**前缀索引** `KEY idx(email(10))`，但前缀索引用不了覆盖索引和排序；
  * 一张表的索引一般控制在 5 个左右。
* **真实项目反例**（[实验 7](code/02_index.sql#L138)）：黑马点评的 [`tb_voucher_order`](../repos/hm-dianping/src/main/resources/db/hmdp.sql#L1266) 只有主键，但“一人一单”要按 `user_id + voucher_id` 查询，会全表扫描。应该加唯一联合索引 `UNIQUE KEY (user_id, voucher_id)`：查询走索引，而且并发下即使代码层的锁失效，数据库也能用唯一约束兜底。同理 [`tb_follow`](../repos/hm-dianping/src/main/resources/db/hmdp.sql#L72) 也缺 `user_id` 上的索引。（这两个链接指向本地拉取的参考仓库）

### Q5：ORDER BY 怎么才能走索引？

* **满分话术**：B+ 树本身是有序的，如果排序字段和索引顺序一致，就可以直接按索引顺序读，不需要额外排序；否则 EXPLAIN 的 Extra 会出现 `Using filesort`（[实验 6](code/02_index.sql#L122)）。
  * `ORDER BY create_time LIMIT 10` 顺着 `idx_create_time` 读前 10 条即可（[6.1](code/02_index.sql#L125)）；
  * 联合索引 `(city, age, name)` 在 `city`、`age` 都是等值时，`ORDER BY name` 不用排序（[6.3](code/02_index.sql#L131)）；跳过了 `age` 就需要 filesort（[6.4](code/02_index.sql#L134)）。

## 5. 事务与隔离级别

> 代码：[03_transaction_lock.sql 实验 1、2](code/03_transaction_lock.sql#L35)（两个会话交替执行）

### Q1：ACID 是什么？分别靠什么实现？

* **满分话术**：
  * **原子性（Atomicity）**：事务要么全做，要么全不做。靠 **undo log** 实现，回滚时按 undo log 反向操作。
  * **持久性（Durability）**：提交后数据不丢。靠 **redo log** 实现，提交时先把 redo log 刷盘，宕机后可以重放恢复。
  * **隔离性（Isolation）**：并发事务互不干扰。靠 **锁 + MVCC** 实现。
  * **一致性（Consistency）**：数据从一个正确状态变到另一个正确状态（比如转账前后总额不变）。它是**目的**，由前三者加上应用层的业务逻辑共同保证。

### Q2：并发事务会有哪些问题？四种隔离级别分别能解决什么？

* **满分话术**：
  * **脏读**：读到别的事务**未提交**的数据（[实验 1](code/03_transaction_lock.sql#L35)）；
  * **不可重复读**：同一事务内两次读**同一行**，结果不同（被别人修改并提交了）；
  * **幻读**：同一事务内两次按**同一条件**查询，结果集的**行数**不同（被别人插入了新行）。

  | 隔离级别 | 脏读 | 不可重复读 | 幻读 |
  |---|---|---|---|
  | 读未提交 READ UNCOMMITTED | 有 | 有 | 有 |
  | 读已提交 READ COMMITTED（RC） | 无 | 有 | 有 |
  | 可重复读 REPEATABLE READ（RR，MySQL 默认） | 无 | 无 | InnoDB 基本解决 |
  | 串行化 SERIALIZABLE | 无 | 无 | 无 |

  * RC 和 RR 的区别可以在 [实验 2](code/03_transaction_lock.sql#L58) 里直接看到：同样的操作，RC 第二次读到了新值，RR 还是旧值。
  * **MySQL 为什么默认 RR**：历史原因。早期 binlog 只有 statement 格式，在 RC 下主从执行顺序不同会导致数据不一致。现在 binlog 默认 row 格式，很多互联网公司会改成 **RC**，好处是不加间隙锁、并发更高、死锁更少。

## 6. MVCC

> 代码：[03_transaction_lock.sql 实验 2、3、4](code/03_transaction_lock.sql#L58)

### Q1：讲一下 MVCC 的原理？（快手、小红书一面）

* **满分话术**：MVCC（多版本并发控制）让**读不加锁、读写不冲突**，靠三样东西实现：
  1. **隐藏字段**：每行记录有 `DB_TRX_ID`（最近一次修改它的事务 ID）和 `DB_ROLL_PTR`（回滚指针，指向 undo log 里的上一个版本）。
  2. **undo log 版本链**：每次修改不是直接覆盖，而是把旧版本写进 undo log，用回滚指针串成一条从新到旧的链表。
  3. **ReadView（读视图）**：事务执行快照读时生成，包含四个字段：
     * `m_ids`：生成 ReadView 时还**活跃（未提交）**的事务 ID 列表；
     * `min_trx_id`：m_ids 里最小的；
     * `max_trx_id`：生成时**下一个将要分配**的事务 ID；
     * `creator_trx_id`：创建这个 ReadView 的事务自己的 ID。
  4. **可见性判断**：从版本链最新的版本开始，拿它的 `DB_TRX_ID` 比较：
     * 等于 `creator_trx_id`：自己改的，可见；
     * 小于 `min_trx_id`：生成 ReadView 前就已提交，可见；
     * 大于等于 `max_trx_id`：生成 ReadView 之后才开启的事务改的，不可见；
     * 在两者之间：在 `m_ids` 里说明还没提交，不可见；不在说明已提交，可见。
     * 不可见就顺着回滚指针找上一个版本，直到找到可见的版本。

### Q2：RC 和 RR 在 MVCC 上的区别是什么？

* **满分话术**：唯一的区别是 **ReadView 的生成时机**：
  * **RC**：**每次 SELECT** 都生成新的 ReadView，所以能读到别人刚提交的数据，出现不可重复读；
  * **RR**：只在事务中**第一次 SELECT** 时生成，之后一直复用，所以同一事务内读到的数据始终一致（[实验 2](code/03_transaction_lock.sql#L58)）。
  * 注意是“第一次 SELECT”而不是 `BEGIN`：只 BEGIN 不查询，别人提交的修改依然能看到（[实验 4](code/03_transaction_lock.sql#L110)）。想在开启事务时立刻生成快照，用 `START TRANSACTION WITH CONSISTENT SNAPSHOT`。

### Q3：RR 级别能完全解决幻读吗？

* **满分话术**：基本解决，但不是完全解决。
  * **快照读**（普通 SELECT）靠 MVCC，读的是 ReadView 那一刻的版本，看不到别人新插入的行；
  * **当前读**（`FOR UPDATE`、UPDATE、DELETE）靠 **Next-Key Lock** 锁住记录和间隙，别人插不进来（[实验 6](code/03_transaction_lock.sql#L145)）。
  * **特殊情况**：事务 A 先快照读，事务 B 插入一行并提交，A 再对这一行执行 UPDATE（当前读能看到它），UPDATE 之后这一行的 `DB_TRX_ID` 变成了 A 自己，A 再快照读就能看到这一行了，产生幻读。避免办法是在事务开始时就用 `FOR UPDATE` 当前读加锁。

## 7. 锁

> 代码：[03_transaction_lock.sql 实验 3、5~8](code/03_transaction_lock.sql#L89)

### Q1：普通 SELECT 会加锁吗？什么是快照读和当前读？

* **满分话术**（[实验 3](code/03_transaction_lock.sql#L89)，最重要的一个实验）：
  * **快照读**：普通 `SELECT`，**不加锁**，通过 MVCC 读历史版本；
  * **当前读**：`SELECT ... FOR UPDATE`（加 X 排他锁）、`SELECT ... FOR SHARE` / `LOCK IN SHARE MODE`（加 S 共享锁）、`INSERT`、`UPDATE`、`DELETE`，读**最新已提交**的版本并加锁。
  * 实验现象：RR 下事务 A 先读到余额 100，B 改成 200 并提交；A 普通 SELECT 还是 100，`FOR UPDATE` 读到 200，执行 `balance = balance + 10` 后是 210。
  * **业务启示**：先普通 SELECT 拿到余额，在 Java 里算好再 UPDATE 写回，会覆盖别人的修改（**丢失更新**）。正确做法是 `SELECT ... FOR UPDATE` 加锁后再算，或者直接 `UPDATE ... SET balance = balance - ? WHERE id = ? AND balance >= ?`，用数据库的原子更新（路线里“防超卖”的思路）。

### Q2：InnoDB 有哪些锁？

* **满分话术**：
  * **按粒度**：表锁、行锁。InnoDB 支持行锁，但**行锁是加在索引上的**。
  * **按模式**：共享锁 S（读锁，S 和 S 兼容）、排他锁 X（写锁，和任何锁都不兼容）。
  * **意向锁** IS / IX：表级锁，事务给某行加 S / X 锁前，先在表上加 IS / IX。作用是加表锁时不用逐行检查有没有行锁，看一眼意向锁就知道。
  * **行锁的三种形态**：
    * **记录锁（Record Lock）**：只锁一条索引记录；
    * **间隙锁（Gap Lock）**：锁两条记录之间的间隙，不锁记录本身，只为了**阻止插入**，间隙锁之间不冲突；
    * **临键锁（Next-Key Lock）**：记录锁 + 前面的间隙锁，左开右闭区间，是 RR 下加锁的**基本单位**。
  * 另外还有插入意向锁（INSERT 前加的一种特殊间隙锁）和 AUTO-INC 锁。

### Q3：`SELECT ... FOR UPDATE` 到底加什么锁？没有索引为什么会锁全表？

* **满分话术**：RR 级别下，加锁的基本单位是 Next-Key Lock，然后在某些情况下退化：

  | 场景 | 加锁情况 | 实验 |
  |---|---|---|
  | 唯一索引等值查询，记录存在 | 退化为**记录锁**，只锁这一行 | — |
  | 唯一索引等值查询，记录不存在 | 退化为**间隙锁**，锁住它所在的间隙 | [实验 5](code/03_transaction_lock.sql#L126)：`id = 7` 锁住 (5, 10)，插入 8 阻塞、插入 12 成功 |
  | 普通索引上的范围查询 | 扫描到的每条记录加 **Next-Key Lock**，回表的主键记录加记录锁 | [实验 6](code/03_transaction_lock.sql#L145)：`k BETWEEN 10 AND 15`，插入 k = 12 和 k = 7 都阻塞 |
  | **WHERE 条件没有索引** | 只能全表扫描聚簇索引，扫描过的**每一行都加 Next-Key Lock，等于锁表** | [实验 7](code/03_transaction_lock.sql#L168)：`v = 10` 只命中 1 行，但改别的行也阻塞 |

  * 结论：**UPDATE、DELETE、FOR UPDATE 的 WHERE 条件一定要走索引**，否则并发一高整张表都被锁住。
  * 观察方法：查询 `performance_schema.data_locks`（[脚本开头](code/03_transaction_lock.sql#L21)），`LOCK_MODE` 为 `X` 是 Next-Key Lock，`X,REC_NOT_GAP` 是记录锁，`X,GAP` 是间隙锁。

### Q4：遇到过死锁吗？怎么排查和避免？

* **满分话术**（[实验 8](code/03_transaction_lock.sql#L188)）：
  * **成因**：两个事务互相持有对方需要的锁。比如 A 锁了账户 1 要锁账户 2，B 锁了账户 2 要锁账户 1。
  * **InnoDB 的处理**：开启了死锁检测（`innodb_deadlock_detect`），发现等待环后**主动回滚代价小的那个事务**，报错 `1213 Deadlock found`；另外还有锁等待超时 `innodb_lock_wait_timeout`（默认 50 秒）兜底。
  * **排查**：`SHOW ENGINE INNODB STATUS` 里的 `LATEST DETECTED DEADLOCK` 段会打印两个事务各自持有和等待的锁、执行的 SQL。
  * **避免**：多个事务**按相同顺序加锁**（转账时总是先锁 id 小的账户）；事务尽量小、尽快提交；加锁条件走索引减少锁范围；业务允许的话用 RC 减少间隙锁。

### Q5：乐观锁和悲观锁有什么区别？

* **满分话术**：
  * **悲观锁**：认为一定会冲突，先加锁再操作，比如 `SELECT ... FOR UPDATE`、`synchronized`。适合写多、冲突多的场景。
  * **乐观锁**：认为很少冲突，不加锁，更新时再检查数据有没有被改过。常见两种写法：版本号 `UPDATE ... SET stock = stock - 1, version = version + 1 WHERE id = ? AND version = ?`；或者直接用条件 `UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0`（黑马点评秒杀防超卖就是这种）。看影响行数是否为 0 判断成功与否。适合读多写少的场景，冲突多时大量失败重试反而更慢。

## 8. 三大日志与主从复制

> 代码：[04_log_replication.sql](code/04_log_replication.sql)

### Q1：redo log、undo log、binlog 分别是什么？

* **满分话术**：
  * **redo log（重做日志）**：InnoDB 引擎层的**物理日志**，记录“某个数据页的某个位置改成了什么”。InnoDB 修改数据时先改内存里的 Buffer Pool，再写 redo log，脏页由后台慢慢刷盘，这叫 **WAL（先写日志）**：把随机写数据页变成了顺序写日志，性能高；宕机后用 redo log 重放，保证**持久性**（crash-safe）。redo log 大小固定、**循环写**，已刷盘的部分可以被覆盖。
  * **undo log（回滚日志）**：InnoDB 的**逻辑日志**，记录修改前的旧值（插入记一条对应的删除，更新记旧值）。两个作用：事务回滚时用来恢复数据，保证**原子性**；作为 **MVCC 的版本链**。
  * **binlog（归档日志）**：MySQL **Server 层**的**逻辑日志**，所有存储引擎都有，记录对数据的所有修改，**追加写**，不会覆盖。用于**主从复制**和**按时间点恢复数据**。格式有 statement（记录 SQL）、row（记录每行改前改后的值，默认，最准确）、mixed（[实验 2](code/04_log_replication.sql#L23) 可以亲眼看到 row 格式的内容）。

### Q2：redo log 和 binlog 有什么区别？既然有 binlog，为什么还要 redo log？

* **满分话术**：

  | | redo log | binlog |
  |---|---|---|
  | 层次 | InnoDB 引擎层 | Server 层，所有引擎通用 |
  | 内容 | 物理日志：哪个页改了什么 | 逻辑日志：哪行数据改成了什么 / 执行了什么 SQL |
  | 写法 | 固定大小，循环写 | 追加写，写满切换新文件 |
  | 用途 | 崩溃恢复 | 主从复制、数据恢复 |

  * binlog 没有 crash-safe 能力：它不知道哪些数据已经刷到了磁盘数据页、哪些还没刷，宕机后无法判断该恢复哪些。redo log 循环写，只记录还没刷盘的那部分修改，正好用来做崩溃恢复。

### Q3：什么是两阶段提交？为什么需要它？

* **满分话术**：一个事务提交时要同时写 redo log 和 binlog，必须保证两者一致，否则用 binlog 同步的从库会和主库不一致。流程：
  1. **prepare 阶段**：写 redo log，状态标记为 prepare；
  2. **写 binlog**；
  3. **commit 阶段**：redo log 状态改为 commit。
* **崩溃恢复规则**：
  * redo log 是 commit：直接提交；
  * redo log 是 prepare：去查 binlog 里有没有这个事务的完整记录（靠 XID 关联）。**binlog 完整就提交**（因为从库可能已经同步了），**不完整就回滚**。
* 如果不用两阶段提交：先写 redo 后写 binlog，中间宕机，主库有这条数据、从库没有；反过来先写 binlog，主库没有、从库有。

### Q4：主从复制的原理是什么？主从延迟怎么办？

* **满分话术**：
  * **流程**（三个线程）：主库提交事务时写 binlog；从库的 **IO 线程**连接主库，主库的 **binlog dump 线程**把 binlog 发过来，IO 线程写到本地的 **relay log（中继日志）**；从库的 **SQL 线程**读取 relay log 重放，数据就和主库一致了（配置和观察命令见 [脚本](code/04_log_replication.sql#L53)）。
  * **复制模式**：默认**异步复制**，主库不等从库，性能好但主库宕机可能丢数据；**半同步复制**要求至少一个从库收到 binlog 后主库才返回提交成功。
  * **主从延迟的原因**：从库机器配置差、从库上跑了大查询、主库有**大事务**（从库要等它执行完）、从库重放是单线程。
  * **解决办法**：
    * 对一致性要求高的读（比如刚下单立刻查订单）**强制走主库**；
    * 开启**并行复制**（`replica_parallel_workers`）；
    * 拆分大事务，避免一次删几百万行；
    * 监控 `Seconds_Behind_Source`，延迟过大时把读流量切回主库。

## 9. 慢 SQL 优化

> 代码：[05_slow_sql.sql](code/05_slow_sql.sql)；和 Java 的结合见 [Spring Boot 第 9 节的 MyBatis 慢 SQL 插件](../05-springboot/八股.md#9-mybatis)

### Q1：线上有一条慢 SQL，你怎么定位和优化？

* **满分话术**：
  1. **发现**：开启慢查询日志（`slow_query_log`、`long_query_time`），用 `mysqldumpslow` 或 `pt-query-digest` 按总耗时、执行次数排序找出最值得优化的 SQL（[实验 1](code/05_slow_sql.sql#L8)）；应用层也可以用 MyBatis 插件或 APM 监控记录慢 SQL。
  2. **分析**：`EXPLAIN` 看执行计划，`EXPLAIN ANALYZE`（8.0.18+）看每一步的实际耗时和扫描行数。
  3. **按顺序排查**（[优化清单](code/05_slow_sql.sql#L85)）：
     * `type` 是 ALL / index、`key` 是 NULL → 没走索引：加索引，或者改写导致索引失效的写法；
     * `key_len` → 联合索引是否只用了一部分，是否被范围查询截断；
     * `Extra`：`Using filesort` 让排序走索引，`Using temporary` 给分组字段加索引，没有 `Using index` 考虑覆盖索引；
     * `rows` → 扫描行数远大于返回行数，说明过滤效率低。
  4. **验证**：改完再 EXPLAIN ANALYZE 对比，确认扫描行数和耗时下降。
  5. **SQL 之外**：大表数据归档、分库分表；读多写少加缓存；复杂报表放到从库或数仓。

### Q2：EXPLAIN 的各个字段怎么看？

* **满分话术**：重点看四个（[02_index.sql 开头](code/02_index.sql#L1)有说明）：
  * **type**：访问类型，从好到差 `system > const > eq_ref > ref > range > index > ALL`。至少要达到 range，最好是 ref；`index` 是扫描整棵索引树，`ALL` 是全表扫描。
  * **key**：实际使用的索引；`possible_keys` 是可能用到的。
  * **key_len**：使用的索引长度，判断联合索引用了几列。
  * **Extra**：`Using index` 覆盖索引（好）、`Using index condition` 索引下推（好）、`Using where` Server 层过滤、`Using filesort` 额外排序（差）、`Using temporary` 用了临时表（差）。
  * 另外 `rows` 是**估算**的扫描行数，`filtered` 是经过条件过滤后剩下的百分比。

### Q3：深分页 `LIMIT 1000000, 10` 为什么慢？怎么优化？

* **满分话术**（[实验 2](code/05_slow_sql.sql#L26)）：
  * **原因**：MySQL 要先找出前 1000010 条记录，再扔掉前 1000000 条，只返回 10 条。如果是 `SELECT *` 还要对这一百万条都回表，优化器甚至会直接放弃索引改成全表扫描加排序。
  * **优化一：延迟关联**（[2.2](code/05_slow_sql.sql#L33)）：子查询只查主键 `SELECT id ... LIMIT 1000000, 10`，在二级索引上用覆盖索引完成翻页，不回表；外面再拿这 10 个 id 关联回原表。
  * **优化二：游标分页**（[2.3](code/05_slow_sql.sql#L42)，推荐）：记住上一页最后一条的排序值，`WHERE create_time > 上一页最后的值 ORDER BY create_time LIMIT 10`，无论翻到哪一页都只扫 10 行。缺点是不能直接跳到第 N 页，适合 App 下拉加载。
  * **业务上**：限制最大页数（比如搜索结果只给前 100 页）。

## 高频追问速查

| 问题 | 一句话答案 |
|---|---|
| InnoDB 和 MyISAM 的区别？ | InnoDB 支持事务、行锁、外键、崩溃恢复，使用聚簇索引；MyISAM 只有表锁、不支持事务，索引和数据分开存 |
| 一张表能有几个聚簇索引？ | 1 个，因为数据只能按一种顺序存放 |
| 为什么不建议用 `SELECT *`？ | 无法使用覆盖索引、多传输无用数据、表结构变更后可能出错 |
| `IN` 和 `EXISTS` 怎么选？ | 外表大、子查询表小用 `IN`；外表小、子查询表大用 `EXISTS`（遵循小表驱动大表），8.0 的优化器很多情况下会自动转换 |
| `UNION` 和 `UNION ALL` 的区别？ | `UNION` 去重（需要排序或临时表），`UNION ALL` 不去重更快，确定没有重复时优先用后者 |
| `CHAR` 和 `VARCHAR` 的区别？ | `CHAR` 定长，不足补空格，适合长度固定的值；`VARCHAR` 变长，额外 1~2 字节存长度 |
| 金额用什么类型？ | `DECIMAL`，不能用 `FLOAT` / `DOUBLE`（有精度误差）；或者以“分”为单位存 `BIGINT` |
| 大表加索引会锁表吗？ | 8.0 的 Online DDL 加普通索引不阻塞读写（`ALGORITHM=INPLACE, LOCK=NONE`），但会消耗大量 IO，要在低峰期执行；更稳妥用 gh-ost / pt-osc |
| 什么是 Buffer Pool？ | InnoDB 在内存里缓存数据页和索引页的区域，读写都先操作它，用改进的 LRU（分新老区）管理，防止全表扫描把热点数据挤出去 |
| 一条更新语句的执行流程？ | 连接器 → 分析器 → 优化器 → 执行器 → InnoDB：读数据页到 Buffer Pool → 写 undo log → 改内存数据 → 写 redo log（prepare）→ 写 binlog → redo log commit |
